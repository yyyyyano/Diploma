# «Кошт» — ИИ финансово-правовой ассистент для граждан Беларуси

Веб-приложение на localhost + Telegram-бот: чеки по фото, импорт выписок любого банка, категоризация,
ИИ-агент с инструментами, правовая база по текстам pravo.by с дословными цитатами, налоговые вычеты,
лимиты, цели, календарь, Excel. Курсовой MVP, затем диплом — достраивается без переписывания MVP.
Один разработчик + агенты. Всё бесплатно и локально (машина без NVIDIA: Intel Arc, 36 ГБ RAM).

**Состояние:** требования и архитектура согласованы; кода ещё нет. Следующий этап — «бетонная» фаза
(каркас, проверки, пустые модули — `docs/ARCHITECTURE.md` §13), затем модули по `docs/CAPABILITIES.md`.

## Золотые правила

1. **Числа считает код, а не модель (P1, P2).** Любая сумма, процент, срок, остаток — в `packages/calc`,
   результат `{ value, trace }`, трасса сохраняется для «Откуда эта цифра?». Сайт денег не считает.
   Агент пишет только те числа, что есть в результатах инструментов.
2. **Изоляция данных (ROLE-01, SEC-04, PRIV-07).** Код, трогающий данные пользователя, получает
   `s: ScopedDb` первым аргументом; в запросе к каждой пользовательской таблице — свой `s.own(таблица)`.
   «Чьи данные» никогда не берутся из входа (тело запроса, аргументы модели, нагрузка задачи).
   `ISOLATION_VIOLATION` — баг запроса, его не обходят. Подробно — `.claude/rules/database.md`, ADR-0006.
3. **Границы модулей.** В чужой модуль — только через его `index.ts` и только если он в `dependsOn`
   (`tooling/architecture/modules.ts`). Вниз — фасад, вверх — событие, подстановка — реестр. Новая
   зависимость — правка `modules.ts` с обоснованием в итоге задачи; связь вверх — только через ADR.
4. **Тесты рядом с кодом.** `x.test.ts` (без БД), `x.int.test.ts` (настоящий Postgres) в той же папке;
   отдельно только `e2e/` и `packages/testing`. Тесты офлайн: модели — кассеты, интернет — фикстуры.
5. **Документы живые (SPEC §0).** Если требование противоречит другому, макету, архитектуре или есть
   заметно лучший путь — **не обходи молча**: остановись (`ESCALATE`; у критика и ревьюера — `ASK_USER`),
   опиши проблему, предложи вариант. Принятое изменение вносится в SPEC/ADR/паспорт в том же коммите, что и код.
   Внешний вид — по макету, поведение — по SPEC; при расхождении прав SPEC (DES-00).
6. **Не выдумывать результаты.** Числа в отчётах, README и комментариях — только из реальных запусков.
   «Тесты прошли» пишется после запуска, с выводом. Ставки, сроки, нормы — только из первоисточника.
7. **Планка не опускается.** `CONSTRAINTS.md` не ослабляют ради зелёного: без `@ts-ignore`, отключения
   правил линтера, `.skip`/`.only`, удаления тестов, заглушек. Что-то мешает — `BLOCKED`
   (нужно решение пользователя — `ESCALATE`).
8. **Язык.** Тексты, комментарии, паспорта, правила, ADR, коммиты, интерфейс — по-русски. Имена в коде,
   коды ошибок, события, задачи, ключи логов, описания инструментов агента — по-английски.
   Комментарий объясняет «почему» и ссылается на требование: `// RCPT-10: без пары — предварительная`.
   Файлы и папки — kebab-case (React-компоненты — PascalCase), таблицы БД — snake_case во множественном числе,
   только именованный экспорт, импорты относительные с `.ts`, без алиасов `@/`.
9. **Секреты и реальные данные.** Ключей нет в коде и в git (только `.env.example`); `samples/`, `data/`,
   `models/`, `secrets/` — вне git (NFR-16, NFR-18). В логах — ключ события и id, без текстов и сумм (OBS-04).

## Команды

Единая точка входа — `Makefile` (NFR-14). **Он появляется в бетонной фазе**; до этого команд нет —
не выдумывай их и не запускай `pnpm`-скрипты в обход. После бетона источник правды — `make help`.

| Группа | Цели |
|---|---|
| Первый запуск | `init` (`.env`, секреты, хуки), `install`, `doctor` (Node, pnpm, Docker Engine, группы, порты) |
| Запуск | `dev` (БД и модели в контейнерах, код на хосте), `up` (всё в контейнерах), `down`, `restart`, `ps`, `build`, `db-up` (только Postgres) |
| Логи | `logs`, `log-find id=<requestId>` |
| БД и демо | `migrate`, `db-generate`, `db-shell`, `db-reset` (спросит `yes`), `demo-reset`, `backup`, `restore file=…` |
| Качество | `fmt`, `fmt-check`, `format-file FILE=…` и `lint-file FILE=…` (для хука правки файла), `lint`, `typecheck`, `deps-check`, `test`, `test-int`, `e2e`, `check`, `check-quick`, `check-full`, `check-commits`, `audit`, `bench` |
| ИИ | `ai-record SCENARIO=…` (перезапись кассет, тратит лимиты), `eval` (QA-10, тратит лимиты) |
| Заготовки | `new-module id=…`, `new-feature id=…`, `new-table module=… name=…`, `capabilities` (таблица CAPABILITIES из `modules.ts`) |

«Готово» = `make check` зелёный (локально, хвост вывода — в итоге задачи); для экранов ещё `make e2e` (axe).
`check-quick` — `pre-push` (типы, границы, быстрые тесты); `check-full` — `check` + `e2e` + `audit` + бюджет бандла.
Пороги и бюджеты времени — `CONSTRAINTS.md`.

## Git

- Локальный репозиторий, ветка `main`. **Без `git push`** — публикует только пользователь (NFR-17).
- Задача делается в ветке `task/<ID>-<slug>`; история не переписывается (`--amend`, `rebase`,
  `reset --hard`, `--no-verify` заблокированы хуками — исправляй причину отказа).
- Conventional Commits: `тип(область): описание` — заголовок 15–72 символа, описательный, тема по-русски,
  тип латиницей (`feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`, `build`, `style`, `revert`).
  Область необязательна; если указана — id модуля из `docs/CAPABILITIES.md` или `web`, `server`,
  `kernel`, `calc`, `contract`, `i18n`, `testing`, `e2e`, `tooling`, `docker`, `docs`, `deps`.
  Пример: `feat(receipts): перепроверять спорные строки чека моделью`.
- Размер коммита проверяет хук: предупреждение от 400 строк, отказ от 800 (трейлер `Large-Commit: <причина>`),
  меньше 3 строк — только `docs/chore/style/fix/revert` или трейлер `Small-Commit: <причина>`.
- Подписи ИИ в коммитах запрещены (`Co-Authored-By: …`, «Generated with …», упоминания модели и т. п.) —
  их отклоняет хук `commit-msg` (`tooling/git-hooks/check-no-ai-attribution.mjs`).

## Конвейер агентов

Разработка идёт **строго последовательно, по одной задаче**; задача плана (`tasks/plan.md`) — крупный цельный
кусок тесно связанной работы (например, «модуль `receipts` целиком»), а не мелкий шаг.
Задача выполняется циклом ролей из `.claude/agents/`: **critic** (проверяет задачу до кода) → **implementer**
(пишет код и тесты, коммитит) → **reviewer** (качество и *строгое* соблюдение архитектуры, конвенций, паспортов
и правил; отступление — только с причиной в итоге задачи и ADR, если меняет правило) → **fixer** (правит по
замечаниям). Не больше 3 ревью и 2 правок, затем вопрос пользователю.
Запуск: `/task-cycle <ID>`; `/task-cycle auto` — задачи подряд до точки остановки (провал проверок, нужен выбор
пользователя, рискованная задача, исчерпан лимит правок, конец фазы, по умолчанию 5 задач подряд). Принятая
задача перематывается в `main` (в `auto` — сразу, иначе — после «да» пользователя). Роли возвращают итог
только ответом в главную сессию (первая строка — `VERDICT: …`), файлов-отчётов нет; итог пользователю — в чате,
статус задачи — в `tasks/plan.md`.
«Итог задачи» (в правилах и ADR) — ответ роли (блоки «Отступления», «Паспорта и документы») и отчёт дирижёра в чате.
Планирование (`/as-plan`, скилл planning-and-task-breakdown): план пишется **только** в `tasks/plan.md`, формат задач —
раздел «План» в `.claude/commands/task-cycle.md`; `tasks/todo.md` не создаётся.
Определение готовности — `.claude/references/definition-of-done.md` + `CONSTRAINTS.md`.
