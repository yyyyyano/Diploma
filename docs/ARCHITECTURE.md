# Архитектура «Кошта»

> Как устроен код и почему именно так. Требования — только в `SPEC.md`; карта модулей — `docs/CAPABILITIES.md`;
> обоснования и отвергнутые варианты — `docs/adr/`. Документ описывает **целевое** устройство: кода ещё нет,
> он появляется в бетонной фазе (§13). Если код и документ разошлись — это ошибка одного из них: остановись
> и выясни (SPEC §0 «Документы живые»), а принятое изменение внеси сюда или в ADR в том же коммите.
> Детали, замеры и источники — в `research/architecture/01…14` (справочно; где 13 и 14 расходятся, прав 14).

## 1. Обзор системы

```
 Браузер (сайт, SPA)            Telegram (личные чаты)
   │ HTTP: oRPC + SSE              │ long polling (бот сам опрашивает Telegram)
   ▼                               ▼
┌─────────── apps/server: один код, три процесса ─────────────────────────────────┐
│  api     — oRPC, поток чата, events.stream (SSE), статика сайта;                 │
│            слушатели local 127.0.0.1:8140 и lan :8141 (выкл. по умолчанию)       │
│  worker  — задачи pg-boss: чеки, выписки, загрузчик законов (один поток),        │
│            эмбеддинги, расписания, подписки на события, итоги недели             │
│  bot     — grammY, один опрашивающий (advisory lock Postgres)                    │
└───────┬───────────────────────────┬───────────────────────────┬─────────────────┘
        │ SQL, pg-boss, LISTEN/NOTIFY│ OpenAI-совместимый HTTP    │ OTLP
        ▼                            ▼                            ▼
  PostgreSQL 18 + pgvector     llama-server (чат, зрение,     Langfuse v4 (трассы ИИ,
  (данные, очередь, сигналы)   эмбеддинги) · whisper.cpp      127.0.0.1:3001)
        внешние: Groq → Z.ai (облако, по согласию) · pravo.by · API НБРБ · SMTP · Telegram Bot API
```

- **Процессы общаются только через Postgres**: задачи pg-boss и мгновенные сигналы `LISTEN/NOTIFY`
  (прогресс чека из `worker` доходит до браузера через `api` → `events.stream`). Одна топология в разработке
  и на показе.
- **Внешний мир — за портами** (интерфейсами): модели, pravo.by, НБРБ, Telegram, почта, файлы, часы.
  В тестах каждый порт подменяется офлайн-реализацией (§12).
- **Облачные модели** — только для пользователей с облачным согласием (PRIV-02) и для задач без данных
  пользователя (PRIV-09); иначе — локальные. Эмбеддинги — всегда локально (NFR-05).

| Сервис | Адрес по умолчанию | Примечание |
|---|---|---|
| Сайт и API, «локальный вход» | `http://127.0.0.1:8140` | первый запуск, почтовый ящик, демо-вход, микрофон — только здесь |
| «Сетевой вход» | `:8141` | слушатель открывается переключателем в админке (NFR-24) |
| Vite (режим `make dev`) | `127.0.0.1:5173` | проксирует `/api` на 8140 |
| PostgreSQL | `127.0.0.1:5440` | публикуется всегда с адресом |
| llama-server | `127.0.0.1:8142` | режим роутера: чат, зрение, эмбеддинги |
| whisper.cpp server | `127.0.0.1:8143` | речь локально |
| Langfuse | `127.0.0.1:3001` | только для разработчика, регистрация закрыта |

Порты согласованы с пользователем (2026-10-24, `10-consensus.md`): не пересекаются с другими проектами на машине;
`make doctor` проверяет, что они свободны.

| Папка | Отвечает за | Запрещено (проверяется) |
|---|---|---|
| `apps/web` | экраны, состояния, взаимодействия | импорт `apps/server`, `packages/calc`, `packages/testing` (кроме тестов); «сырые» цвета вне `ui/theme`; текст литералом |
| `apps/server/src/entrypoints` | старт процесса, сигналы завершения | бизнес-логика (только `compose()` и старт) |
| `apps/server/src/main` | создать платформу, модули по порядку `modules.ts`, зарегистрировать роутеры, задачи, подписки, инструменты, каналы, обработчики | логика сверх «соединить» |
| `apps/server/src/platform` | техника без бизнеса | импорт любых `modules/*` |
| `apps/server/src/modules/<id>` | одна возможность SPEC целиком | глубокий импорт чужого модуля; зависимость не из `dependsOn` |
| `packages/kernel` | типы, нужные всем | зависимости, кроме `zod` |
| `packages/calc` | расчёты | всё, кроме `kernel`: ни БД, ни сети, ни `Date.now()`, ни `Math.random()` |
| `packages/contract` | форма данных «на проводе» | серверный код; зависимости, кроме `zod`, `@orpc/contract`, `kernel` |
| `packages/i18n` | тексты и форматы | импорт приложений; зависимости, кроме `i18next`, `kernel`, `contract` (в тестах — и `calc`) |
| `packages/testing` | помощники тестов | импорт из боевого кода; `pg` и `drizzle-orm` — только в `src/db` (шаблонная БД, §12) |
| `e2e/` | ключевые сценарии + axe | походы в интернет |
| `datasets/` | эталонные данные с описанием происхождения | реальные выписки и фото пользователя (NFR-18) |

**Почему три пакета, а не один «shared».** `kernel` — «что такое деньги и дата» (меняется почти никогда),
`calc` — «как считать» (самые строгие тесты), `contract` — «как выглядит на проводе» (меняется ради экранов).
Добавили поле «Заметка» в карточку операции — меняется `contract`, `calc` не перекомпилируется.
UI-кит — не пакет: потребитель один (`apps/web/src/ui`), вынос в `packages/ui` механический, когда появится
второй. Связь пакетов — без сборки: в `exports` лежит `.ts`, Node 26 и Vite читают исходники (ADR-0002).

## 3. Процессы и корень композиции

| Процесс | Что делает | Почему отдельно |
|---|---|---|
| `api` | oRPC (сайт), поток чата, `events.stream`, статика, два слушателя | отвечает быстро; тяжёлый разбор PDF/HEIC его не тормозит |
| `worker` | обработчики pg-boss: распознавание, импорт, загрузчик законов, эмбеддинги, расписания, подписки | падение или долгий разбор не роняет сайт; загрузчик pravo.by живёт строго в одном процессе (LAW-35) |
| `bot` | grammY, long polling под консультативной блокировкой Postgres | смена токена в админке перезапускает только бота; два запуска не дерутся за опрос (ошибка 409) |

Все три вызывают `compose(config, role)` (`main/compose.ts`): создать платформу → создать модули в порядке
топологической сортировки `modules.ts` (обычные функции `create<Id>Module(deps)`, без DI-контейнера и
декораторов) → зарегистрировать в реестрах роутеры, задачи, подписки, инструменты агента, каналы доставки,
обработчики отмены/подтверждения, владельцев данных, настройки → вернуть то, что нужно роли. Тест сверяет
порядок в `compose.ts` с `modules.ts`. Завершение по `SIGTERM` — корректное: досылаются задачи, закрывается пул.
Миграции применяются при старте под `pg_advisory_lock` (одинаково в обоих режимах запуска).

## 4. Устройство модуля сервера

### 4.1 Раскладка

У маленьких модулей лишних папок нет. Пример — `receipts`:

```
modules/receipts/
├─ CLAUDE.md                     паспорт (docs/templates/module-passport.md)
├─ index.ts                      ПУБЛИЧНЫЙ API: export type { ReceiptsFacade }; export { createReceiptsModule }
├─ module.ts                     фабрика: сценарии, фасад, роутер, задачи, подписки, инструменты, userData, sweeps, undo
├─ facade.ts                     что модуль даёт ДРУГИМ модулям (узко, по их нуждам)
├─ events.ts                     события, которые модуль публикует: имя + Zod-схема нагрузки
├─ settings.ts                   defineSetting: допуск 0,01 BYN, попыток перепроверки 2 (RCPT-05/06)
├─ user-data.ts                  defineUserData: таблицы и файлы для экспорта и удаления (PRIV-05/06)
├─ domain/                       чистые правила: статусы и переходы, ключ дубля, текст перепроверки, гарантия
├─ application/                  сценарии — по файлу: upload-receipts.ts, recognize-receipt.ts, edit-receipt-items.ts…
│  ├─ ports.ts                   QrDecoder, ImagePreparer — внешний мир модуля
│  └─ receipt-extraction.ts      Zod-схема извлечения + текст подсказки + версия подсказки (LLM-04)
├─ infrastructure/
│  ├─ db/schema.ts               receipts, receipt_items (userOwnedTable, ownedFk)
│  ├─ db/receipts.repo.ts        SQL — только здесь; первый аргумент s: ScopedDb
│  ├─ qr/zxing-qr-decoder.ts     адаптеры внешних сервисов модуля
│  └─ image/sharp-preparer.ts · image/heic-decoder.ts
├─ api/router.ts                 contract.receipts.* → сценарии (тонко)
├─ jobs/recognize.job.ts         receipts.recognize; jobs/stuck.sweep.ts — «для всех» (§6.6)
├─ subscriptions/on-transactions-merged.ts
├─ agent/tools.ts                get_receipt, receipt_status (defineTool)
└─ __fixtures__/ __cassettes__/  данные тестов рядом с кодом
```

Большой модуль (`legal-base`) делит `application/` на подпапки по подобластям (`catalog/`, `sync/`, `index/`,
`search/`, `public/`), но **фасад и `index.ts` остаются одни**. Сигнал к разделению через ADR: сценарий
длиннее 300 строк или больше 25 файлов в `application/`.

### 4.2 Слои и что в них можно

| Слой | Можно | Нельзя |
|---|---|---|
| `domain/` | чистые типы и функции модуля, `@kosht/kernel`, `@kosht/calc` | БД, сеть, время, платформа, другие слои модуля |
| `application/` | сценарии: фасады соседей, платформа, порты, `domain`, `calc`, репозитории своего модуля | SQL, библиотеки внешних сервисов напрямую |
| `infrastructure/` | Drizzle, SQL, адаптеры (sharp, cheerio, grammY…), реализации портов | импорт `application/` и `api/` (кроме `ports.ts`) |
| `api/`, `jobs/`, `agent/`, `subscriptions/` | вызвать сценарий | репозитории и SQL (`api-thin`) |

### 4.3 Сигнатуры (одна форма на весь проект)

```ts
// application/recognize-receipt.ts — сценарий: фабрика make<Сценарий>(deps) → функция (s, input)
export function makeRecognizeReceipt(d: RecognizeDeps) {
  return async function recognizeReceipt(s: ScopedDb, receiptId: ReceiptId): Promise<void> {
    const draft = await receiptsRepo.get(s, receiptId);                        // без транзакции
    const image = await d.images.prepare(await d.files.read(s, draft.photoFileId));
    const uid = await d.qr.decode(image);                                       // RCPT-04: локально
    let extracted = await d.llm.extract(s.scope, { task: "receipt.extract", ...receiptExtraction, images: [image] });
    let check = validateReceipt(extracted, d.settings.tolerance);               // @kosht/calc → { value, trace }
    for (let i = 1; !check.value.ok && i <= d.settings.maxRechecks; i++) {      // RCPT-06: модель — вне транзакции
      d.platform.realtime.progress(s.scope, { receiptId, stage: "rechecking", line: check.value.firstBadLine });
      extracted = await d.llm.extract(s.scope, { task: "receipt.extract", ...recheckPrompt(extracted, check.value) });
      check = validateReceipt(extracted, d.settings.tolerance);
    }
    await s.transaction(async (tx) => {                                         // короткая транзакция: атомарная запись
      const saved = await receiptsRepo.saveRecognized(tx, receiptId, extracted, check, uid);
      const txn = await d.transactions.recordFromReceipt(tx, toPurchase(saved)); // фасад соседа получает tx
      await d.platform.events.publish(tx, "receipts.recognized", { receiptId, transactionId: txn.id });
    });
  };
}
```

- **Первый аргумент** сценария, фасада и репозитория, трогающего данные пользователя, — `s: ScopedDb`
  (внутри транзакции — `tx`, тоже `ScopedDb`). В `llm`, конверт задачи и `realtime` уходит `s.scope`.
- **Транзакция — явно** `s.transaction(tx => …)`, только когда нужна атомарность. Внутри — только БД,
  `events.publish(tx, …)` и фасады соседей с `tx`. Модель, HTTP, чтение файлов — между транзакциями
  (`LlmGateway` бросает `LLM_IN_TRANSACTION`, если его позвать внутри: флаг транзакции хранится в
  `AsyncLocalStorage` — только булево, данных там нет).
- **Фасад** — узкий набор функций под нужды соседей, агрегаты — пачками (`aggregate(s, { period, groupBy })`,
  а не «по категории в цикле»).
- **Роутер** — проверил вход контрактом → вызвал сценарий (пример — `.claude/rules/backend-module.md`).
- **Модуль собирается** `defineModule({ id, facade, router, jobs, sweeps, subscriptions, tools, userData, undo,
  confirm, settings })`; всё, кроме `id`, необязательно. Части описываются помощниками платформы: `defineJob`,
  `defineSweep`, `defineSubscription`, `defineTool`, `defineUserData`, `defineSetting`, события — в `events.ts`.
  Корень композиции раскладывает это по реестрам.
- **Порты** — только на внешних границах (часы, файлы, модели, pravo.by, НБРБ, Telegram, почта, QR, фото).
  Интерфейсов «на каждый репозиторий» нет: сценарии тестируются на настоящем Postgres.

## 5. Связи модулей

Ярусы и зависимости — `docs/CAPABILITIES.md`; источник правды после бетона — `tooling/architecture/modules.ts`,
проверка — `make deps-check` (dependency-cruiser, правила генерируются из карты).

| Ситуация | Механизм | Пример |
|---|---|---|
| нужен результат сейчас, зависимость вниз, общая транзакция | **фасад** | `receipts` → `transactions.recordFromReceipt(tx, …)` |
| остаток счёта по операциям (STMT-02) | **фасад** вниз | `transactions` → `accounts` (применить изменение остатка); `accounts` от `transactions` не зависит |
| нижний модуль сообщает наверх | **событие** (нижний не знает слушателей) | `transactions.changed` → `budgets` проверяет пороги 80/100 % |
| побочный эффект, который может прийти через секунды | событие | пересчёт регулярных после импорта |
| «приёмник», которого зовут все | фасад нижнего яруса | `notifications.notify()`, `explain.save()`, `actions.record()`, `profile.upsertDerivedFact()` |
| верхний модуль подставляет реализацию вниз | **реестр** в корне композиции | канал `telegram` для `notifications`; словарь имён `profile` для маскирования в `llm`; обработчики «Отменить»/«Да» для `actions`; владельцы данных для `privacy`; инструменты всех модулей для `agent` |

**События.**
- `events.publish(tx, name, payload)` ставит задачу pg-boss **в той же транзакции** (`fromDrizzle`): нет записи —
  нет события, нет события — нет записи. Схема нагрузки — в `events.ts` публикующего модуля.
- Подписка = своя очередь `evt.<событие>.<модуль-слушатель>`; доставка «хотя бы раз», поэтому обработчики
  **идемпотентны**; в конверте — `scope` и `requestId` (цепочка логов не рвётся, OBS-01). Scope из конверта
  перепроверяется: пользователь существует, домохозяйство то же; иначе задача отбрасывается.
- Нагрузка — только id и **пачки** (`{ ids: [...] }`, ≤ 1000): импорт 300 операций = одно событие. Пересчёты —
  с `singletonKey` через `jobKey(scope, …)` и небольшой задержкой (схлопывание «шторма»). Уведомления порогов
  идемпотентны по ключу «лимит + месяц + порог» (BUD-03).
- Порядок доставки не гарантирован: обработчик перечитывает актуальное состояние, а не доверяет нагрузке.

**Живые сигналы в браузер.** `platform.realtime.progress(scope, …)` / `realtime.changed(scope, { entity, ids })` →
`NOTIFY kosht_realtime` (в сообщении `householdId`, вид и id — без данных) → `api` → `events.stream` (SSE) отдаёт
клиенту только события его домохозяйства → `invalidateQueries`. Так таблицы обновляются и после действий агента
и бота.

**Ожидающие решения — в `actions`** (решение пользователя 2026-10-24). Всё, что ждёт «Да/Нет» человека, — строка
«ожидающего решения» в `actions`: подтверждение удаления и массового действия (AGT-07, TXN-03/04) и вопрос
«Нашёл чек и платёж по карте — это одна покупка?» (TXN-10). Модуль-владелец (`transactions` для сопоставления)
создаёт его фасадом `actions` и регистрирует через реестр обработчики ответов; уведомление (NOTIF-05) ссылается на
id решения, а не хранит свой вариант вопроса. «Да/Нет» на сайте (карточка, уведомление), кнопка в боте и короткий
ответ в чате (распознаётся кодом до запуска агента) ведут в одну функцию `actions` с этим id — поведение одинаково
во всех каналах, повторный ответ ничего не меняет.

**Реестры** (запись вместо правки ядра): модели (БД, `llm`), провайдеры (код: id → фабрика адаптера), инструменты
и наборы инструментов агента, каналы уведомлений, обработчики отмены и подтверждения, владельцы данных,
настройки, задачи и расписания, части сообщений чата (на сайте). Новая модель — строка в админке; дипломный
инструмент — новый `defineTool`.

## 6. Изоляция данных (ROLE-01, SEC-04, PRIV-07) — «пять замков» без RLS

RLS в Postgres не используется (решение пользователя, ADR-0006). Защищаемся от **забывчивости и подстановки
чужих id** (в том числе моделью через prompt injection), а не от злонамеренного разработчика с доступом к БД.

### 6.1 Три вида таблиц

| Вид | Что | Обязательно |
|---|---|---|
| `userOwnedTable` | финансы, профиль, чат, файлы, уведомления, согласия — всё, что принадлежит домохозяйству | `household_id NOT NULL`, `user_id`, `created_at`, `updated_at`; PK `(household_id, id)`; ссылки на другие пользовательские таблицы — `ownedFk` (составной FK + индекс); строки входят в `defineUserData` |
| `systemTable` | пользователи Better Auth, сессии, домохозяйства, настройки, журнал расхода ИИ, привязки Telegram, журналы загрузчика | доступ через `SystemDb` у модулей с флагом `systemTables` |
| `publicTable` | акты и фрагменты, курсы, справочник контрагентов, встроенные категории и глобальные правила | без `household_id`; читать можно и через `s.db`, писать — только владелец через `SystemDb` |

«Смешанные» таблицы (общие строки с `household_id IS NULL` рядом со своими) запрещены. Встроенные категории
общие (`system_categories`, `publicTable`), свои — у домохозяйства (`categories`, `userOwnedTable`); операция
ссылается на одну из них (две колонки + `CHECK` «ровно одна»), скрытие встроенной категории — строка
настроек домохозяйства (решение пользователя, `10-consensus.md`).

### 6.2 Пять замков

| № | Замок | Что ловит | Когда |
|---|---|---|---|
| 1 | **Типы**: `Scope` с брендом (литералом не собрать), `s: ScopedDb` первым аргументом, `s.insert` не принимает `householdId`/`userId` | забыл scope, подделал scope, передал чужое домохозяйство | компиляция |
| 2 | **Схема**: PK `(household_id, id)`, составные FK, `NOT NULL`, нет уникальности по одному `id` | ссылку на чужую строку (модель подставила чужой `categoryId`), UPSERT по `id` | запись в БД |
| 3 | **Аудитор SQL** в `Logger` Drizzle: до отправки проверяет, что **каждое** обращение к пользовательской таблице ограничено `household_id = $n`, где `$n` — домохозяйство scope; иначе `ISOLATION_VIOLATION`, запрос не уходит | забытый `where`, затёртый `where`, JOIN, подзапрос, CTE, агрегат, сырой `sql`, UPDATE/DELETE по id, INSERT с чужим `household_id`, системный доступ к пользовательским таблицам | каждый запрос, всегда, и в продакшене («отказ», не «лог и продолжить») |
| 4 | **Статика**: dependency-cruiser (`schema-only-in-infrastructure`, `no-cross-module-repo`, `no-unsafe-db`, `cross-tenant-only-in-sweeps`, `system-db-only-for-flagged-modules`, `admin-no-user-data`) + `tooling/checks/isolation.mjs` + проверка схемы в CI | импорт чужой схемы, `drizzle-orm`/`pg` вне `platform/db` и `infrastructure/db`; `makeScope`/`as Scope` вне входов; `sql.raw`/`.execute` вне `infrastructure/db`; `$client`/`unsafeRaw`; `userId`/`householdId` во входной схеме процедуры или инструмента; `VIEW`/функции/триггеры в `public`; таблица с `household_id` вне реестров | `make check` |
| 5 | **Тесты**: генерируются по реестрам процедур и инструментов («A вызывает с id из B»), канарейки данных и механизма, покрытие `*.repo.ts` | утечка или порча любой процедуры; поломка самого механизма после обновления Drizzle | `make test` |

Пределы аудитора честно: запрос он читает парсером PostgreSQL 18 (ADR-0019) и проверяет булеву логику
дерева (`… OR true`, `NOT`, предикат в `select`/`CASE`/`filter`, `ON` внешнего соединения не засчитываются), но
представления и SQL-функции базы и побочные каналы (ошибка выражения на чужой строке раньше фильтра) не видит —
их закрывают проверка схемы, построитель `ScopedDb` и ревью; текст, который парсер не принял, — отказ. Цена —
16–25 мкс на разбор нового текста и ~0,05 мкс на повтор из кэша (замер T-058; RLS стоил бы +70 мкс и 4
обращения к базе).

### 6.3 `ScopedDb` и запросы

```ts
interface ScopedDb {
  readonly scope: Scope;                                     // для llm, событий, realtime, jobKey
  readonly db: Omit<NodePgDatabase, "$client">;             // обычный Drizzle; каждый запрос проходит аудитор
  own(t: OwnedTable): SQL;                                   // «строка моего домохозяйства» — на КАЖДУЮ таблицу запроса
  insert(t): { values(v | v[]) };                            // household_id/user_id проставляются сами
  update(t, where: SQL): { set(patch) };                     // фильтр домохозяйства добавляется сам
  delete(t, where: SQL);
  transaction<R>(fn: (tx: ScopedDb) => Promise<R>): Promise<R>;   // вложенная = SAVEPOINT
}

// infrastructure/db/receipts.repo.ts
async withItems(s: ScopedDb, id: ReceiptId) {                // JOIN: у каждой таблицы свой s.own()
  return s.db.select({ receipt: receipts, item: receiptItems }).from(receipts)
    .leftJoin(receiptItems, and(s.own(receiptItems), eq(receiptItems.receiptId, receipts.id)))
    .where(and(s.own(receipts), eq(receipts.id, id)));
}
```

Чужой id неотличим от несуществующего: ответ `NOT_FOUND`. Связанная строка читается со своим `own`, а не
считается видимой «по родителю». Сортировки и поля из ввода — только `enum`. Сообщение аудитора говорит, что
добавить («обращение к receipts без фильтра — добавьте `s.own(receipts)`»).

### 6.4 Где рождается `Scope` (единственные места)

| Вход | Как |
|---|---|
| Сайт (oRPC) | middleware: сессия Better Auth → `userId` и `householdId` из сессии (без отдельного запроса на каждый вызов — решение пользователя) → `makeScope` → `platform.scoped(scope)` → `context.s` |
| Telegram | `chat_id` → `telegram_links` (системная таблица) → пользователь; только личные чаты; для непривязанного чата scope не создаётся |
| Задача / подписка | scope из конверта задачи + перепроверка «пользователь существует, домохозяйство то же» |
| Инструмент агента | адаптер `defineTool → AI SDK` строит `ctx.s` из scope запуска агента; во входной схеме инструмента нет `userId`/`householdId` |
| Тесты, сидирование | `makeScope` разрешён в `*.test.ts` и `packages/testing` |

### 6.5 Системный доступ и админка

Платформа раздаёт возможности типами: `scoped(scope): ScopedDb` — модулям с пользовательскими данными;
`system: SystemDb` — только модулям с признаком `systemTables` (выводится из `tables` в `modules.ts`: есть
`system` или `public`; аудитор запрещает ему любое упоминание пользовательской таблицы); `crossTenant` —
только `defineSweep` в `platform/jobs`; `unsafeRaw` — только миграции и тесты. Модуль `admin` своих данных
не имеет и пользовательские схемы импортировать не может; счётчиков «сколько у пользователя операций»
в админке нет (решение пользователя).

### 6.6 «Для всех пользователей», экспорт, удаление, файлы, кэши

- **`defineSweep`** (`*.sweep.ts`): сквозной запрос возвращает **только** `(id, householdId, userId)`, дальше —
  задача на каждую строку под scope владельца. Так работают тик напоминаний, итоги недели, зависшие чеки.
- **`defineUserData`** в каждом модуле с пользовательскими таблицами: что экспортировать (PRIV-05, потоковый ZIP
  задачей) и удалять (PRIV-06, дети раньше родителей). Тест полноты: каждая `userOwnedTable` в реестре; после
  удаления в таблицах 0 строк пользователя, данные другого домохозяйства не изменены. Затем удаляются каталог
  файлов и трассы Langfuse пользователя, последней — запись `identity`.
- **Файлы**: путь `data/files/<householdId>/<fileId>` строит сервер; запрос передаёт только `fileId`, который
  сначала ищется в БД через `s`. Имена и пути из запроса не используются.
- **Кэши** пользовательских данных — только `scopedCache(s)` (ключ всегда с `householdId`); опция `cache` Drizzle
  выключена. Реестры в памяти (запущенные агенты, ожидающие действия) ключуются `householdId:id`.
- **Сайт**: при выходе и смене пользователя `queryClient.clear()`; данные пользователя не кладутся в `localStorage`.

### 6.7 Семейный режим [Д] (DIP-03)

Жёсткая граница — домохозяйство; внутри — мягкая ось «автор + `visibility` (`personal | shared`)». Колонки
`user_id` и `visibility` есть с MVP, условие видимости пока — только `household_id`. Переход = новая реализация
`s.own()` (для таблиц с видимостью: `user_id = $uid OR visibility = 'shared'`) + вторая проверка аудитора +
второй прогон тестов изоляции. Места вызова не меняются. Судьба общих операций при удалении участника —
решается в дипломе (§16).

## 7. Расчёты и «Откуда эта цифра?» (P1, P2)

Почему так — ADR-0017; правила кода (`Calc<T>`, трасса, деньги, округление, тесты-примеры) — `.claude/rules/calc.md`.

- Все финансовые, налоговые и проверочные числа — чистые функции `packages/calc` с результатом `{ value, trace }`;
  «сегодня» (`Clock`), ставки (`norm-tables`), пороги (настройки) — входом. Из трассы сайт рисует
  «2 400 − 180 − 35 − 1 200 − 145 = 840 BYN» и ссылки на основания (EXPL-01).
- Сохраняется **тот самый** расчёт (EXPL-02): модуль вызывает `explain.save(s, calc)` и отдаёт рядом с числом `traceId`;
  панель «Откуда эта цифра?» грузит `explain.get(traceId)`. Эквивалент в BYN — по курсу НБРБ на дату операции, курс
  входит в трассу (STMT-09).
- Время — `LocalDate` (по Минску) для дней, ISO UTC для моментов (NFR-23); id — `uuidv7()`, в TypeScript — бренды
  (`ReceiptId`). Сайт денег не считает: даже ползунок «Крупной покупки» пересчитывается на сервере (~50–100 мс).

## 8. ИИ-слой

### 8.1 Шлюз `llm` — единственный, кто знает провайдеров

```
modules/llm/
├─ facade.ts              LlmGateway: model(scope, task, opts) · extract() · classify() · embed() · transcribe()
├─ domain/                задачи (chat | receipt.extract | statement.columns | classify.* | law.topic | …),
│                         возможности моделей, правило выбора цепочки — чистые функции
├─ application/           build-chain.ts · chained-model.ts · limiter.ts · masking/ · ledger.ts · local-models/
└─ infrastructure/        providers/ (groq, openai-compatible: Z.ai, llama-server), embedder, transcribers, ner, db/
```

- **Реестр моделей** (LLM-09, R45): модель — строка в БД (провайдер, id модели, облачная/локальная, возможности:
  инструменты, изображения, ответ по схеме, речь, эмбеддинги; контекст; лимиты тарифа; цены). Новый провайдер —
  один адаптер `ProviderAdapter`; новая модель — запись в админке. Тестовый провайдер с детерминированными ответами —
  такой же настоящий адаптер в реестре, а не «заглушка» в смысле запрета `CONSTRAINTS.md`.
- **Цепочка по задаче** (LLM-02): из записей с нужными возможностями; для пользователя без облачного согласия —
  только локальные (контекст `cloudAllowed` на каждом вызове, тест-инвариант). Выбранная пользователем модель
  (LLM-10) идёт первой, если разрешена; при недоступности ответ даёт следующая, сайт показывает «Модель X
  недоступна, ответила Y». Задачи без данных пользователя (PRIV-09) вызываются с `systemCaller("<модуль>")`
  вместо scope — облачная цепочка.
- **«Цепочка как одна модель»** (`LanguageModelV4`): переключение на следующего провайдера при ошибке, таймауте,
  429 — до первого куска потока; лимитёр по окнам RPM/TPM/RPD и заголовкам `x-ratelimit-*`, размыкатель по
  `retry-after` (LLM-03, LLM-05); кэш одинаковых классификаций.
- **Маскирование** (PRIV-03) перед любой отправкой в облако: правила + склонённый словарь имён (порт `KnownNames`,
  реализацию подставляет `profile` через реестр) + локальная NER (~178 МБ, скачивается сама). Демаскирование —
  внутри обёртки: текст, поток и **аргументы инструментов**. Фото чека уходит как есть (PRIV-04), с удалёнными
  EXIF/GPS.
- **Документы — данные** (SEC-10, SEC-11): текст чека, выписки, закона передаётся блоком `<document>` отдельно от
  инструкций; извлечение — только в строгую схему с проверкой и повтором (LLM-04); фильтр инструктивных фраз.
- **Журнал расхода** (LLM-06): строка на каждый вызов — задача, провайдер, модель, токены, длительность, условная
  стоимость, ошибка; без текстов; 90 дней. Это основа лимитов в реальном времени и цифр админки (ADM-20);
  работает и без Langfuse.
- **Langfuse** (OBS-03/05, R46): трассы с текстами, шагами агента и инструментами — через `@langfuse/vercel-ai-sdk`
  + `@langfuse/otel` (версии OTel закреплены, ADR-0010); `userId` — внутренний id, `sessionId` — id диалога;
  хранение 30 дней (своя ночная задача), удаление трасс пользователя при PRIV-06.
- **Локальные модели** (NFR-25, ADM-50): свой загрузчик (Range + sha256 + прогресс) в `data/models/`, llama-server
  в режиме роутера, самотест «2+2» + эталонный вектор при старте с откатом на CPU. Подробно — ADR-0011.

### 8.2 Агент

- Цикл — AI SDK 7 `ToolLoopAgent`: не больше 8 шагов (`isStepCount`, настройка AGT-01), на последнем шаге
  `toolChoice: "none"` — иначе при пределе текст пуст. Агент зависит только от `llm`, `actions`, `profile`,
  `legal-consult`; ни одного финансового модуля — инструменты приходят реестром.
- **Инструмент** описывает модуль-владелец в `agent/tools.ts` своим `defineTool` (`platform/tools`, без AI SDK):

```ts
type ToolKind = "read" | "write" | "destructive";
interface ToolCtx { s: ScopedDb; requestId: string; channel: "web" | "telegram"; page?: PageContext }
type ToolDef<I, O> =
  | { kind: "read" | "write"; name: string; toolset: Toolset; description: string;
      input: ZodType<I>; output: ZodType<O>; execute(ctx: ToolCtx, input: I): Promise<O> } // write → в выходе undoToken
  | { kind: "destructive"; name: string; toolset: Toolset; description: string;
      input: ZodType<I>; propose(ctx: ToolCtx, input: I): Promise<PendingActionDraft> };  // удалить нельзя по типу
```

- **`write`** (одиночное действие, AGT-05) выполняется сразу, регистрирует отмену в `actions` и возвращает
  `undoToken` — карточка с «Отменить»/«Изменить». **`destructive`** (удаление, массовое, AGT-07) только создаёт
  «ожидающее действие» в `actions`; «Да» на сайте и кнопка в Telegram вызывают одну функцию
  `actions.confirm(s, pendingId)`, которая исполняет действие кодом. Короткое «да» текстом сервер распознаёт
  детерминированно до запуска агента.
- **Дозапрос** (AGT-06) — инструмент `ask_user` без `execute`: цикл останавливается, ответ сохраняется фактом
  (PROF-04).
- **Наборы инструментов** — 3–4 фиксированных (`core`: операции, профиль, калькулятор, дозапрос, объяснение,
  контекст страницы, график; `legal`: + право и налоги; `planning`: + счета, лимиты, цели, календарь, регулярные,
  покупка; `reports`: + Excel). Набор выбирается правилами по странице и словам, без вызова облачной модели.
  Префикс (системная подсказка + набор) байт-в-байт постоянен ради кэша провайдера; дата, контекст страницы,
  факты — в конце, в сообщении пользователя. Описания инструментов — короткие, по-английски; результаты —
  компактные (агрегаты, а не сотни строк).
- **Стражи** (`agent/application/guards/`): «вне темы» и защитный классификатор до дорогого цикла (правила →
  локальные эмбеддинги → малая модель, AGT-12, SEC-10); **проверка чисел ответа** — каждое число в тексте должно
  быть в результатах инструментов (P1, AGT-04); постобработка цитат через `legal-consult`.
- **Цитаты** (LEGAL-03): модель ставит метки `[[F12.2]]` (id версии фрагмента и предложения), программа подставляет
  дословный текст; вольная цитата проверяется на дословность (нормализация пробелов и кавычек), непрошедшая —
  заменяется ссылкой с пометкой.
- **Подсказки** — в `agent/prompts/` и рядом со сценариями извлечения, с `PROMPT_VERSION` (ключ кассет и кэша eval).

### 8.3 Поток чата

`chat.send` — обычная процедура oRPC: сервер превращает UI-поток AI SDK в итератор событий, сайт — обратно в поток
для `useChat` (интеграция oRPC с AI SDK; точные имена функций сверяются с oRPC 1.16 в бетонной фазе). Те же вход,
сессия, ошибки и `requestId`, что у остальных процедур. Запуск агента **не привязан к соединению**: ответ
дописывается при закрытой вкладке и сохраняется (`UIMessage.parts`), при повторном открытии виден целиком;
«Стоп» — отдельная процедура `chat.stop(runId)` с проверкой владельца. Запасной путь, если интеграция подведёт, —
отдельный маршрут Hono `/api/chat` с той же проверкой сессии (решение — новым ADR). Telegram получает тот же
поток через фасад `chat` и показывает его `sendMessageDraft` (запасной — `editMessageText` ≤ 1/с).

## 9. API, ошибки, конфигурация, логи, безопасность

- **Процедуры по доступу**: `publicProc` (гость: вход, «База законов»), `authed` (сессия → `context.s`), `localOnly`
  (только локальный слушатель: первый запуск, почтовый ящик, демо-вход), `admin` (роль администратора).
- **Контракт-первым**: `packages/contract` описывает процедуры (`oc.route(...).input(...).output(...).errors(...)`),
  сервер реализует (`implement(contract)`), сайт получает типизированный клиент и `queryOptions` для TanStack Query.
  DTO ≠ строка БД (явный `toDto()`); поля только добавляются, удаление — через `deprecated`. Тот же роутер отдаёт
  REST/OpenAPI для `curl` и тестов.
- **Ошибки**: каталог `packages/contract/src/errors.ts` (код → HTTP-статус, повторяемость);
  `throw new AppError("RECEIPT_DUPLICATE", { receiptId, uploadedOn })` — параметры, а не текст. Перевод в ответ —
  в одном месте каждого входа: oRPC (`{ defined, code, status, message, data: { requestId, params } }` — форма
  `ORPCError` oRPC 1.16, `message` = код: клиент oRPC без него ошибку не узнаёт), обёртка инструмента
  (`{ ok: false, code }` — агент сообщает и предлагает повторить, AGT-13), обёртка задачи (повтор, если
  `retryable`). Всё прочее — `INTERNAL` без текста исключения наружу, стек — в лог. Текст для человека — на сайте
  и в боте: `t("errors:RECEIPT_DUPLICATE", params)`.
- **Конфигурация в два слоя**: `platform/config` — окружение через Zod-схему, падение при старте с понятным
  сообщением (адрес БД, порты; `process.env` читают только `config` и точки входа); `platform/settings` — реестр `defineSetting` в БД с приоритетом «админка > env >
  умолчание» (SMTP, ключи, часовой пояс, пороги алгоритмов, ночное окно). Секреты (NFR-16) — поля только для
  записи, AES-256-GCM, мастер-ключ в файле `secrets/master.key` (0600, вне резервной копии), в логи не попадают.
  Таблицы `settings`, `secrets`, `rate_limits` — `systemTable` самой платформы: их `schema.ts` и `*.repo.ts` — единственное
  место `drizzle-orm` вне `platform/db` и `infrastructure/db` модулей (решение по T-005).
- **Логи** (OBS-01/02/04/06): pino + `AsyncLocalStorage` (`requestId`, `uid`, `source` подмешиваются сами);
  сообщение — стабильный английский ключ события (`^[a-z]+(\.[a-z0-9-]+)+$`, проверяется типом и при записи), данные —
  полями из белого списка (чужие отбрасываются): `log.info({ receiptId, ms }, "receipt.recognized")`. Ошибки — без
  текста значений: у ошибок pg — код, ограничение, таблица и стек, у прочих — `scrub(message)` и стек. Ротация —
  ежедневно, 14 файлов (`pino-roll` в процессе); `make logs`, `make log-find id=…`.
- **Наблюдаемость задач** (OBS-07): таблица `background_job_run` (вид, статус, прогресс, «водяной знак»
  последнего обработанного периода, ошибка) — экран «Система» в админке; расписания с догоном пропущенного
  (`missed: "once"` + водяной знак, NFR-22).
- **Безопасность** (SEC-01…05, NFR-24, R40): почему так — ADR-0016, правила (два слушателя `local`/`lan` и
  `localOnly`, `Host`/`Origin`, cookie, CSP, лимиты частоты, пароли, файлы, Markdown ответов) —
  `.claude/rules/security-privacy.md`.

### 10.2 Данные, адрес, формы

Правила — `.claude/rules/frontend-feature.md` (запросы только через `lib/api`, состояние страницы в адресе, формы на
схемах контракта, числа готовыми с `traceId`). Пример «адрес — состояние страницы»: клик по «Такси» на дашборде →
`/operations?period=2026-09&category=taxi` (DASH-03); контекст для агента (CHAT-08) собирает `usePageContext` из
маршрута, параметров и выбранного объекта по схеме `PageContext` из контракта.

**Список операций** (TXN-02, решение пользователя 2026-10-24): на компьютере — таблица со страницами по 50 строк
(серверная пагинация: номер страницы, размер, `total`); на телефоне — тот же запрос, список с «Показать ещё»
(следующая страница дописывается снизу). Курсор — только для лент вроде уведомлений (`.claude/rules/api-contract.md`).

### 10.3 Чат (`features/assistant`)

`useKoshtChat` — обёртка `useChat` (AI SDK) с транспортом oRPC; реестр частей сообщения
`{ "tool-<имя>" | "data-<вид>" → компонент }` с безопасным запасным видом; карточки переиспользуют `entities/*`.
Потоковый Markdown — `react-markdown` + `remend` + блоки в `memo`; метки `[[F12.2]]` → `LawRefChip` → `LawQuote`
(Popover на компьютере, нижняя шторка на телефоне); подписи шагов («Ищу траты за сентябрь…») — из словаря по имени
инструмента, не из модели. Лента `role="log"` с `aria-live="off"` + отдельная скрытая живая область только для вех.
Без веток диалога и покадрового «проявления слов». Панель чата — `Drawer` в каркасе, на телефоне — полноэкранный
маршрут. Микрофон — только на `localhost` (VOICE-02), иначе подсказка «Надиктуйте в Telegram».

### 10.4 Вид, тексты, доступность

Внешний вид — по макету `design/` (DES-00), поведение — по SPEC. Правила: дизайн-система, токены (в том числе
`--warn-bar` для полосы лимита 80–99 %), шрифты, доступность компонентов — `.claude/rules/frontend-ui.md`; состояния
экрана (DES-16), подтверждения и телефон — `.claude/rules/frontend-feature.md`; тексты и форматы —
`.claude/rules/i18n.md`; планка axe — `CONSTRAINTS.md`.

### 10.5 Экраны собираются задачами модулей

Решение пользователя 2026-10-24: **задача плана = модуль сервера вместе со своей частью экранов.** Элементы экрана,
зависящие от ещё не готового модуля, скрыты; задача этого модуля сама встраивает свой кусок в уже существующий экран.
Пример: «Операции» появляются в задаче `transactions`, а карточку чека и признак «есть чек» в них добавляет задача
`receipts`; кнопку «Excel» — задача `xls-export`. Общие сущности фронта (`entities/<x>`, например
`entities/receipt`) и контракт процедур (`packages/contract/src/<модуль>/`) делает задача модуля-владельца;
следующие задачи их только используют. Так же устроены admin-экраны (`docs/CAPABILITIES.md`, «сквозной»).

## 11. Потоки данных (ключевые сценарии)

### 11.1 Фото чека (RCPT, TXN-10)

1. Сайт: `receipts.upload` (до 10 файлов) → `api`: `files` проверяет тип по содержимому и сохраняет;
   `receipts` пишет чек «распознаётся» и ставит задачу `receipts.recognize` (priority 10, `singletonKey` через
   `jobKey(scope, receiptId)`) в той же транзакции → ответ сразу (P5, NFR-21).
2. `worker`: HEIC → JPEG (`heic-decode`), подготовка `sharp`, QR → УИ локально; дубль по УИ (или магазин + дата +
   время + итог) → `RECEIPT_DUPLICATE`.
3. `llm.extract` (облако при согласии, иначе локальная VLM ~50 с) → `calc.validateReceipt` → при расхождении
   перепроверка спорных строк (≤ 2), прогресс через `realtime.progress` → SSE → анимация проверки на сайте.
4. Короткая транзакция: сохранить позиции и статус, категории позиций (`categories`), `transactions.recordFromReceipt`
   (сопоставление с операцией из выписки или предварительная операция, TXN-10/RCPT-10; неуверенное совпадение —
   ожидающее решение «одна покупка?» в `actions`, §5), `explain.save`, событие
   `receipts.recognized` (+ `receipts.warranty-items-found` → `calendar`).
5. Карточка «Верно / Изменить / Отменить» на сайте или в боте; «Отменить» — обработчик `receipts.cancel` в `actions`.

### 11.2 Импорт выписки (STMT, R44)

1. Загрузка → `files` → задача `statements.parse` в `worker`: чтение (PDF — `unpdf` + своя сборка строк и колонок по
   координатам; XLSX/XLS — SheetJS CE; CSV — `papaparse` + определение кодировки; скан — модель с изображениями).
2. Колонки: запомненный формат (STMT-05, без модели) → эвристика → `llm` по маленькому замаскированному фрагменту
   (только смысл колонок; строки разбирает код). Сверка цепочки остатков (`calc`), расхождение → «проверьте».
3. Очистка названий (`merchants`), дубли между файлами (STMT-07), типы (переводы, доходы, возвраты), категории
   пакетами (CAT-06) → **предпросмотр** (сохранён черновиком импорта), сайт/бот показывает «Нашёл 47, 12 уже были».
4. «Импортировать 35» → транзакция: операции (`transactions`), отпечаток формата, итоги импорта, `actions.record`
   (откат импорта, STMT-11), событие `statements.imported`; `transactions.changed { ids }` одной пачкой →
   `budgets`, `recurring`, `tax`, `calendar` пересчитывают со схлопыванием; уведомление «импорт завершён».

### 11.3 Вопрос ассистенту о законе (LEGAL, LAW-21)

1. `chat.send` → стражи (вне темы, защитный классификатор) → выбор набора `legal` → агент.
2. Инструменты `search_law` (точное обращение по реквизитам → гибрид FTS `russian` + векторы `halfvec` со слиянием
   RRF k = 60 → только действующие версии → расширение по ссылкам и определениям; 6–10 фрагментов),
   `get_law_fragment`, `law_act_card`; данные пользователя — своими инструментами (`get_receipt` и т. п.), числа —
   калькулятором.
3. Ответ с метками `[[F…]]` → `legal-consult` подставляет дословные цитаты, дату редакции и ссылку на pravo.by,
   предупреждения о принятых изменениях (LAW-32), «в моей базе нет» (LEGAL-04), пометку «Не является юридической
   консультацией»; проверка чисел (P1). Ответ ссылается на версии фрагментов — позже `chat` пометит «статья
   изменилась после ответа» (CHAT-10). Тема без ответа пишется в журнал спроса без текста вопроса (LAW-15).

### 11.4 Ночное обновление законов (LAW-30…39)

1. Расписание `legal-base.daily-check` внутри ночного окна (по умолчанию 04:00, окно 02:00–06:00); пропущенное
   догоняется при включении (NFR-22). Один поток, 3–5 с между запросами, честный User-Agent с контактом, robots.txt
   на каждый адрес, лесенка повторов, остановка цикла при 403/429 или > 20 % ошибок.
2. Карточки актов (изменяющие акты, утрата силы, появился ли текст), лёгкая проверка текста (`HEAD` без сжатия) →
   загрузка новой редакции → сырой HTML снимка (gzip) → разбор `cheerio` → сопоставление фрагментов по путям и
   тексту: неизменённые продлеваются, изменённые — новая версия, пропавшие — «исключён» (LAW-31).
3. Карантин (LAW-39): пропало > 5 % фрагментов, нет статей или шапки, сломана кодировка → редакция не применяется,
   уведомление админу. Канарейки — известные акты с известным числом статей.
4. Новая версия сразу доступна в точном и полнотекстовом поиске; задача `legal-base.embed` векторизует только
   изменённые фрагменты; событие `legal-base.act-updated` → `norm-tables` сверяет числа ставок и уведомляет админа
   (ставка сама не меняется, LAW-33). «Новые поступления» за пропущенные дни → фильтры LAW-13 → таблица маршрутов
   LAW-17.

| Компонентный | `ui`, карточки чата, формы, состояния DES-16 | рядом: `*.test.tsx` | Vitest + Testing Library + MSW |
| E2E | 5–8 сценариев (первый запуск, чек, импорт, чат, вычет, экспорт) + axe на всех маршрутах 1440/390 | `e2e/specs/*.spec.ts` | Playwright + `@axe-core/playwright`, сервер в режиме кассет |

| Eval (не в `make test`) | QA-11…15 на реальных моделях с бюджетом токенов и возобновлением, результаты в БД (QA-16) | `modules/quality`, `datasets/` | `make eval` |

- **Кассеты** — на границе шлюза `llm` (обёртка `LanguageModelV4`), а не HTTP: не ломаются при смене провайдера.
  Ключ — «сценарий + номер шага», мягкая проверка отпечатка (имена инструментов, последнее сообщение) с сообщением
  «запись устарела — выполните `make ai-record SCENARIO=…`». Лежат в `__cassettes__/` рядом с тестом. Режимы шлюза:
  `replay` (по умолчанию в тестах: промах — понятная ошибка, не поход в сеть) · `record` · `live`.
- Тесты не ходят в интернет и не тратят лимиты (NFR-11); время — `FakeClock`; файлы — `MemoryBlobStore`;
  очередь — `InlineJobs` или настоящий pg-boss в интеграционных.
- Сообщение теста — человеческое, по-русски: `it("чек 3 × 2,49 = 8,47 не сходится и называет строку 2")`.
- Тестовые данные без реальных ПД: синтетика из `tooling/synth/`, обезличенные копии (NFR-18).
- Postgres для тестов `make check` и `make test-int` поднимают сами (`make db-up`), если он не запущен; кассеты
  перезаписывает сам имплементатор (`make ai-record`), ключи читает программа — подробно `.claude/rules/testing.md`.

## 13. Бетонная фаза: что появляется до первой бизнес-функции

Цель — чтобы задача «Операции» сводилась к «написать сценарии, схему и экран», а всё вокруг уже было и
проверялось. Разработка идёт **строго последовательно, по одной задаче**; задачи плана — крупные цельные куски
тесно связанной работы, а не мелкие шаги: каждый шаг ниже — одна задача (крупный шаг может стать двумя, если
части проверяются независимо), у каждой — проверка «готово». Так же нарезаются и фазы 2–8 `docs/CAPABILITIES.md`:
задача = модуль целиком (схема, сценарии, роутер, инструменты, тесты) вместе со своей частью экранов (§10.5).

1. **Репозиторий и ворота (T-001).** pnpm-workspace, Node 26, `tooling/tsconfig.base.json` (TS 7, стираемый синтаксис),
   Oxlint (type-aware) + oxfmt (точная версия), lefthook + commitlint + проверка размера, Turborepo, Makefile —
   каждую цель добавляет задача, которая даёт её функцию (заглушек нет, см. `CONSTRAINTS.md`), `.gitignore`
   дополняется `secrets/`. *Готово:* `make check` зелёный на пустом проекте и красный на намеренной ошибке каждого вида.
2. **Архитектура как код (T-002, T-056).** T-002: `tooling/architecture/modules.ts` (36 модулей, ярусы, `dependsOn`,
   `tables`, из которых выводятся `userData` и `systemTables`) из `docs/CAPABILITIES.md`, генератор правил
   dependency-cruiser (+ `typescript@6` рядом), `deps-guard` (порог числа файлов), фикстуры нарушений с тестом
   «каждое правило ловит своё», `make capabilities`, области коммитов из карты. T-056: `isolation.mjs`,
   `no-raw-colors.mjs`, `calc-no-clock.mjs`, `jsx-literals.mjs` (литералы в JSX), `floor.mjs` («Пол» `CONSTRAINTS.md`)
   — цель `make static-checks` в `make check` и `check-quick`; `bundle-size.mjs` — для `check-full` (T-011).
3. **Общие пакеты (T-003, T-057).** T-003: `kernel` (Money, LocalDate, Period, интерфейс `Clock`, Scope с брендом,
   бренды id, TraceNode), `calc` (`Calc<T>`, помощники трассы, правила округления, `freeBalance` с тестами-примерами),
   `testing` (фабрики, `FakeClock`; остальное в `testing` добавляют задачи, которым оно нужно), покрытие `calc` и
   `kernel` в `make test`. T-057: `contract` (каталог ошибок, общие схемы, `health`, `PageContext`, части сообщений
   чата, `events.stream`), `i18n` (ru, типизированные ключи, форматы).
4. **База данных и платформа сервера (T-004…T-006).** T-004: сервис `db` в `compose.yaml`, db (пул, `ScopedDb`,
   аудитор, `userOwnedTable`/`systemTable`/`publicTable`/`ownedFk`, `SystemDb`, первая ручная миграция с `vector`
   и `pg_trgm`, миграции при старте, проверка `casing` drizzle-kit), канарейки аудитора, шаблонная БД на тестовый файл.
   T-005: config, логи, errors, clock, settings + secrets, rate-limit, blob-store (+ `MemoryBlobStore`), первая
   боевая миграция (`settings`, `secrets`, `rate_limits`). T-059: http (Hono + oRPC, request-id, заголовки, CSRF,
   `Host`, два слушателя), `/healthz`, `/readyz`, три точки входа, `SIGTERM`. T-060: роль приложения без
   суперпользователя БД.
   T-006: jobs (pg-boss, `background_job_run`, `missed: "once"`, конверт со scope, `defineSweep`, `jobKey`), events
   (публикация в транзакции, подписки), realtime (`NOTIFY` → SSE с фильтром по домохозяйству).
5. **Все модули пустыми, но живыми (T-007).** 36 папок по шаблону с паспортами, `index.ts`, фабрикой; корень
   композиции собирает их в порядке `modules.ts`; реестры работают на пустых списках; цели `new-module`, `new-table`.
   *Готово:* граф содержит все модули, тест порядка зелёный.
6. **Каркас сайта и дизайн-система (T-008).** Vite + TanStack Router + Query + клиент oRPC, тема из `tokens.css`,
   шрифты, ~16 компонентов `ui/`, каркас, i18n, клиент `events.stream`, граница ошибок, `/dev/gallery` со всеми
   состояниями, Playwright + axe (`make e2e`), Vitest-проект `web`, цель `new-feature`. *Готово:* axe — 0 нарушений
   на галерее (1440/390), скриншоты сверены с `kit.css`.
7. **Сквозной срез (T-009).** `identity` в минимуме (первый запуск только с localhost, вход, сессия) + `accounts.list`
   («Наличные»): контракт → роутер → `ScopedDb` + аудитор → БД → сайт (TanStack Query) → e2e. Генератор тестов
   изоляции по реестрам в `testing`; тест «пользователь A не видит счёт B» — уже здесь.
8. **ИИ-шлюз и чат-заглушка (T-010).** `llm`: реестр моделей и цепочек, `LlmGateway` с тестовым провайдером —
   настоящим адаптером в реестре провайдеров (детерминированные ответы для тестов, не заглушка в смысле запрета
   `CONSTRAINTS.md`) — и режимами `replay|record|live`, кассеты (`ReplayModel`), журнал расхода, Langfuse, запрет
   вызова в транзакции, интерфейс маскирования. `agent`: цикл на `MockLanguageModelV4` с одним инструментом через
   `defineTool`. `chat.send` по oRPC → `useChat` рисует поток, шаг и карточку; закрытие вкладки не обрывает ответ;
   размер префикса (подсказка + `core`) ≤ 3 тыс. токенов.
9. **Запуск и тестовая инфраструктура (T-011).** `compose.yaml` с профилями, Dockerfile (tsdown → один `.mjs` на
   точку входа), `make dev/up/down/logs/db-reset/backup/doctor`; Vitest projects (unit, int, web) + шаблонная БД;
   Playwright + axe в режиме кассет; база покрытия `tooling/coverage-baseline.json`. Паспорта пакетов и
   `apps/*/CLAUDE.md` по шаблонам `docs/templates/`.

## 14. Запуск

Подробно (профили, образ, порты, тома, секреты) — ADR-0015 и ADR-0010 (состав Langfuse); правила для `Makefile`,
`compose.yaml`, `docker/` — `.claude/rules/docker-tooling.md`. Суть:

- Один `compose.yaml` с профилями: без профиля — `db`; `app` — `api`, `worker`, `bot` из одного образа; `models` —
  llama-server и whisper.cpp; `observability` — Langfuse, **включён по умолчанию** (OBS-05), приложение работает и без него.
- **`make dev`** — инфраструктура в контейнерах, код на хосте (`node --watch`, Vite с прокси); **`make up`** — всё в
  контейнерах (`make init && make up` на чистой машине). Только Docker Engine (пробрасывает iGPU `/dev/dri`).
- Данные — тома `pgdata`, `models` и `./data/{files,logs,backups,exports}` (одни пути в обоих режимах); копия —
  `make backup` и кнопка в админке, мастер-ключ в неё не входит.
