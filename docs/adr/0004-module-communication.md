# ADR-0004: Связи модулей — фасад вниз, событие вверх, реестр для подстановки

- **Статус:** Принято
- **Дата:** 2026-10-24
- **Требования:** NFR-21, NFR-22, OBS-01, BUD-03, TXN-10, P5

## Контекст

Модули должны вызывать друг друга без циклов и без «знаний наверх»: `transactions` не должен знать, что
`budgets` проверяет пороги, а `notifications` — что существует Telegram. Импорт 300 операций не должен порождать
сотни задач и дубли уведомлений.

## Решение

Три механизма (устройство — `docs/ARCHITECTURE.md` §5, правила задач и событий — `.claude/rules/jobs-events.md`):

- **Фасад вниз** — нужен результат сейчас, в той же транзакции (`receipts` → `transactions.recordFromReceipt(tx, …)`).
- **Событие вверх** — `events.publish(tx, …)` ставит задачу pg-boss в той же транзакции (outbox бесплатно);
  доставка «хотя бы раз», нагрузка — только id пачками, пересчёты схлопываются `jobKey(scope, …)`.
- **Реестр** в корне композиции — верхний модуль подставляет реализацию вниз (каналы уведомлений, обработчики
  `actions`, владельцы данных, инструменты агента, настройки).
- Имена: события `<модуль>.<прошедшее время>`, задачи `<модуль>.<глагол>`.

## Альтернативы

- **Прямые вызовы вверх** — циклы, «ком грязи».
- **Шина событий в памяти** — теряет события при падении процесса и не переживает перезапуск.
- **Брокер (Redis/BullMQ)** — лишний сервис, нет транзакционной постановки вместе с данными (ADR-0008).

## Последствия

- Реакция на событие приходит через доли секунды – секунды: тест «трата → уведомление 80 %» ≤ 3 с.
- Уведомления порогов идемпотентны по ключу «лимит + месяц + порог»; тест: импорт 300 операций → ≤ 5 задач
  пересчёта и ровно одно уведомление.
- Схемы событий — в `events.ts` публикующего модуля; подписаться может только модуль, у которого публикующий
  есть в `dependsOn`.
