# ADR-0016: Вход и секреты — Better Auth (ядро) + свои надстройки, argon2id, AES-256-GCM

- **Статус:** Принято
- **Дата:** 2026-10-24
- **Требования:** AUTH-01…12, ROLE-02, SEC-01, SEC-02, NFR-16, NFR-24, PRIV-07, R36, R37, R40

## Контекст

Нужны регистрация по email, подтверждение, сброс пароля (почта, Telegram, админ, код восстановления), сессии,
ограничение частоты, роли, блокировка, «последний админ», первый запуск только с localhost и демо-вход. Админ не
должен иметь возможности войти в чужой аккаунт (R37, PRIV-07). Ключи API, пароль SMTP и токен бота вводятся в
админке и хранятся зашифрованно (NFR-16).

## Решение

- **Better Auth — только ядро** (email + пароль, подтверждение, сброс, сессии, встроенное ограничение частоты),
  **без плагина `admin`**: он даёт права «войти как пользователь» и «задать чужой пароль», что противоречит R37.
  Таблицы Better Auth — системные (`systemTable`), владелец — модуль `identity`. В таблице пользователя —
  `role`, `status`, `demo`, `household_id` (`additionalFields`); `householdId` попадает в сессию.
- **Свои надстройки в `identity`**: первый запуск — синглтон `system_state.initialized` (признак, а не «нет админов»),
  экран только на локальном входе; **код восстановления** — один, хэш argon2id, после использования выдаётся новый;
  блокировка — поле `status` и немедленная отзывка сессий (`cookieCache` выключен); «последний админ» — проверка в
  каждом сценарии смены роли, блокировки и удаления; сброс из админки отправляет ссылку **пользователю** (почта и
  Telegram), ссылку админу — только при отсутствии обоих каналов, с журналом и уведомлением; демо-вход — только на
  локальном входе.
- **Пароли**: длина ≥ 12, **argon2id из `node:crypto`** (m = 64 МиБ, t = 3, p = 1, ≈ 145 мс), перехэш при входе.
- **Ограничение частоты**: ключ — email/`user_id` (вход, сброс, ассистент), не IP из `X-Forwarded-For` (подменяется;
  в контейнере IP — адрес шлюза); счётчики — в Postgres.
- **Сессии и CSRF**: cookie `kosht_session`, `HttpOnly`, `SameSite=Lax`; изменяющие запросы — проверка `Origin` /
  `Sec-Fetch-Site`; проверка `Host` против DNS-rebinding; без CORS и `trustProxy`.
- **Секреты**: AES-256-GCM (`node:crypto`), AAD = имя секрета, мастер-ключ в файле `secrets/master.key` (0600, создаёт
  `make init`, вне резервной копии); поля только для записи («задан ✓ / не задан»); приоритет «админка > env >
  умолчание»; в логи не попадают.
- **Почта**: Nodemailer + свой «локальный ящик» (таблица + страница только на локальном входе); при настроенном SMTP
  ящик выключается.

## Альтернативы

- **Lucia** — проект свёрнут в учебный материал; **Auth.js** — ориентирован на OAuth и Next.js.
- **Плагин `admin` Better Auth** — нарушает PRIV-07/R37.
- **Envelope-шифрование, KMS** — избыточно для ~10 значений на локальной машине.
- **«Только localhost» по IP или заголовку `Host`** — ломается в контейнере; признак — порт слушателя.

## Последствия

- Обновления Better Auth проверяются тестами надстроек (блокировка мгновенна, ссылка сброса одноразовая и истекает
  через 1 час, экран первого запуска один раз).
- Потеря `secrets/master.key` = повторный ввод секретов в админке (данные пользователей не шифруются им).
