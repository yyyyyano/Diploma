# ADR-0019: Аудитор SQL читает запрос настоящим парсером PostgreSQL (`libpg-query` 18)

- **Статус:** Принято (решение пользователя 2026-10-25)
- **Дата:** 2026-10-25
- **Требования:** ROLE-01, SEC-04, PRIV-07, OBS-04

## Контекст

Аудитор SQL — замок 3 изоляции (ADR-0006): до отправки он проверяет, что каждое обращение к пользовательской
таблице ограничено `household_id` домохозяйства scope. В T-004 он читал текст своим лексером и регулярками. Это
проверка текста, а не разбор: грамматику Postgres он угадывал по словам (`from` в `IS DISTINCT FROM`, алиас
`values`, `from"t"`), а булеву логику не видел вовсе — `where household_id = $1 or true` проходил. Каждая
найденная дыра закрывалась ещё одной регуляркой, а дифференциальный тест против Postgres находил новые.

## Решение

- Текст запроса разбирает `libpg-query` 18.x — грамматика PostgreSQL 18, собранная в WebAssembly
  (`libpg_query`, MIT). Точная версия — в `catalog:` (`pnpm-workspace.yaml`), с учётом `minimumReleaseAge`.
- Аудитор остаётся синхронной чистой функцией `(sql, params, режим)`: модуль WASM загружается один раз
  `await loadModule()` на верхнем уровне `audit.ts`, дальше — `parseSync`. Таблицы, предикаты, цели `SET`,
  `INSERT … VALUES`, `MERGE`, CTE и подзапросы берутся из дерева; текст, который парсер не принял, — отказ
  `UNPARSEABLE_SQL` (текст ошибки парсера в сообщение не попадает, OBS-04).
- Пакет — только в `apps/server/src/platform/db` (правило границ `libpg-query-only-in-platform-db`).

## Альтернативы

- **Лексер и регулярки (T-004)** — не видят приоритетов и булевой логики; каждая форма записи — новая регулярка.
- **`pgsql-parser`** — тот же `libpg-query` плюс депарсер, который аудитору не нужен.
- **`node-sql-parser`** и другие парсеры на JS — своя грамматика «похожая на Postgres»: расхождения с базой
  и есть то, от чего уходим.
- **Нативный `pg-query-native`** — сборка при установке (`allowBuilds`), зависимость от компилятора.
- **`EXPLAIN` в базе перед запросом** — второй запрос на каждый запрос и план вместо синтаксиса.

## Последствия

- Аудитор видит запрос так же, как Postgres: `OR`, `NOT`, `CASE`, внешние JOIN и область видимости имён —
  из дерева; дифференциальный тест проверяет ещё и то, что каждый текст, принятый базой, принимает парсер.
- Top-level await в `audit.ts`: модуль импортируется только из ESM (весь сервер — ESM), первый импорт ждёт
  загрузки WASM (~11 мс на машине разработки); вызвать аудитор до загрузки невозможно.
- WASM-файл (~1,7 МБ) читается пакетом с диска рядом с собой: при сборке образа (T-011) `libpg-query` остаётся
  внешней зависимостью и едет в `node_modules` образа (ADR-0002: нативные и динамические зависимости — внешние).
- Сбой WASM (переполнение стека на глубокой вложенности, нехватка памяти) — исключение парсера, то есть отказ
  `UNPARSEABLE_SQL`; экземпляр пакет пересоздаёт сам (до готовности нового синхронный разбор идёт старым). Текст
  запроса пишет код, данные пользователя приходят параметрами, поэтому вызвать такой сбой вводом нельзя.
- Известное расхождение 18.2.0 с базой: склейку строки через «--»-комментарий (`'x' --c↵'y'`) парсер не читает —
  отказ, не утечка; канарейка — в `audit.test.ts`, исключение — в дифференциальном тесте.
- Версия закреплена точно и обновляется отдельной задачей с прогоном канареек и дифференциального теста;
  новая версия ставится не раньше суток после публикации (`minimumReleaseAge`, без исключений).
- Цена — время разбора непрокэшированного запроса (замер — в паспорте `platform`); повтор текста — из кэша.
