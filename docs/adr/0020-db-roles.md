# ADR-0020: Роли БД — приложение работает ролью без прав владельца

- **Статус:** Принято (дирижёром по ADR-0021, 2026-10-25)
- **Дата:** 2026-10-25
- **Требования:** ROLE-01, SEC-04, PRIV-07, NFR-16

## Контекст

До T-060 приложение подключалось к базе ролью `kosht` — это `POSTGRES_USER` из `compose.yaml`, суперпользователь и
владелец всех таблиц. Пять замков ADR-0006 ловят забытый фильтр, но если запрос всё же ушёл мимо аудитора (ошибка
в самом аудиторе, неизвестная функция), у суперпользователя нет второго рубежа. Например,
`select pg_read_binary_file(pg_relation_filepath('receipts'))` читает с диска страницы таблицы со строками всех
домохозяйств, `select most_common_vals from pg_stats` показывает частые значения колонок, `COPY … TO PROGRAM`
запускает программу на сервере. ADR-0006 («Принято») не переписывается: роль — дополнительный замок к пяти.

## Решение

- **Две роли одной базы.** Приложение ходит ролью `kosht_app` (`DATABASE_URL`, пароль — `secrets/db_app_password`,
  создаёт `make init`): `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, без членства в ролях.
  Владелец `kosht` (`MIGRATION_DATABASE_URL`, `secrets/db_password`; `compose.yaml` и том не меняются) только
  мигрирует и выдаёт права: при старте процесса, `make migrate`, при сборке тестового шаблона. Хост, порт и база двух
  адресов совпадают, роли различаются — иначе `ConfigError`.
- **Права** (`platform/db/roles.ts`, `ensureAppRole`): `USAGE` на схемы из списка (`public`; T-006 добавит `pgboss`),
  `SELECT, INSERT, UPDATE, DELETE` на все их таблицы и `USAGE` на последовательности; `ALTER DEFAULT PRIVILEGES FOR
  ROLE kosht` — то же для будущих таблиц владельца; явный отзыв `TRUNCATE, REFERENCES, TRIGGER, MAINTAIN`, `CREATE` на
  `public` у `PUBLIC` и `SELECT` на `pg_stats`, `pg_stats_ext`, `pg_stats_ext_exprs` у `PUBLIC`. На схему `drizzle`
  (журнал миграций) прав нет. Расширения (`vector`, `pg_trgm`) и схемы создаёт владелец. `ALTER ROLE … SET` не
  используется.
- **Порядок старта** (`main/compose.ts`): одно соединение владельца `kosht-<роль>-migrate` → миграции и
  `ensureAppRole` под той же `pg_advisory_lock` → соединение закрыто → пул роли приложения → `assertAppRole`
  (отказ старта, если у роли есть `rolsuper`, `rolcreatedb`, `rolcreaterole`, `rolreplication`, `rolbypassrls`,
  членство в любой роли или `CREATE` на `public`, — так ловится старый `.env`, где приложение осталось бы владельцем).
- **Роль общая для кластера, блокировка — на базу.** Роль меняется только при расхождении атрибутов или пароля,
  транзакция выдачи повторяется на 23505/42710/XX000 (гонка процессов разных баз).
- **Пароль вне логов**: в `ALTER ROLE` уходит готовый SCRAM-SHA-256 verifier, на время транзакции выключена запись
  команд в лог Postgres (`log_statement`, `log_min_error_statement`, `log_min_duration_*`).
- **Аудитор не ослабляется**: функции файлов сервера и статистика планировщика остаются `HIDDEN_SQL` — замки
  независимы.
- **Переход**: `make init` заменяет в существующем `.env` старые умолчания `DATABASE_URL` и `DB_PASSWORD_FILE` и
  дописывает `MIGRATION_*` (программа `tooling/upgrade-env.ts`, печатает только имена переменных); `make migrate`
  создаёт роль на существующем томе без `db-reset`.

## Альтернативы

- **Оставить суперпользователя, полагаться на аудитор** — один замок там, где можно два; утечка при ошибке аудитора
  тихая и полная.
- **RLS** — решение пользователя «нет» (ADR-0006).
- **Владелец таблиц — сама роль приложения** — владелец может `ALTER`/`DROP` и выдавать права; миграции под
  приложением.
- **Роль и права в init-скрипте образа Postgres** (`docker-entrypoint-initdb.d`) — срабатывает только на пустом
  томе; существующие тома и права на новые таблицы не покрывает.
- **Отдельная роль-владелец без суперпользователя** — отзыв `pg_stats` у `PUBLIC` и создание расширений требуют
  суперпользователя; выигрыш мал, а `compose.yaml` и том пришлось бы менять.
- **`ALTER ROLE … SET` для настроек роли** — скрытое состояние роли кластера, которое не видно в коде.

## Последствия

- SQL мимо аудитора у роли приложения получает 42501: файлы сервера, `COPY … PROGRAM`, `lo_import`, DDL, роли,
  базы, `SET ROLE`, статистика, журнал миграций (`roles.int.test.ts`, сырой клиент мимо аудитора).
- Тесты работают ролью приложения (`createTestDb().pool`), DDL и фикстуры — владельцем (`owner`); тест, который
  портит роль, — со своей ролью `test_*`. Права копируются с шаблоном в клон; отпечаток шаблона включает текст выдачи.
- Два секрета БД: в контейнерах (T-011) приложению нужен ещё `db_app_password`.
- Новая схема с таблицами приложения — владелец создаёт и мигрирует, роль получает права через список схем
  (`APP_SCHEMAS`); права на функции схемы — задача, которой они нужны (T-006).
- Цена — одно лишнее соединение и несколько `GRANT` на старте каждого процесса.
