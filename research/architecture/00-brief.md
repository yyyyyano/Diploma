# Задание для исследователей архитектуры «Кошт»

## Продукт

«Кошт» — ИИ финансово-правовой ассистент для граждан Беларуси: веб-приложение на localhost и Telegram-бот.
Чеки по фото (модель с изображениями + арифметический валидатор + QR), импорт банковских выписок
(PDF/XLSX/CSV), категоризация, ИИ-агент с инструментами и стримингом, правовая база по текстам pravo.by
(каталог + индекс фрагментов, гибридный поиск, версии редакций, ежедневное обновление), калькулятор
налоговых вычетов, лимиты, цели, календарь, уведомления, Excel с живыми формулами и диаграммами,
админка, демо-данные. Полные требования — `SPEC.md` (прочитать §0–2, §5 и разделы своей области;
§10 — журнал решений, §11 — открытые вопросы).

## Жёсткие ограничения

- Всё бесплатно (open-source, бесплатные уровни API) и запускается локально; публичного хостинга нет.
- Машина: Intel Core Ultra 5 225H, встроенная графика Intel Arc, 36 ГБ RAM, **без NVIDIA**, Linux.
- Облачные модели: Groq → Z.ai (бесплатные), запасная — локальная модель; эмбеддинги только локально.
- Интерфейс на русском, i18n-ready; доступность WCAG AA.
- Лучшие практики, тесты без лишних (обычные тесты офлайн, на записанных ответах моделей; отдельно eval),
  линтеры и форматтеры, Makefile со всеми командами, обязательное структурированное логирование.

## Предпочтения пользователя (принимать как исходные, но честно указывать риски)

- **Монорепозиторий.**
- **Фронтенд — React**; UI-кит — тот, что даёт максимум готовых компонентов и минимум шаблонного кода.
- **Бэкенд — Node.js на TypeScript**, чтобы схемы данных были общими для фронта и бэка на одном языке.
  Фреймворк бэкенда и ORM — выбрать под задачу.
- **PostgreSQL + pgvector**; полнотекстовый поиск продумать (русский язык).
- Фоновые задачи и обращения к внешним сервисам — продумать; рассмотреть **pg-boss** против брокеров.
- **Oxlint**, форматтер **oxfmt**, **dependency-cruiser** (программные границы зависимостей между модулями).
- Для ассистента рассмотреть **LangChain / LangGraph / Deep Agents** (JS/TS).
- **Docker + Docker Compose** по лучшим практикам: проект запускается и локально без контейнеров,
  и полностью в контейнерах.
- Локальный git; **Conventional Commits**, описательные заголовки не длиннее ~72 символов, коммиты
  не слишком большие и не слишком маленькие — всё проверяется хуком.

## Как исследовать

- **Сегодня 2026-10-24.** Знания из памяти могут устареть: проверяй версии, статус поддержки и API по
  первоисточникам — официальная документация, Context7 (инструменты `mcp__context7__resolve-library-id`
  и `mcp__context7__query-docs`, загрузить через ToolSearch), `npm view <пакет> version time license`,
  GitHub (релизы, активность). Метки уверенности: **[В]** проверил сам, **[С]** косвенно, **[Н]** предположение.
- Цифр не выдумывать. Если можно быстро проверить на этой машине — проверь; эксперименты только во
  временной папке `/tmp/claude-1000/-home-user-University-DiplomaSupport-yana/b028d80d-e3f9-43c1-8889-7cdf568be4ad/scratchpad/research-<область>/`.
  Ничего не устанавливать глобально, не трогать другие файлы проекта.
- Пользователь — не архитектор: каждый выбор объяснять простыми словами с примером того, что это даёт
  проекту («например, при добавлении нового поля в операцию…»), термины пояснять в скобках.

## Формат результата

Файл `research/architecture/<NN>-<область>.md`, начинается с той же плашки «Справочник, а не требования».
Для каждого решения в своей области:

1. Что решаем и почему это важно для «Кошта» (1–3 предложения, пример).
2. Таблица 2–4 вариантов: суть, плюсы, минусы, зрелость и поддержка (версия, дата релиза), лицензия,
   соответствие требованиям SPEC (с номерами требований).
3. **Рекомендация** и почему; что могло бы изменить выбор.
4. Как это стыкуется с другими областями (на что опирается, что требует от соседей).
5. Риски и открытые вопросы к пользователю.
6. Источники (URL).

В конце файла — «Итог одним списком»: решение → рекомендованный вариант → одна строка почему.
Финальный ответ агента — выжимка этого списка на 10–20 строк.
