# 02. Бэкенд на Node.js/TypeScript и контракт «фронт ↔ бэк»

Область: HTTP-фреймворк, общие схемы и контракт API, устройство ~30 модулей, вход в систему, шифрование
секретов, почта, файлы, конфигурация и ошибки. ORM, БД, поиск и фоновые задачи исследует другой агент —
здесь только отмечено, что от них нужно бэкенду (раздел 9).

Метки уверенности: **[В]** проверил сам (запуск на этой машине, `npm view`, `gh api`, документация через
Context7), **[С]** косвенно (документация/статьи, сам не запускал), **[Н]** предположение.
Версии и даты — на 2026-10-24. Машина: Node.js 24.21.0, pnpm, Linux.

---

## 0. Главное за одну минуту

1. **Бэкенд = тонкая оболочка + модули.** Рекомендуется **Hono + oRPC + Zod 4**: модули ничего не знают
   про HTTP, а контракт API (схемы запросов/ответов/ошибок/стримов) лежит в отдельном пакете и
   подключается и к фронту, и к бэку. Запасной вариант — NestJS 12 (раздел 1).
2. **Единая схема на весь стек — Zod 4.** Одна и та же схема проверяет форму на сайте, запрос на сервере и
   описывает инструмент агента (LangChain/LangGraph JS сами зависят от Zod). Ошибки валидации выходят
   на русском (в Zod 4 есть русская и белорусская локали) **[В]**.
3. **Контракт без кодогенерации** (oRPC): поменяли поле в схеме — TypeScript сразу краснеет там, где
   фронт или бэк не согласованы. Стриминг чата (SSE), загрузка файла и типизированные ошибки работают
   в одной связке — **собрал и запустил прототип** (раздел 2.3) **[В]**.
4. **Модульный монолит с ярусами.** ~30 модулей SPEC разложены на 5 ярусов; зависимости идут только вниз,
   это проверяет `dependency-cruiser` (правила проверил на макете) **[В]**. Все расчёты (P1) — в чистом
   пакете `calc` без базы и сети.
5. **Вход — Better Auth** (core, без плагина admin) + свои тонкие надстройки (код восстановления,
   первый запуск, демо-вход). Нашёл и проверил две ловушки: подмена `X-Forwarded-For` обходит ограничение
   попыток, а плагин admin по умолчанию умеет «войти за пользователя» и «задать чужой пароль» —
   это ломает `PRIV-07`/R37 **[В]**.
6. **Секреты в БД** — AES-256-GCM из `node:crypto`, мастер-ключ в файле с правами 0600 вне БД.
7. **Локальный почтовый ящик — свой** (таблица + страница), а не Mailpit; «только с localhost» надёжнее
   делать **отдельным портом, опубликованным только на 127.0.0.1**, а не проверкой IP (в Docker адрес
   клиента может быть неотличим) — раздел 6.
8. **Файлы — локальная ФС за интерфейсом `BlobStore`**; MinIO отпадает — репозиторий **заархивирован**
   2026-04-24 **[В]**. Тип файла — по содержимому (`file-type`), CSV — отдельной эвристикой.

## 1. HTTP-фреймворк

**Что решаем и почему важно.** Фреймворк принимает запросы, раздаёт сайт, держит открытым поток ответа
ассистента (`CHAT-02`) и принимает фото чеков (`RCPT-01`). Пример: пользователь нажал «Спросить»,
ассистент 20 секунд ищет траты и считает — всё это время сервер должен отправлять по строчке («Ищу траты
за сентябрь…», потом слова ответа), а при нажатии «Стоп» — перестать тратить лимит модели.

Производительность не сравнивал: «Кошт» — локальное приложение для одного-нескольких пользователей,
узкое место — ответы моделей, а не каркас. Это не критерий выбора **[Н]**.

### Рекомендация: **Hono 4 + oRPC** (каркас — тонкая оболочка), запасной вариант — **NestJS 12 + `@orpc/nest`**

Почему Hono:

- **Всё на веб-стандартах.** oRPC (через fetch-адаптер), Better Auth и тесты говорят на одних и тех же
  `Request`/`Response`. В прототипе подключил oRPC и Better Auth к Hono без «переходников» **[В]**.
  Fastify для Better Auth требует ручного пересбора запроса (пример из их документации) **[В док.]**.
- **Каркас заменяем.** Бизнес-логика живёт в модулях и в oRPC-обработчиках; Hono — это ~100 строк
  «склейки» (middleware: заголовки безопасности, CSRF, лимит тела, id запроса, раздача сайта).
  Если Hono не устроит, переезд на Fastify — правка одного файла (у oRPC есть адаптеры и под Fastify,
  и под Node, и под Nest).
- **Нет второй системы маршрутов.** В Nest контроллеры дублировали бы то, что уже описано в контракте.
- **Готовые middleware в самом Hono** для наших требований `SEC-01/03`: `secure-headers`, `csrf`,
  `body-limit`, `request-id`, `context-storage` (AsyncLocalStorage), `timeout`, `ip-restriction`,
  `serve-static` **[В: `ls node_modules/hono/dist/middleware`]**.
- Не включать `compress` на потоке чата — сжатие может задерживать порции SSE **[Н]**; локально оно не нужно.

**Честно про Nest.** Он даёт готовую «раскладку по модулям», DI и самую большую базу примеров (удобно для
ИИ-агентов, пишущих код). Но: (1) v12 — свежий мажор (только ESM, rxjs для SSE, декораторы с
`emitDecoratorMetadata`; тесты — через SWC-плагин); (2) при контракте oRPC контроллеры становятся лишней
прослойкой (`@Implement`); (3) мы всё равно проверяем границы модулей dependency-cruiser'ом. Nest с oRPC
**сам не собирал** — только прочёл документацию **[С]**. Выбор поменяется на Nest, если пользователю важнее
«как у всех в индустрии» и привычная раскладка, чем минимум кода.

**Про DI-контейнер.** Не нужен: модули собираются вручную в одном файле «корень композиции»
(`createTxnModule({ db, clock, events })`). Зависимости видны глазами и dependency-cruiser'ом, а тесты
подставляют фальшивки без магии. Если позже захочется контейнер — `awilix` 13.0.5 **[В]**.

**Как стыкуется.** Опирается на: контракт (раздел 2), вход (4). Требует от соседей: от DB-агента — способ
запускать тесты на настоящем Postgres быстро; от инфраструктуры — два слушающих порта (раздел 6).

**Риски/вопросы.**
- Hono на Node: порядка 3 МБ, мажор 5 — в канале `next`; закрепить 4.x.
- Дисциплину модулей держат наши правила, а не фреймворк: нужен шаблон «новый модуль» в Makefile.
- **Вопрос пользователю:** лёгкий Hono (меньше кода, правила проверяем сами) или привычный Nest
  («все так делают», больше шаблонного кода)? Мой выбор — Hono.

## 2. Общие схемы и контракт API

### 2.1 Язык схем — источник истины

**Что решаем.** «Схема» — описание формы данных: что такое «операция», какие поля обязательны, как выглядит
сообщение об ошибке. Если описать её **один раз**, то и форма на сайте, и проверка на сервере, и инструмент
агента будут из одного источника. Пример: добавили в операцию поле «Заметка» (до 200 символов) — правите
схему в одном месте, и сайт, сервер и инструмент агента получают его сразу.

**Рекомендация: Zod 4.** Главные причины — готовая русская/белорусская локаль (`NFR-19`) и то, что
LangChain/LangGraph уже на Zod: одна и та же схема описывает и API, и инструмент агента, и ответ модели при
«строгом JSON» (`LLM-04`). Размер бандла Valibot — не аргумент для локального приложения. Все три
поддерживают Standard Schema, так что при необходимости схему можно поменять точечно. Что изменит выбор:
если фронту нужен минимальный размер бандла (мобильная сеть) — тогда Valibot на форме, но это усложнение.

**Практики.** Схемы «как на проводе» (DTO) живут в `packages/contract`; схемы таблиц БД — у ORM, между ними
явный маппинг (иначе любое переименование колонки ломает API). Деньги — целые копейки (`number` или строка
для больших значений) + код валюты, не `float`; календарные даты — `YYYY-MM-DD` (день по Минску, `NFR-23`),
моменты времени — ISO-строки UTC.

### 2.2 Как связать фронт и бэк

**Что решаем.** Способ, которым сайт вызывает сервер и «знает» типы ответов. Пример: ассистент присылает
поток событий («шаг», «слово», «карточка операции», «готово»); сайту нужно, чтобы TypeScript знал, что у события
`card` есть `amountMinor`, — и ругался, если кто-то это поле удалил.

**Рекомендация: oRPC (контракт-первым) + Zod 4.** Схема-контракт лежит в `packages/contract` (в нём нет
серверного кода — его безопасно импортировать с сайта), сервер «реализует» контракт (`implement(contract)`),
сайт получает типизированного клиента. Один и тот же роутер даёт два «лица»: быстрый внутренний RPC для
сайта и обычный REST/OpenAPI для `curl`, тестов и страницы документации (Scalar) на защите.

**Что мог бы изменить выбор.** Главный риск — oRPC молодой: одна основная команда, 5,7 тыс. звёзд против 40 тыс.
у tRPC, в разработке v2 (beta). Смягчаем: контракт лежит в отдельном пакете, обработчики тонкие (вся логика —
в сервисах модулей), версии фиксируем точно. Если oRPC «умрёт», запасной путь — tRPC 11: переписываются
роутеры и вызовы на сайте, а не логика. OpenAPI+кодогенерация — самый «стандартный» вариант, но два шага сборки
и слабый стриминг. ts-rest отвергнут: поддержка замерла.

**Версионирование.** Сайт и сервер выпускаются вместе (один репозиторий, один запуск), поэтому версии API для
сайта не нужны. Правило: менять контракт только добавлением полей, устаревшее помечать `deprecated`; если
появятся внешние клиенты [Д] — префикс `/api/v1`.

### 2.3 Что я проверил прототипом (папка `scratchpad/research-backend/`)

Hono 4.13.13 + oRPC 1.16.1 + Zod 4.6.7, Node 24.21, TypeScript 7.0.2:

- Контракт из трёх процедур: поток `chat.stream` (события `step`/`token`/`card`/`done`), загрузка
  `receipts.upload` (`z.file()`), типизированная ошибка `UNSUPPORTED_FILE` (415) **[В]**.
- Клиент получает события по одному с задержкой ≈100 мс между ними (то есть это настоящий стриминг,
  не буфер); при `abort()` на клиенте на сервере срабатывает `signal` и генератор завершается
  (в журнале: `generator finished/aborted, signal.aborted = true`) → «Стоп» реально освобождает лимит модели **[В]**.
- Тот же поток по REST: `content-type: text/event-stream`, формат `event: message / data: {...}`; multipart-загрузка
  по REST работает; `GET /openapi.json` содержит `text/event-stream` для чата и `multipart/form-data` для загрузки **[В]**.
- Некорректный ввод → `BAD_REQUEST 400` автоматически; ошибка типа файла приходит с типизированными данными **[В]**.
- `tsc` (TS 7): неверный тип аргумента и вызов несуществующей процедуры дают ошибки компиляции, тип поля
  `card.amountMinor` выводится как `number` **[В]**. Это и есть «добавили поле — TypeScript подсветил все места».
- Лимитов не проверял: загрузка идёт в память (`Request.formData()`); для фото 10–20 МБ нормально, ограничение
  ставится `bodyLimit` до разбора.

Подходит и для Telegram-бота/фоновых задач: они вызывают сервисы модулей напрямую, без HTTP; контракт
нужен только сайту и внешним клиентам.

### Как стыкуется
- **Агент (LangChain/LangGraph):** событие потока `ChatEvent` — наша схема в контракте; отображение
  событий LangGraph в `ChatEvent` — задача агента-исследователя. Карточки `CHAT-04` — вариантами
  `ChatEvent.card`.
- **Фронт:** `@orpc/tanstack-query` 1.16.1 существует (TanStack Query 5.104.5) — клиент для React-кода

- **Фоновые задачи:** для видимого прогресса (`RCPT-02`, `NFR-21`) нужен поток «событий пользователя»
  (прогресс задач, новые уведомления) — отдельная процедура-стрим `events.stream`; сервер получает события

## 3. Архитектура модулей бэкенда

**Что решаем.** В SPEC ~30 модулей (AUTH, RCPT, STMT, TXN, CAT, LAW, LEGAL, TAX, AGT…). Если модули свободно
ссылаются друг на друга, через пару месяцев получится «клубок»: чтобы поправить лимиты, придётся понимать
чеки и агента. Нужны правила «кто на кого может смотреть», проверяемые программой, а не договорённостью.
Отдельный вопрос — где живут расчёты (P1: число считает код, не модель).

### Варианты

| | Модульный монолит с ярусами (рекомендуемый) | Классическая «чистая» архитектура (domain/application/infrastructure для каждого модуля) | Плоская структура по технологиям (`controllers/`, `services/`, `repos/`) | Микросервисы |
|---|---|---|---|---|
| Суть | Каждый модуль — папка со своим публичным входом `index.ts`; модули разложены по ярусам, импорты только вниз | Те же модули, но внутри — 3 жёстких слоя и интерфейс на каждый репозиторий | Всё по типам файлов | Отдельные процессы |
| Плюсы | Просто; границы проверяет dependency-cruiser; легко расширять (диплом [Д]) | Максимально тестируемо | Минимум правил | Изоляция |
| Минусы | Дисциплина на нас (проверка в CI) | Много шаблонного кода для 30 модулей | «Клубок» гарантирован | Несоразмерно задаче; `NFR-01` «одной командой» |
| SPEC | `NFR-10`, `NFR-11`, `AGT-03` (расширяемость) | то же, дороже | не подходит | нарушает `NFR-01` |

### Рекомендация

**Структура репозитория (бэкенд-часть):**

```
packages/contract   схемы Zod + контракт oRPC; общий с сайтом; без серверных зависимостей
packages/calc       ЧИСТЫЕ расчёты (P1): без БД, сети, времени «сейчас» — всё приходит аргументами
apps/server         Hono-оболочка, корень композиции, модули в src/modules/<код>/
apps/web            React
```

**Внутри модуля — простая раскладка, не полная «чистая»:**

```
modules/txn/
  index.ts      публичный вход: типы + фабрика createTxnModule(deps) + инструменты агента
  domain/       чистая логика модуля (без ввода-вывода)
  service/      сценарии использования (принимают Scope — «чей это пользователь/домохозяйство»)
  repo/         работа с БД (наружу не торчит)
  api/          обработчики oRPC (тонкие: проверили → вызвали сервис)
```

**Порты (интерфейсы) — только там, где начинается внешний мир**, то есть что подменяем в тестах офлайн
(`NFR-11`): `Clock` (время), `BlobStore` (файлы), `Mailer`, `LlmClient` (записанные ответы моделей),
`SecretsVault`, `Jobs`, `EventBus`, внешние HTTP (`НБРБ`, `pravo.by`, `Telegram`). Для остального — обычные
классы/функции, без «интерфейса на всё».

**Ярусы (импорт — только вниз).** Таблица — предложение, детали согласуются с остальными областями:

| Ярус | Модули | Правило |
|---|---|---|
| 0. Платформа | config, db, логирование, ошибки, `Clock`, секреты, настройки, `BlobStore`, `Mailer`, события, обёртка над jobs, rate-limit | Не знает про бизнес |
| 1. Основа | `auth`, `privacy` (PRIV), `notif` (NOTIF — «приёмник»: уведомить может любой, он сам ни на кого не смотрит), `llm` (LLM; смотрит на `privacy`: есть ли согласие на облако) | Только платформа |
| 2. Данные и знания | Финансы: `accounts` → `categories` → `transactions` → {`receipts`, `imports`, `recurring`}; `profile` (PROF); знания: `law` (LAW) → `legal` (LEGAL) | Только ярусы 0–1 и «предки» внутри стека |
| 3. Расчёты над данными | `fin`, `budget`, `afford`, `tax` (смотрит на `law` — таблица ставок), `calendar`, `explain` (EXPL), `dashboard`, `weekly`, `xls` | Читают ярус 2, пишут только своё |
| 4. Оркестрация и входы | `agent` (AGT), `chat` (CHAT), `voice`, `telegram` (TG), `admin` (ADM), `demo`, `qa` (eval) | Могут всё ниже |

Снизу вверх связь — через **события**: например, `transactions` объявляет «операция создана», а `budget`
(лимиты 80%/100%), `recurring` и `tax` (найденные вычеты) подписаны. Так `transactions` не знает про лимиты —
и нет цикла `transactions ↔ budget`.

**Инструменты агента живут в своих модулях.** Каждый модуль экспортирует список инструментов
(схема Zod + функция, всегда с `Scope`), а `agent` их собирает в корне композиции. Дипломная функция
`DIP-01` = новый модуль с инструментами, `agent` не переписывается (`AGT-03`, `AGT-14`).

**Где живут детерминированные расчёты (P1).** В `packages/calc` — чистые функции «входные числа → результат»:
калькулятор вычетов (`TAX`), ПДН/«могу ли я позволить» (`AFF`), валидатор чека (`RCPT-05`), свободный остаток
(`FIN-20`), лимиты и цели (`BUD`), поиск регулярных платежей (`REC`), сопоставление/дедупликация
(`TXN`/`STMT`), формулы Excel (`XLS`). Модули достают данные из БД и **передают** их в `calc`. Преимущества:
тесты мгновенные, без БД и без модели (`NFR-11`); модель физически не может «посчитать сама» (`AGT-04`) —
инструменты агента вызывают только `calc` через модули.
**Совет, закладывающийся сразу:** каждая функция `calc` возвращает не просто число, а `{ value, trace }`,
где `trace` — дерево «формула → входы (идентификаторы операций, фрагментов закона)». Из него строятся
«Откуда эта цифра?» (`EXPL`, P2); добавлять `trace` потом в 20 функций гораздо дороже.

**Проверка границ — dependency-cruiser 18.7.0.** Проверил на макете, что три вида правил срабатывают **[В]**:

```js
// .dependency-cruiser.cjs (фрагмент; в проде правила порождаются из таблицы ярусов)
{ name: 'no-deep-import-into-module', severity: 'error',
  from: { path: '^src/modules/([^/]+)/' },
  to:   { path: '^src/modules/([^/]+)/',
          pathNot: ['^src/modules/$1/', '^src/modules/[^/]+/index\\.ts$'] } },
{ name: 'no-upward-dependency', severity: 'error',
  from: { path: '^src/modules/notif/' }, to: { path: '^src/modules/(bud|agt)/' } },
{ name: 'calc-is-pure', severity: 'error',
  from: { path: '^packages/calc/' }, to: { path: '^(src|node_modules)/' } },
```

Результат прогона: `no-upward-dependency`, `no-deep-import-into-module` и `calc-is-pure` ловят заведомо
неправильные импорты **[В]**. Порождение правил из таблицы ярусов в цикле — обычный JS в конфиге **[С]**.

**Правило под `PRIV-07`:** модуль `admin` **запрещено** импортировать из финансовых ярусов 2–3 (и из
`chat`/`agent`). Админка видит только метаданные (пользователи, провайдеры, задачи, законы). Это даёт
программную гарантию «админ не видит финансы и переписку», а не только «мы так договорились».

**Изоляция данных (`ROLE-01`, `SEC-04`).** Каждый сервис и репозиторий первым аргументом принимает `Scope`
(`userId`, `householdId`), который создаёт вход (HTTP-контекст, инструмент агента, фоновая задача). Без `Scope`
запрос к данным не скомпилируется. Как дополнительную страховку просить у DB-агента рассмотреть политики
строк Postgres (RLS) — это его область.

### Как стыкуется
- От DB-агента: транзакции из сервисов; тесты сервисов на настоящем Postgres достаточно быстрые (нужен
  способ: контейнер или встроенный Postgres); id и типы денег.
- От jobs-агента: порт `Jobs.enqueue(имя, данные, {singletonKey})`; обработчики запускаются в том же
  «контексте запроса» (раздел 8); догон пропущенных расписаний (`NFR-22`).
- Тулчейн: **dependency-cruiser 18.7.0 не поддерживает TypeScript 7** — предупреждает
  «missing-tsc-transpiler … typescript >=2.0.0 <7.0.0» и **не видит `.ts`-файлы**, пока рядом не стоит
  `typescript@6` **[В]**. Поставить TS 6 как dev-зависимость для проверок (TS 7.0.2 вышел, и его
  собственный компилятор тоже работает: `emitDecoratorMetadata` проверил **[В]**) — передать агенту по
  инструментам.

### Риски и вопросы
- Таблицу ярусов нужно согласовать со всеми агентами (особенно `notif`, `llm`, `profile`).
- Время «сегодня» по Минску (`NFR-23`): в Node 24.21 нет `Temporal` (проверил: `typeof Temporal` →
  `undefined`) **[В]**. Достаточно `Intl.DateTimeFormat` с часовым поясом из настроек в модуле `Clock`
  (или `temporal-polyfill` 1.0.6) **[С]**.
- Вопрос по деньгам (решить с calc/DB): целые копейки в `number`/`bigint` — по умолчанию; проценты ставок —
  десятичная арифметика (`decimal.js` 10.6.0 / `big.js` 7.0.1) — **[Н]**, когда дойдём до `TAX`.

## 4. Аутентификация

**Что решаем.** Регистрация, вход, подтверждение почты, сброс пароля, коды восстановления, роли,
блокировка, ограничение попыток (`AUTH-01…12`, `SEC-01/02`). Пример: единственный администратор забыл
пароль, почта не настроена и Telegram не привязан → «Войти с кодом восстановления» должно сработать (`AUTH-05`).

| | Better Auth (core) | Своя на сессиях | Lucia | Auth.js (NextAuth) |
|---|---|---|---|---|
| Версия, дата | 1.7.12, 2026-10-20 **[В]**; 30,4 тыс. звёзд; MIT | — | 3.2.2, **объявлена устаревшей** (март 2025); сайт теперь «учебник» **[В]** | `@auth/core` 0.41.3, `next-auth` 4.24.15 (июль 2026) **[В]** |
| Суть | Библиотека входа: email+пароль, письма, сессии в БД, лимиты, плагины | ~500–800 строк: таблицы `session`, хэши, токены | Рекомендует писать самому по их руководству | Заточена под Next.js; с сентября 2025 ведёт её команда Better Auth, новичкам советуют Better Auth **[В]** |
| Сессии в Postgres | Да, по умолчанию в БД **[В док.]** | Да | — | Ограничения для credentials **[Н]** |
| Подтверждение почты/сброс | Есть (`sendVerificationEmail`, `sendResetPassword`, срок 1 час по умолчанию) **[В]** | Пишем сами | — | Слабо для пароля |
| Лимит попыток | Встроенный по путям: `customRules` **[В]** | Своя (`rate-limiter-flexible`) | — | Нет |
| Роли/блокировка | Плагин `admin` (см. ловушку ниже) | Свои поля | — | — |
| Риск | Куплена Vercel 2026-07-07, остаётся MIT; частые релизы | Безопасность «на нас» | Не использовать | Не подходит под Hono |

**Рекомендация: Better Auth (только ядро, без плагина `admin`) + свои надстройки.**

**Что проверил.** (1) Регистрация → вызывается наше письмо подтверждения (`sendOnSignUp`), вход разрешён
до подтверждения (`requireEmailVerification: false`, как в `AUTH-03`) **[В]**. (2) Запрос сброса → ссылка
в обработчике `sendResetPassword`: оттуда мы решаем, куда отправить (почта/Telegram/показать админу) —
этого достаточно для `AUTH-05` **[В]**. (3) Свой хэш пароля работает: **argon2id из самого Node**
(`crypto.argon2`, есть в Node ≥24.7; на этой машине 29 мс при 19 МиБ, 2 прохода) **[В]**; параметры
(19 МиБ, t=2, p=1) — минимум по OWASP **[С]**. Встроенный scrypt тоже допустим; если не хочется отвечать за
формат хэша — оставить по умолчанию **[Н]**. (4) Ограничение попыток: 3 неверных входа → `429` со временем
ожидания **[В]**.

**Две ловушки, которые нашёл (обе проверены):**

1. **Подмена `X-Forwarded-For` обходит ограничение попыток.** По умолчанию Better Auth берёт IP из этого заголовка,
   клиент может подставить любой → 8 неверных паролей подряд с разными «адресами» дали 8 раз `401`, а не `429` **[В]**.
   Лечение: наш Hono берёт адрес из соединения (`getConnInfo`), кладёт его в служебный заголовок и
   `advanced.ipAddress.ipAddressHeaders: ['x-client-ip']`; после этого те же 6 попыток дают `401,401,401,429,429,429` **[В]**.
2. **Плагин `admin` по умолчанию даёт роли admin права `impersonate` (войти как пользователь) и `set-password`
   (задать чужой пароль)** — в исходниках `dist/plugins/admin/access/statement.mjs` **[В]**. Это прямо противоречит
   `PRIV-07` и R37 («админ не может войти в чужой аккаунт»). Решение: не использовать плагин — блокировка,
   роль и «выдать ссылку сброса» (`ADM-30`) пишем сами поверх поля `status` и `auth.api.requestPasswordReset`;
   либо плагин с кастомными ролями без этих прав.

**Что дописываем сами (тонкие надстройки):**
- **Первый запуск (`AUTH-10`):** таблица-синглтон `system_state.initialized` с уникальным ограничением
  (две одновременные попытки → одна проходит); работает только на «локальном» слушателе (раздел 6).
- **Код восстановления (`AUTH-05`):** таблица `recovery_code` (хэш argon2id, `used_at`); эндпойнт «задать новый
  пароль по коду» меняет пароль и отзывает все сессии; после использования выдаётся новый. Реализация
  использует `auth.$context` (внутренний API) **[С]** — проверить при реализации; запас — написать плагин
  Better Auth на `createAuthEndpoint`.
- **Демо-вход (`DEMO-04`):** эндпойнт «Войти как демо» создаёт сессию демо-пользователя; доступен только на
  локальном слушателе.
- **Блокировка (`AUTH-11`):** поле `status`; выключить `cookieCache`, чтобы блокировка действовала сразу, а не через
  5 минут; плюс проверка статуса в хуке создания сессии.
- **Последний администратор (`AUTH-12`):** проверка в одной транзакции в модуле `admin`/`auth`.
- **Доставка ссылки сброса (R37):** один метод `deliverResetLink(user, url)`: почта → Telegram → (только если
  нет ни того ни другого) показать админу с записью в журнал.
- **Пароль:** длина от 10 до 128 (предлагаю; SPEC требует «требования к длине» без числа).
- **Вход через браузер:** куки `HttpOnly`, `SameSite=Lax`; сайт и API — **один источник** (разработка — прокси Vite,
  работа — раздаёт сервер), поэтому CORS не нужен. CSRF: проверка `Origin` в Better Auth и `hono/csrf` для
  multipart-загрузки. При включённом «доступе из сети» (`NFR-24`) список доверенных адресов должен быть
  динамическим (`trustedOrigins` как функция **[С]**).

### Как стыкуется
От DB-агента: адаптер таблиц Better Auth (`user`, `session`, `account`, `verification`) — Drizzle, Prisma, Kysely
или напрямую `pg` **[В: peerDependencies]**; нужны uuid-идентификаторы и внешние ключи на пользователя; расширение
таблицы `user` полями `role`, `status`, `demo` (`additionalFields`). Telegram-агенту: `deliverResetLink`, привязка.

### Риски и вопросы
- Better Auth перешёл под крыло Vercel (2026-07-07): лицензия MIT, но возможны смены курса — **точные версии
  в lock-файле**, не обновлять автоматически; запасной путь — «своя на сессиях».
- Не включать `rateLimit.enabled` только «в production»: по умолчанию в разработке он выключен **[В док.]** —
  включить явно.
- **Вопросы пользователю:** (1) код восстановления — один код, после использования выдаётся новый (мой
  вариант) или набор из 8 одноразовых? (2) минимальная длина пароля 10 — подходит?

## 5. Шифрование секретов в БД (`NFR-16`)

**Что решаем.** Ключи Groq/Z.ai, пароль почты и токен бота вводятся в админке и должны лежать в БД
зашифрованными. Пример: кто-то получил копию файла БД — без мастер-ключа он не должен прочитать ключ Groq.

| | `node:crypto` AES-256-GCM, один мастер-ключ с версией (рекомендуемый) | Envelope-схема (мастер-ключ → ключ данных → секрет) | Внешний сервис (Vault, KMS, `age`/SOPS) | Системное хранилище паролей ОС (libsecret) |
|---|---|---|---|---|
| Суть | Каждое значение шифруется мастер-ключом | Мастер-ключ шифрует ключ данных, он — секреты | Отдельная служба хранит ключи | Ключ в связке ключей ОС |
| Плюсы | Нет зависимостей; 10 секретов — мало | Смена мастер-ключа без пересохранения всех секретов | Лучшая практика для облака | Ключ вне диска приложения |
| Минусы | Смена ключа = перешифровать ~10 строк (тривиально) | Лишняя сложность для 10 значений | Нарушает «локально, одной командой» (`NFR-01`) | Не работает в Docker; нужен D-Bus/GUI-сеанс (`@napi-rs/keyring` 2.1.2) **[Н]** |
| Зрелость | Встроено в Node | то же | — | — |

**Рекомендация.** AES-256-GCM из `node:crypto`: случайный 12-байтовый IV на каждое значение, **AAD =
имя секрета + номер ключа** (подмена одной записи другой не проходит), формат записи `v1.<kid>.<iv>.<tag>.<ct>`.
Проверил: расшифровка с верным AAD работает, с чужим AAD — `Unsupported state or unable to authenticate data` **[В]**.
Envelope — избыточен для десятка значений: ротация = перешифровать ~10 строк. Что изменит выбор: если секретов
станут сотни (токены per-user [Д]) — тогда envelope.

**Где хранить мастер-ключ локально.** Файл `data/secrets/master.key` (32 байта случайных), создаётся
автоматически при первом запуске с правами `0600` — **вне БД и в отдельном томе** (в Docker — отдельный
том или Docker secret). Переопределение для разработчика — переменная окружения. Запрет на лишнее:
- Копия БД без файла ключа бесполезна; файл ключа в `.gitignore`.
- Потеря ключа = секреты придётся ввести заново в админке (приемлемо; `ADM-50`/`ADM-60`).
- Секреты в коде всегда в обёртке `Secret` (`toString()`/`toJSON()` → `[REDACTED]`) плюс редакция путей в
  логгере (`OBS-04`).
- Контракт: поле «только запись»: вход `{ value: string }`, выход `{ isSet: boolean, updatedAt }` (`NFR-16`).
- Приоритет «значение из админки > переменная окружения > по умолчанию»: реестр настроек
  (раздел 8) знает, какие ключи секретные.

**Риски/вопросы.** Тот, кто получил и файл ключа, и БД, читает всё — это уровень защиты локального
приложения (угроза — потеря копии БД/бэкапа, а не взлом работающей машины). Вопросов к пользователю нет.

**Источники.** [Node: crypto](https://nodejs.org/api/crypto.html) · [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) ·
эксперимент `scratchpad/research-backend/t1.mjs`.

## 6. Почта и локальный ящик (`AUTH-06`, `NFR-24`)

**Что решаем.** Письма подтверждения и сброса пароля должны уходить по SMTP, а пока почта не настроена —
попадать в «локальный ящик», который открывается только на этом компьютере. Пример: демо на защите — «Забыли
пароль?» → письмо появляется на странице «Почта (демо)», нажимаем ссылку — пароль сброшен, интернет не нужен.

### 6.1 Отправка и ящик

| | Nodemailer + свой ящик (таблица `mail_outbox` + страница) (рекомендуемый) | Nodemailer + Mailpit | Только SMTP без ящика |
|---|---|---|---|
| Суть | Порт `Mailer` с двумя адаптерами: SMTP и «сохранить в БД»; страница показывает письма | Mailpit — готовый почтовый «ящик-песочница» со своим веб-интерфейсом | Без демо-режима |
| Плюсы | Внутри приложения, в нашем дизайне, одна команда запуска, письма — сущность из §5 SPEC («Письмо»), ссылка кликабельна | Настоящий SMTP, красивый интерфейс, поиск | Просто |
| Минусы | Свою страницу писать (несложно) | Ещё один процесс/контейнер: для запуска без Docker нужно скачать бинарь (на этой машине `mailpit` нет **[В]**); интерфейс не наш; SPEC: «не в админке», «встроенный» | Нарушает `AUTH-06` |
| Зрелость | Nodemailer 10.2.1 (2026-10-22), MIT-0 | Mailpit 1.32.0 (2026-10-22), MIT, 10,7 тыс. звёзд | — |

**Рекомендация.** Nodemailer для SMTP (проверка настроек `transporter.verify()` для кнопки «Отправить тестовое
письмо»), порт `Mailer` и адаптер «локальный ящик» в БД; страница доступна только на локальном слушателе, без входа,
с пометкой «только для демо и разработки»; при настроенной почте адаптер переключается на SMTP, ящик выключается
(`AUTH-06`). Mailpit — по желанию как инструмент разработчика (профиль compose), не часть продукта.
Письма отправляются в фоне (не ждать SMTP в обработчике: заодно не раскрываем, существует ли адрес, по времени ответа).

### 6.2 «Только с localhost» — как сделать надёжно

Что обнаружил: проверка «адрес клиента = 127.0.0.1» в Docker **ненадёжна**. Docker на Linux публикует порт
через сеть-мост, и запрос с самого компьютера может выглядеть как пришедший с адреса шлюза (172.17.0.1), а в
Docker Desktop (на этой машине CLI настроен на `~/.docker/desktop/docker.sock`, и сейчас он не запущен **[В]**)
все запросы приходят изнутри виртуальной машины — отличить своего от соседа по Wi-Fi по IP нельзя **[Н]**.
Проверить не смог (демон не запущен) — нужна проверка на реальной машине.

| | Два слушающих порта: «локальный» (публикуется только на 127.0.0.1) и «сетевой» (рекомендуемый) | Проверка IP клиента | Проверка заголовка `Host` |
|---|---|---|---|
| Суть | Один процесс слушает два порта; маршруты «только локально» (первый запуск, ящик, демо-вход) работают только на первом | `socket.remoteAddress` ∈ {127.0.0.1, ::1} | `Host: localhost` |
| Надёжность | Граница задаётся сетью, а не данными запроса | Хороша без Docker; в Docker неоднозначна | Подделывается любым клиентом (`curl -H "Host: localhost"`) |
| Docker | `127.0.0.1:3001:3001` и `3000:3000` в compose | Нужно знать адрес шлюза | Годится только как дополнение |

**Рекомендация.** Два порта (названия примерные): основной слушает всегда; «локальный» — только `127.0.0.1`.
Сайт целиком доступен на обоих; маршруты первого запуска, ящика и демо-входа отвечают **только** на локальном
(`NFR-24`, R40). Переключатель «доступ из сети» (`NFR-24`) без Docker перепривязывает основной порт
(127.0.0.1 ↔ 0.0.0.0) на лету; в Docker привязка задаётся в compose, поэтому переключатель либо требует
перезапуска, либо основной порт публикуется на 0.0.0.0, а приложение отвечает отказом, когда опция выключена
(различимость IP — см. выше). Ссылки в письмах строятся из настройки по адресу (`localhost` или сетевой).
Риск: сайт на двух портах — разные источники; куки привязаны к хосту, не к порту, поэтому вход общий **[С]**,
но проверить при реализации.

**Как стыкуется.** Инфраструктура (Docker/Compose): публикация портов, тома данных и ключа. Админка: ADM-60.
**Вопрос пользователю:** допустимо ли, что в Docker включение «доступа из сети» вступает в силу после
перезапуска контейнера (простой вариант), или нужно «на лету» (сложнее)?

**Источники.** [Nodemailer](https://github.com/nodemailer/nodemailer) · [Mailpit](https://github.com/axllent/mailpit) ·
[Hono conninfo](https://hono.dev/docs/helpers/conninfo) **[С]** · `docker info` на этой машине (проверка выше).

## 7. Хранение файлов (`SEC-03`, `RCPT-11`, `STMT-10`, `PRIV-06`)

**Что решаем.** Фото чеков и исходные выписки нужно хранить, открывать только владельцу и удалять целиком
вместе с аккаунтом. Пример: пользователь удалил аккаунт — ни одного его файла не должно остаться (`КП PRIV`).

| | Локальная ФС за интерфейсом `BlobStore` (рекомендуемая) | MinIO | RustFS / другие S3-совместимые | Файлы в БД (bytea / large objects) |
|---|---|---|---|---|
| Суть | Файлы в `data/files/<userId>/…`, метаданные в таблице | S3-хранилище локально | то же | Бинарные поля Postgres |
| Плюсы | Ничего лишнего; «удалить пользователя» = удалить папку; интерфейс допускает S3 позже | Стандарт S3 | Активны | Один бэкап; транзакционно |
| Минусы | Бэкап — копировать папку | **Репозиторий заархивирован 2026-04-24, последний релиз RELEASE.2025-10-15 (CVE)** **[В]** | Ещё один сервис (RustFS: Apache-2.0, 35 тыс. звёзд, активен **[В]**); избыточно | Раздувает БД, медленные бэкапы |
| SPEC | `NFR-01`, `SEC-03`, `PRIV-06` | `NFR-01` под вопросом | то же | работает, но хуже |

**Рекомендация: локальная ФС за `BlobStore`.** Раскладка `files/<userId>/<вид>/<uuid>`: удаление аккаунта —
`rm -r` одной папки (контентная адресация с общими файлами между пользователями усложнила бы `PRIV-06`).
Запись «во временный файл → fsync → rename» (без битых файлов при сбое); метаданные (владелец, вид, тип по
содержимому, размер, SHA-256, ключ хранилища) — в таблице `file`; файлы без записи подбирает фоновая очистка.
Отдача — только через проверку владельца (`GET /files/:id`) с `Content-Type` из **определённого** типа (не
присланного клиентом), `X-Content-Type-Options: nosniff`, `Content-Disposition`. MinIO отпадает; S3-адаптер
понадобится, только если появится публичный хостинг [Д].

**Проверка типа по содержимому (`SEC-03`) — `file-type` 22.2.0** (2026-10-14, MIT). Прогнал на реальных
образцах **[В]**:

| Файл | Результат |
|---|---|
| PNG, JPEG | `image/png`, `image/jpeg` |
| PDF | `application/pdf` |
| XLSX | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
| XLSX, переименованный в `fake.png` | **XLSX** (расширение не обманывает) |
| EXE, переименованный в `renamed.pdf` | `application/x-msdownload` → отклонить |
| CSV (UTF-8 и windows-1251), HTML, SVG, случайные байты | **не определены** |

Выводы: (1) **белый список** типов: JPEG, PNG, WebP, HEIC/HEIF (снимки iPhone, `RCPT-01`) **[С]**, PDF, XLSX; всё
остальное — отказ; HTML и SVG не принимаем никогда (XSS). (2) **CSV определяется только эвристикой**
(нет нулевых байтов, читается как UTF-8 или windows-1251, ≥2 строки с единым разделителем) — это отдельный
явный путь «по расширению + эвристике». (3) Старый `.xls` (формат OLE) `file-type`, вероятно, определит как
общий контейнер, не отличая от `.doc` **[С]** — проверить на реальном образце. (4) XLSX — это zip: до разбора
проверить число записей и суммарный распакованный размер (защита от «zip-бомбы»); PDF разбирать в отдельном
потоке/процессе с лимитами памяти и времени — требование агенту по разборщикам выписок.

**Загрузка.** Лимит размера — `bodyLimit` до разбора (по умолчанию: фото ≤ 15 МБ, выписки ≤ 25 МБ — предлагаю);
oRPC читает файл в память — для таких размеров нормально **[В]**.

**Как стыкуется.** Агент чеков: HEIC → JPEG конвертация нужна до модели (prebuilt-сборки `sharp` не декодируют HEVC
**[Н]**; iOS Safari обычно сам отдаёт JPEG из `<input type=file>`, а Telegram присылает фото сжатыми в JPEG **[С]**).
DB-агент: таблица `file`.

**Вопросы.** Лимиты размера (15/25 МБ) — устраивают? Поддерживать ли старый `.xls` (формат Excel 97–2003)?

**Источники.** [file-type](https://github.com/sindresorhus/file-type) · [MinIO (архив)](https://github.com/minio/minio) ·
[RustFS](https://github.com/rustfs/rustfs) · эксперимент `scratchpad/research-backend/t3.mjs`.

## 8. Конфигурация, ошибки, идентификатор запроса

### 8.1 Конфигурация и env-схема

**Что решаем.** Откуда берутся настройки. Часть нужна до подключения к БД (адрес БД, порт, путь к ключу,
режим разработки `OBS-05`), часть редактируется в админке (SMTP, ключи, часовой пояс, режим сети) — и `NFR-16`
требует приоритета «админка > окружение».

**Рекомендация.** Два слоя:
1. **Окружение (bootstrap):** `.env.example` в репозитории, загрузка встроенным `process.loadEnvFile()` /
   `--env-file` Node и разбор схемой Zod (`z.coerce.number()`, `z.stringbool()`, `z.url()`) — при ошибке
   приложение сразу падает и печатает, что именно не так (`z.prettifyError`: «✖ expected string, received
   undefined → at DATABASE_URL») **[В]**. Отдельная библиотека (`@t3-oss/env-core` 0.13.11) не нужна.
   Режим разработки (`OBS-05`) читается **только** отсюда.
2. **Реестр настроек в БД:** `defineSetting({ key, schema, secret, default, envFallback })`; чтение — `БД >
   окружение > умолчание`; секретные ключи шифруются (раздел 5); кэш сбрасывается событием. Типы выходят в
   контракт: секрет → `{ isSet }`.

Системный часовой пояс (`NFR-23`) — настройка из реестра, по умолчанию `Europe/Minsk`.

### 8.2 Единый формат ошибок (`OBS-02`)

Рекомендую использовать формат ошибки oRPC `{ code, status, message, data }` **[В]** как единственный и добавить
к нему:
- **стабильные коды** (реестр в `contract`): `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`,
  `VALIDATION`, `RATE_LIMITED`, `UNSUPPORTED_FILE`, `LLM_UNAVAILABLE`, `LAW_NOT_IN_BASE` и т. д.; тексты для
  человека — **на сайте по коду** (i18n, `NFR-19`), а не сообщения сервера;
- `data.requestId` во всех ответах-ошибках — пользователь может назвать код обращения, а мы найдём его в логах;
- внутренние ошибки → `500 INTERNAL` с общей фразой, без текста исключения и стека (стек — в логе, `OBS-02`);
- ошибки проверки схемы → `data.issues` с путём и кодом проверки, **без подстановки введённых значений**
  (в них могут оказаться суммы и персональные данные, `OBS-04`);
- в сервисах бросается `AppError(code, params)`, в одном месте (перехватчик oRPC) преобразуется в ответ.
  Модули про HTTP-коды не знают.

### 8.3 Идентификатор запроса и контекст

Создаётся **на каждом входе**: HTTP (`hono/request-id`; чужой `X-Request-Id` принимать только по шаблону
`[A-Za-z0-9-]{8,64}`), апдейт Telegram, фоновая задача. Хранится в `AsyncLocalStorage` (`hono/context-storage`
есть **[В]**) вместе с внутренним `userId` и источником (`web`/`telegram`/`job`); логгер подмешивает эти поля
сам. Так прослеживается путь «сообщение в боте → агент → вызов модели → инструмент» (`OBS-01`). Сам логгер
(pino 10.4.0 и т. п.) и трассы ИИ — область соседнего агента; от меня ему нужно только это «окно контекста».

**Вопросы.** Нет.

**Источники.** [Node: process.loadEnvFile / util.parseEnv](https://nodejs.org/api/process.html) ·
[Zod: prettifyError, stringbool](https://zod.dev) · [oRPC: ошибки](https://github.com/middleapi/orpc/blob/main/apps/content/docs/error-handling.mdx) ·
эксперимент `scratchpad/research-backend/t4.mjs`.

## 10. Сводные риски и вопросы к пользователю

**Риски (по убыванию):**
1. oRPC молод (одна команда, v2 в бете) — смягчено изоляцией контракта и тонкими обработчиками.
2. Better Auth под Vercel, частые релизы, нужны надстройки на внутреннем API — точные версии, запасной путь «своя».
3. Определение «только локально» в Docker (особенно Docker Desktop) не проверено — две порты, проверить на реальной машине.
4. dependency-cruiser не видит TS 7 — нужен TS 6 для проверок.
5. Hono v5 на подходе — закрепить 4.x.
6. Дисциплина модулей держится на проверках в CI, а не на каркасе (в отличие от Nest).

**Вопросы:**

## Итог одним списком

| Решение | Рекомендованный вариант | Почему |
|---|---|---|
| HTTP-фреймворк | **Hono 4.13** (запасной — NestJS 12 + `@orpc/nest`) | Веб-стандарты, тонкая заменяемая оболочка, нет второй системы маршрутов |
| Язык схем | **Zod 4.6** | Русская/белорусская локаль, `z.file`, JSON Schema, на нём же LangChain/LangGraph |
| Контракт фронт ↔ бэк | **oRPC 1.16 (контракт-первым) в `packages/contract`** | Типизированный стриминг, файлы и ошибки в одной связке (прототип), плюс REST/OpenAPI бесплатно |
| Версионирование API | Один репозиторий, только добавление полей, `deprecated`; `/api/v1` — если появятся внешние клиенты | Сайт и сервер выходят вместе |
| Устройство модулей | Модульный монолит, 5 ярусов, публичный `index.ts`, корень композиции без DI-контейнера | Просто и проверяемо |
| Проверка границ | **dependency-cruiser 18.7** (+ `typescript@6`) | Правила «только вниз», «только через index.ts», «calc чист», «admin не видит финансы» — проверены на макете |
| Расчёты (P1) | Пакет `packages/calc`: чистые функции, возвращают `{value, trace}` | Тесты без БД; основа для «Откуда эта цифра?» |
| Вход | **Better Auth 1.7 (ядро, без плагина admin)** + свои надстройки | Покрывает почту/сброс/сессии/лимиты; плагин admin нарушает `PRIV-07` |
| Хэш пароля | argon2id из `node:crypto` (19 МиБ, t=2, p=1) | Встроен в Node ≥24.7, 29 мс |
| Лимит попыток | Встроенный Better Auth + IP из соединения, не из `X-Forwarded-For` | Иначе обходится подменой заголовка (проверено) |
| Шифрование секретов | AES-256-GCM, `node:crypto`, AAD = имя секрета, мастер-ключ в файле 0600 вне БД | Минимум зависимостей; envelope избыточен для ~10 значений |
| Почта | Nodemailer 10 + свой «локальный ящик» (таблица + страница) | Встроен, в нашем дизайне; Mailpit — только инструмент разработчика |
| «Только localhost» | Два порта: локальный (публикуется на 127.0.0.1) и сетевой | Граница задаётся сетью, а не IP/заголовком |
| Хранение файлов | Локальная ФС за `BlobStore`, `files/<userId>/…` | Удаление аккаунта = удаление папки; MinIO заархивирован |
| Проверка типа файла | `file-type` 22.2 + белый список; CSV — эвристика | Не обманывается переименованием; CSV/HTML/SVG не определяются |
| Конфигурация | Окружение через Zod-схему + реестр настроек в БД (БД > env > умолчание) | Соответствует `NFR-16`; быстрая понятная ошибка при старте |
| Ошибки | Формат oRPC + стабильные коды + `requestId`, тексты на сайте | Единый формат, i18n, без утечки внутренностей |
| Идентификатор запроса | `hono/request-id` + AsyncLocalStorage на каждом входе (HTTP, Telegram, задача) | Сквозная трассировка (`OBS-01`) |
