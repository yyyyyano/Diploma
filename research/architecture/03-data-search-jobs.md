## 1. PostgreSQL: версия, образ, расширения

**Что решаем.** На какой версии Postgres строим базу и как получить pgvector в Docker, чтобы «поиск по законам»
и «очередь задач» жили в одной СУБД. Например, ночная проверка законов, очередь векторизации и сам поиск
по статье 209 НК работают в одном процессе базы, без отдельного Redis и отдельного поискового сервера.

| Вариант | Суть | Плюсы | Минусы | Версия, дата | Лицензия |
|---|---|---|---|---|---|
| **A. `pgvector/pgvector:0.8.7-pg18-trixie`** | официальный образ Postgres + pgvector | один образ, нужное расширение есть, всё остальное (`pg_trgm`, contrib) как в обычном образе | образ ведёт автор pgvector, а не Docker Official Images | теги `0.8.7-pg18*` от 2026-10-01 [В]; Postgres в базовом образе 18.6 (2026-10-21) [В] | PostgreSQL License (pgvector) [С] |
| B. Официальный `postgres:18.6` + свой Dockerfile (`apt install postgresql-18-pgvector`) | то же, но сборка своя | полный контроль версии | лишний Dockerfile, пакет надо проверять | `postgres:18.6` от 2026-10-21 [В] | PostgreSQL License |
| C. `paradedb/paradedb:pg18` | Postgres + `pg_search` (BM25) + pgvector | ранжирование BM25 из коробки | **AGPL-3.0** для Community-версии [В]; для русского — тот же Snowball-стеммер (`stemmer=russian`) [С], то есть морфология не лучше встроенной; нестандартный образ | `0.26.3-pg18` от 2026-10-22 [В] | AGPL-3.0 (Community), Enterprise — коммерческая [В] |

**Рекомендация: A, Postgres 18 (сейчас 18.6), тег зафиксировать точно** (`0.8.7-pg18-trixie`, не `latest`).
Версия 18 — текущая основная ветка; нужные возможности: `uuidv7()` встроен [В: `select uuidv7()` работает],
новые планировщик и асинхронный ввод-вывод [С]. Срок поддержки 18-й ветки до конца 2030 [Н]. Расширения: `vector`
и `pg_trgm` (для нечёткого поиска по названиям и кратким именам актов — таблица в сотни строк); больше ничего.
`pg_cron`, RUM, ParadeDB не нужны.

**Ловушки Postgres 18, которые я проверил или нашёл:**
- **Сгенерированные столбцы в 18-й версии по умолчанию «виртуальные», и по ним нельзя строить индекс**
  (`indexes on virtual generated columns are not supported`) [В]. Для `tsvector` с GIN нужно явно `STORED`.
  Drizzle пишет `STORED` сам [В: см. сгенерированный SQL в разделе 2].
- **Docker-образ 18 поменял путь данных**: том надо монтировать в `/var/lib/postgresql`, а не в
  `/var/lib/postgresql/data` (иначе после пересоздания контейнера данные пропадут) [С, страница образа на Docker Hub].
- `CREATE EXTENSION vector` требует прав суперпользователя (расширение не «доверенное») — в образе это обычный
  `POSTGRES_USER`; если приложение будет ходить отдельной ролью, расширения создаёт init-скрипт.
- Часовой пояс: хранить `timestamptz` (UTC), «сегодня по Минску» (`NFR-23`) считать в приложении и в cron
  pg-boss (`tz: 'Europe/Minsk'`), а не менять часовой пояс сервера.

**Что могло бы изменить выбор:** если QA-12 покажет, что нужен BM25, а не `ts_rank` — тогда пересмотреть C
(но AGPL и тот же стеммер — слабые аргументы), либо добавить внешнюю лемматизацию (раздел 4).

**Стык.** Монорепо/инфраструктура: сервис `db` в Compose с healthcheck `pg_isready`, том, `shm_size`
(нужен при увеличении `maintenance_work_mem` для построения HNSW), `max_connections` ~50.

**Риски.** Образ `pgvector/pgvector` — сторонний; при смене мажорной версии Postgres нужен `pg_dump`/`pg_upgrade`
(для учебного проекта — просто пересоздать базу из снимков, раздел 6).

**Источники:** https://hub.docker.com/r/pgvector/pgvector/tags, https://hub.docker.com/_/postgres,
https://github.com/pgvector/pgvector, https://github.com/paradedb/paradedb

## 2. ORM / построитель запросов для TypeScript

**Что решаем.** Как код на TypeScript разговаривает с базой. Например, когда в таблицу «Операция» добавляется
поле, нужно, чтобы тип поля обновился и в бэкенде, и в схеме проверки формы на фронте, а миграция создалась
сама; и при этом можно было руками написать хитрый SQL гибридного поиска.

### Что проверено на практике (Drizzle, одна и та же схема на двух версиях)

Схема: таблица `fragment` с `halfvec(1024)`, HNSW-индексом, сгенерированным `tsvector` (`russian`) с GIN,
частичным уникальным индексом, `bytea`, внешним ключом, и схемы Zod из ORM. [В] — прогнано на PGlite (pgvector 0.8.7):
- `drizzle-kit generate` выдал корректный SQL: `halfvec(1024)`, `USING hnsw (... halfvec_cosine_ops) WITH (m=16, ef_construction=64)`,
  `tsvector GENERATED ALWAYS AS (to_tsvector('russian', …)) STORED`, `USING gin`, частичный индекс `WHERE valid_to_snapshot is null`.
- `CREATE EXTENSION vector` Drizzle **не генерирует** — нужна ручная миграция (`drizzle-kit generate --custom`), она должна идти
  **первой**; это работает [В].
- `cosineDistance()`, `sql\`…\``, транзакции с откатом, круговой обмен `bytea`, Zod-схемы (`halfvec` проходит проверку) — всё работает.
- В **стабильной 0.45.4 нет типа `bytea`** (нужен `customType`) [В]; в 1.0-rc он есть.
- `tsvector` во всех версиях — через `customType` (3 строки).

### Сравнение

| Критерий | **Drizzle** (0.45.4 stable от 2026-10-08; **1.0.0-rc.5 от 2026-10-21**) | **Kysely** 0.29.7 (2026-10-17) | **Prisma** 7.10.1 (GA) / 8.0.0-rc.27 | **MikroORM** 7.2.5 / **TypeORM** 1.1.2 |
|---|---|---|---|---|

### Рекомендация

**Drizzle ORM + drizzle-kit, в паре с `pg` (node-postgres).** Почему: единственный из вариантов, где нужные нам вещи
(`halfvec`, HNSW, `tsvector`+GIN, частичные индексы, схемы Zod) описываются и мигрируются без обходов, а сложный SQL
(гибридный поиск) пишется рядом тем же инструментом. Это снимает риск «нужна ручная правка миграции для каждой
фичи поиска». Kysely — хороший запасной вариант, если схема-в-коде не понравится; Prisma 7 заставит писать на сыром SQL
как раз самую важную часть системы, Prisma 8 ещё RC.

**Какую версию: Drizzle 1.0.0-rc.5, зафиксировать точно (`"drizzle-orm": "1.0.0-rc.5"`), запасной путь — 0.45.4.**
Аргументы за RC: проект только начинается, переход 0.45→1.0 потом включает перепись реляционных запросов
(Relations v2) и `drizzle-kit up`; в 1.0 встроены Zod и `bytea`; на моей схеме RC сгенерировал тот же SQL и прошёл
те же проверки. Риск: RC может ещё меняться. **Смягчение:** писать запросы построителем (`select/insert/update` и
`sql\`\``), а не реляционным API `db.query.*` (оно как раз различается в версиях) — тогда откат/переход
почти бесплатный.

**Что могло бы изменить выбор:** если до начала кода выйдет Drizzle 1.0 stable — берём его; если RC начнёт ломаться
— 0.45.4 + `drizzle-zod` 0.8.3.

**Стык.**
- Бэкенд-фреймворк: один экземпляр `db` и передача `tx` через вызовы (чтобы «операция + напоминание + задача
  pg-boss» были атомарны).
- Фронтенд/общий пакет схем: схемы Zod из Drizzle использовать как **основу** DTO, но не отдавать их наружу как есть
  (в них `embedding`, `rawGz` и т. п.); отдельные «публичные» схемы строятся через `.pick()/.omit()`.
- Drizzle не должен видеть таблицы pg-boss (`schemaFilter: ['public']`).

**Риски / вопросы.** RC-статус (см. выше); `bytea` отдаёт `Buffer` или `Uint8Array` в зависимости от драйвера [В]
(в продакшене всегда `pg`). **Вопрос пользователю:** согласны начать на 1.0 RC с точной фиксацией версии?

## 3. Векторный поиск (pgvector)

**Что решаем.** Как хранить и быстро искать «смысловые» векторы 20–30 тыс. фрагментов законов, и как не
привязаться навсегда к одной модели эмбеддингов (`LAW-23`). Например, вопрос «можно ли вернуть пылесос» должен
находить ст. 28 Закона о защите прав потребителей, даже если в вопросе нет слова «возврат» в той же форме.

### Решения

| Решение | Выбор | Почему |
|---|---|---|
| Тип | **`halfvec`** (2 байта на число) | вдвое меньше: 30 тыс. × 1024 = ~61 МБ против ~123 МБ [расчёт]; индексируется до **4000** измерений (у `vector` — до 2000) [В: проверено ошибками при создании индекса]; потеря качества на нормированных векторах пренебрежимо мала [Н — проверить на QA-12] |
| Индекс | **HNSW** (`m=16`, `ef_construction=64` — значения по умолчанию) | лучше компромисс скорость/полнота, строится на пустой таблице, поддерживает вставки без перестройки; IVFFlat строится быстрее, но хуже по запросам и требует данных до создания [С, README pgvector] |
| Расстояние | косинусное (`halfvec_cosine_ops`, оператор `<=>`) | не зависит от нормировки модели |
| Запрос | `SET LOCAL hnsw.ef_search = 100` (по умолчанию 40, максимум 1000 [В]); `SET LOCAL hnsw.iterative_scan = relaxed_order` | итеративное сканирование (pgvector ≥0.8) не даёт фильтру «только действующие акты» обнулить выдачу [С] |
| Без индекса? | на 30 тыс. строк точный перебор, вероятно, 20–80 мс [Н, не измерено] — **оставить как режим для эталонных замеров (100% полнота)** | HNSW — приближённый; для QA-12 нужен эталон |
| Модели | **таблица `embedding_model`** (id, имя, версия, размерность, префиксы запроса/документа, активна) и **отдельная таблица `fragment_embedding`** (`fragment_version_id`, `model_id`, `embedding halfvec`) | смена модели = фоновое задание, пока работает старая; потом переключили флаг `active` и удалили старые векторы |
| Индекс на несколько моделей | **частичный индекс по выражению для каждой модели**: `CREATE INDEX … USING hnsw ((embedding::halfvec(1024)) halfvec_cosine_ops) WHERE model_id = 1` | столбец без фиксированной размерности нельзя индексировать напрямую; частичный индекс с приведением типа создаётся, планировщик им пользуется (запрос должен содержать то же выражение и условие) [В: `explain` показал `Index Scan using emb_m1`] |
| Какие версии хранят векторы | **только текущие версии фрагментов**; при закрытии версии её вектор удаляется | история нужна для цитат (текст), а не для поиска → индекс не пухнет, фильтр `is_current` для векторов не нужен |

**Проверенные цифры [В, малая выборка, PGlite]:** HNSW-индекс на 3 000 векторов `halfvec(1024)` занял 8 МБ
(~2,7 КБ на вектор) → на 30 тыс. ожидается **~80 МБ** (линейная оценка [Н]); итого векторы + индекс ~140 МБ —
укладывается в «< 1 ГБ» из `LAW-23`. Время построения (13 с на 3 000) в WebAssembly **не показательно**; на нативном
Postgres должно быть на порядок быстрее [Н]. Размерность 768 против 1024 против 1536 — вопрос модели (раздел «Стык»), для
`halfvec` все варианты в пределах индексируемого.

**Рекомендованная настройка (проверить в `make bench`):** `maintenance_work_mem` 1–2 ГБ на время построения,
`max_parallel_maintenance_workers` 4; в Compose поднять `shm_size`.

**Что могло бы изменить выбор:** если замер покажет, что HNSW-полнота хуже 95% на эталонных вопросах — поднять
`ef_search`/`m` или вообще не строить индекс (перебор на 30 тыс. строк).

**Стык.**
- **Локальный инференс (соседняя область):** нужен единый интерфейс `embed(texts[], kind: 'query' | 'passage') →
  { model: { name, version, dims }, vectors }`, пакетная обработка, ограничение размера пачки; префиксы запроса/документа
  хранятся в `embedding_model` (у разных моделей разные правила: у части нужна инструкция к запросу).
  Для тестов — детерминированный «фальшивый» эмбеддер на хэшах.
- **Задачи (раздел 5):** очередь `law.embed` пачками по 32–64 фрагмента, прогресс в таблице запусков.

**Риски.** Главный — производительность эмбеддингов на CPU/Arc (в `legal-corpus-strategy.md` оценка 1,7–8 ч на всё,
без замера [Н]); задача идёт ночью и возобновляется. Второй — фильтры при ANN: см. итеративное сканирование.

**Источники:** https://github.com/pgvector/pgvector (README: HNSW/IVFFlat, `halfvec`, `hnsw.iterative_scan`, пределы размерности),
эксперименты `vec1.mjs`, `vec2.mjs`, `vec3.mjs` в scratchpad.

## 4. Полнотекстовый поиск на русском и гибридный запрос (`LAW-21`)

**Что решаем.** Как искать слова в тексте законов с учётом падежей и как склеить результат с векторным поиском.
Например, пользователь пишет «налоговый вычет на детей», а в кодексе «стандартные налоговые вычеты» и «детей» —
поиск должен это связать, а «ст. 209 НК» — открыть ровно статью 209.

### Что я измерил на реальном тексте (Postgres 18.4, 24 220 фрагментов) [В]

| Показатель | `russian` (Snowball, встроенный) | `ru_h` (словарь Hunspell из Firefox + Snowball как запасной) |
|---|---|---|
| Сборка `tsvector` для 24 тыс. строк | 6,5 с | **32,5 с** (в 5 раз дольше) |
| Построение GIN | 0,56 с | 0,66 с |
| Размер GIN | 5,5 МБ (занижено: тексты — копии, настоящий индекс ~30–80 МБ [Н]) | 5,8 МБ |
| Первый запрос в новом соединении | 3 мс | **254 мс** (словарь грузится в каждое соединение) |
| Совпадение 75 пар «форма в тексте ~ форма в запросе» (падежи, глаголы; юридическая лексика, список мой) | **62 из 75 (83%)** | **67 из 75 (89%)**; оба вместе — 68 (91%) |
| Запрос из нескольких слов через ИЛИ, ранжирование всех совпавших (~10 тыс. строк) | 115–150 мс | 400 мс |
| Запрос через И (строгий) | 1 мс | 1 мс |
| Точное обращение «статья 209 НК» (btree по акту и номеру статьи) | 0,6 мс | — |

**Что именно ломается (примеры, [В]):**
- Snowball: `кредит` → `кред`, а `кредита` → `кредит` — **слова «кредит» и «кредита» не находят друг друга**;
  `продавец` ≠ `продавца` (беглая гласная); `ребёнок` ≠ `ребёнка`; `вернул` ≠ `вернуть` (`вернул`/`вернут`).
- Hunspell: приводит к начальной форме (`купил`→`купить`, `кредита`→`кредит`), но слова вне словаря остаются
  как есть и **расходятся с запросом** (`алименты` ≠ `алиментов`); `детей` не связано с `ребёнок`; для `ё` нужна
  нормализация вручную.
- Ни тот ни другой не связывают однокоренные разные части речи (`налог` — `налоговый`, `возврат` — `вернуть`):
  это работа курируемого словаря «бытовое → юридическое» (`LAW-21`, шаг 2) и векторов.
- **`ё`→`е`** надо заменять и в тексте, и в запросе (`replace(x, 'ё', 'е')`) — сделал в замерах.
- Длинный разговорный запрос через ИЛИ приносит мусор («мочь», «день», «10» из ТК вместо Закона о правах потребителей)
  — поэтому **в инструмент поиска агент должен передавать ключевые слова, а не пересказ вопроса** (стык с агентом).

### Рекомендация

**A на старте** (`russian` + `ё→е` + расширение запроса словарём из админки + RRF с векторами) — достаточно, чтобы
пройти `LAW-21`, и закрывает пробелы ровно в тех местах, где вектора сильны (бытовые формулировки). Гибрид
вообще не требует от FTS идеальной морфологии: ранги склеиваются.

**Двухэтапный FTS-запрос:** сначала строгий (`И`, 1 мс), и только если нашлось меньше N — ослабленный (`ИЛИ`,
115–150 мс). Это убирает основную стоимость.

**Критерий перехода на E (или B):** если на эталонном наборе QA-12 доля «нужная статья в топ-10 FTS-канала» ниже
порога, который выберете вы (я бы взял 80%). Тогда добавляется столбец `lemmas`, а схема не меняется — это
«план Б» без переделки. B (Hunspell) я бы не брал: выигрыш мал, а стоимость в пуле соединений реальна.
ParadeDB и внешние поисковики — **не оправданы** на 25–30 тыс. фрагментов.

### Точные обращения («ст. 210 НК»)

Это не полнотекстовый поиск: `act_alias` (краткие имена, правятся в админке, GIN `pg_trgm` по нескольким сотням строк
для опечаток) → `act_id` → поиск по `(act_id, article_no)` btree. **Номера статей с надстрочным индексом** — в HTML pravo.by это
`<p class="article" id="216/1">Статья 216<sup>1</sup>. …` [В, НК Особенная часть]; наивное удаление тегов даёт «Статья 2161».
Нормализованный ключ — `216.1` (`article_no text`), в тексте показываем «216¹». Это закрывает открытый вопрос **O11** из SPEC.

### Гибридный запрос через RRF

Проверен в упрощённой форме на PGlite (Postgres 18.6 + pgvector 0.8.7): индекс HNSW использовался, ранги склеивались.
Ниже — вариант под предлагаемую схему раздела 6 (имена таблиц мои; полностью на реальной схеме не гонял [Н]):

```sql
-- параметры: $1 вектор запроса (halfvec), $2 текст запроса (ключевые слова + расширения словаря),
--            $3 id активной модели эмбеддингов
SET LOCAL hnsw.ef_search = 100;
SET LOCAL hnsw.iterative_scan = relaxed_order;

WITH q AS (
  SELECT $1::halfvec(1024) AS qv,
         replace(plainto_tsquery('russian', replace($2, 'ё', 'е'))::text, ' & ', ' | ')::tsquery AS tq
),
fts AS (
  SELECT fv.id,
         row_number() OVER (ORDER BY ts_rank_cd(fv.ts, q.tq, 32) DESC) AS rnk
  FROM fragment_version fv
  JOIN act a ON a.id = fv.act_id
  CROSS JOIN q
  WHERE fv.is_current AND a.status = 'active' AND fv.ts @@ q.tq
  ORDER BY ts_rank_cd(fv.ts, q.tq, 32) DESC
  LIMIT 40
),
vec AS (
  SELECT fe.fragment_version_id AS id,
         row_number() OVER (ORDER BY fe.embedding::halfvec(1024) <=> q.qv) AS rnk
  FROM fragment_embedding fe
  CROSS JOIN q
  WHERE fe.model_id = $3
  ORDER BY fe.embedding::halfvec(1024) <=> q.qv
  LIMIT 40
)
SELECT fv.id, fv.act_id, fv.path, fv.text,
       coalesce(1.0 / (60 + fts.rnk), 0) + coalesce(1.0 / (60 + vec.rnk), 0) AS score,
       fts.rnk AS fts_rank, vec.rnk AS vec_rank
FROM fts
FULL JOIN vec ON vec.id = fts.id
JOIN fragment_version fv ON fv.id = coalesce(fts.id, vec.id)
JOIN act a ON a.id = fv.act_id
WHERE fv.is_current AND a.status = 'active'          -- фильтр для векторной ветки (где его нет внутри)
ORDER BY score DESC
LIMIT 10;
```
`k = 60` — общепринятое значение RRF; пороги и веса каналов подбираются на QA-12. Расширение «по графу ссылок»
(`LAW-21`, шаг 4) — отдельным запросом по таблице `fragment_ref`, в пределах бюджета токенов.

**Стык.** Агент: инструмент `search_law` получает **ключевые слова**, при желании `act`/`ref`; возвращает 6–10
фрагментов с `fragment_version_id`, путём, датой снимка и предупреждениями (`LAW-32`). Словарь «бытовое → юридическое»
и краткие имена — таблицы в БД с редакторами в админке; расширение запроса делает приложение до SQL.

**Риски.** Качество FTS-канала до QA-12 не известно (мой тест из 75 пар — мой набор слов, а не эталонные вопросы); вывод о 83% против 89%
— ориентир, а не метрика продукта.

**Источники:** https://www.postgresql.org/docs/current/textsearch-dictionaries.html, https://github.com/paradedb/paradedb,
https://www.meilisearch.com/blog/enterprise-license, эксперименты `fts1–fts6.mjs` и `vec1–vec3.mjs` в scratchpad; HTML pravo.by
(`/document/?guid=3871&p0=Hk0900071`).

## 5. Фоновые задачи и расписание

**Что решаем.** Чем запускать ночную проверку законов, векторизацию, итоги недели и напоминания — так, чтобы после
выключенного на выходные компьютера всё само догналось (`NFR-22`), загрузчик ходил к pravo.by ровно по одному запросу
в 3–5 секунд (`LAW-35`), а администратор видел прогресс.

### Что я проверил на настоящем Postgres 18.4 (pg-boss 12.38.0) [В]

| Проверка | Результат |
|---|---|
| **Догон пропущенного**: два расписания «каждую минуту», у одного `missed: 'once'`; остановил процесс на 3 мин 10 с и запустил заново | у `missed: 'once'` — **один** догоняющий запуск сразу после старта (три пропущенных срока → один запуск), у обычного — только текущий срок. Состояние хранится в БД, переживает перезапуск |
| Повторы с нарастающей паузой (`retryDelay: 2, retryBackoff: true`) | попытки на 0,5 / 4,5 / 10 / 24,5 с — рост примерно вдвое с разбросом |
| Дедупликация (`policy: 'short'` + `singletonKey`) | второй `send` с тем же ключом вернул `null`, другой ключ — принят |
| Приоритет и отложенный запуск (`startAfter`) | высокий приоритет вышел первым; отложенный — ровно через 4 с |
| **Падение рабочего процесса** (убил `SIGKILL` во время задачи, `heartbeatSeconds: 10`, `superviseIntervalSeconds: 10`) | задача подхвачена другим процессом через ~14 с с `retryCount = 1`. С интервалами по умолчанию за 45 с **не** восстановилась — надо задать `superviseIntervalSeconds`/`monitorIntervalSeconds` явно |
| **Транзакционная постановка**: `boss.send(…, { db: fromDrizzle(tx, sql) })` | commit → строка + задача; rollback → ни строки, ни задачи |

### Рекомендация

**pg-boss, отдельный брокер не нужен.** Нагрузка — сотни задач в сутки; всё требуемое (`NFR-22`, повторы,
приоритеты, отложенные, видимость) есть в Postgres, который уже обязателен. Бонус: **постановка задачи в той же
транзакции, что и запись** (проверено) — нельзя потерять «векторизовать эту версию фрагмента» при сбое.

**Как закрыть то, чего нет в pg-boss:**

| Требование | Решение |
|---|---|
| Догон после выключения (`NFR-22`) | `schedule(..., { missed: 'once', tz: 'Europe/Minsk' })` [В] **+ «водяной знак»** в доменной таблице: задача сама вычисляет, за какие даты работать (`LAW-12`: с последнего обработанного дня по вчера, не более 30). `once` не сообщает, *сколько* пропущено |
| Ночное окно (`LAW-35`) | cron ставит запуск на выбранное время *внутри* окна; плановые массовые задачи проверяют окно и, если вне окна и это не «разрешённый в любое время» вид, откладывают себя `startAfter` на начало окна. Догон, ручные кнопки, `LAW-09` — без проверки окна |
| Один поток, пауза 3–5 с (`LAW-35`) | пауза нужна **между HTTP-запросами**, а не между задачами (проверка одного акта = несколько запросов). Делается в модуле загрузчика: глобальный мьютекс + случайная пауза 3–5 с + проверка robots.txt; плюс запуск очередей `law.*` только в **одном рабочем процессе**, `localConcurrency: 1` |
| Повторы по `LAW-38` (30 с, 2 мин, 10 мин) | лесенка в коде обработчика (`startAfter` по номеру попытки из данных задачи); экспоненциальные `retryBackoff` pg-boss дают другие паузы. 403/429 или >20% ошибок → флаг `law_fetch_paused_until` в настройках, обработчики его проверяют |
| Прогресс (векторизация, загрузка каталога) | своя таблица `background_job_run` (вид, статус, `done/total`, водяной знак, ошибка, время) — это сущность «Фоновая задача» из §5 SPEC; обработчик обновляет не чаще раза в секунду; админка опрашивает раз в 2 с (при желании `LISTEN/NOTIFY`) |
| Приоритеты | действия пользователя (чек, `LAW-09`, ручные кнопки) — `priority: 10`; ночные — 0; фоновая векторизация — −1 |
| Видимость в админке (`ADM-60`, `OBS-07`) | собственная страница читает `background_job_run` + API pg-boss (`getQueues`, `getSchedules`, `findJobs`); `@pg-boss/dashboard` — только как инструмент разработчика |
| Отложенные напоминания (`NOTIF`, `CAL`) | **не** по задаче на каждое напоминание, а таблица `reminder(due_at, sent_at)` + cron «каждую минуту» с `missed: 'once'`: обработчик берёт всё с `due_at <= now() AND sent_at IS NULL`. Правка/удаление события не требует отмены задач, догон после выключения получается сам |
| «Итоги недели» | cron по понедельникам, `missed: 'once'`, водяной знак — последняя неделя с готовым итогом |

**Раскладка очередей (набросок):** `law.daily-check` (cron в окне, `missed: once`) → порождает `law.check-act`

`law.weekly-demand-digest`, `law.monthly-dept-pages`; `law.effective-date-check` (отложенные на день после даты
вступления); `law.embed` (пачки 32–64), `law.reindex-model`; `reminders.tick` (раз в минуту); `report.weekly`;
`import.statement`, `receipt.recognize`, `eval.run`.

**Что могло бы изменить выбор:** появление сотен задач в секунду или нескольких серверов — тогда BullMQ; сложные
многодневные процессы с компенсациями — Temporal. Для «Кошта» ни то ни другое не предвидится.

**Стык.**
- **Бэкенд:** два режима одного кода — API-процесс (только `send`, `start()` без `work`) и рабочий процесс (`work`, cron). В локальном
  запуске можно в одном процессе. Схема `pgboss` создаётся и мигрируется самим pg-boss при `start()` — нужны права на DDL; Drizzle её не трогает.
- **Приватность (P4, `OBS-04`):** payload задач хранится открытым текстом в таблице `pgboss.job` (по умолчанию неделя после завершения) —
  **в него класть только идентификаторы**, не тексты вопросов, суммы и т. п.
- **Админка:** эндпоинты статуса задач и «Проверить сейчас» (ставят задачу вне окна).
- **Инференс:** `law.embed` вызывает сервис эмбеддингов; недоступность сервиса = повтор с паузой.

**Риски.** Быстрая смена мажорных версий pg-boss — **фиксировать версию** и читать журнал изменений при обновлении; не доверять
значениям интервалов по умолчанию (см. восстановление после падения — задать явно); нет встроенного прогресса. **Вопрос
пользователю:** допустимо ли, что при долгом выключении «итоги недели» придут одним уведомлением за последнюю неделю, а не за каждую пропущенную?

## 6. Версионирование фрагментов и снимков (`LAW-31`)

**Что решаем.** Как хранить редакции законов, чтобы (а) новая редакция создавала версии только у изменённых статей,
(б) цитата в ответе всегда указывала на конкретную версию текста, (в) после исправления парсера всё пересобиралось
без обращения к pravo.by. Например, изменили одну статью НК: должна появиться ровно одна новая версия и один новый вектор.

### Модель (наброски таблиц; типы — Postgres 18)

```
act              — каталог (LAW-07): id uuidv7, pravo_id UNIQUE, kind, number, title, status, has_text, level (card|index),
                   source, mode, theme, epk_rubrics text[], text_checked_at, ...
act_alias        — краткие имена (НК, ЗоЗПП) — правятся в админке; GIN pg_trgm по alias
act_snapshot     — снимок: id, act_id, fetched_at, sha256, content_length, parser_version,
                   parse_status (ok|quarantined), header_amendments text[], card_amendments text[],
                   raw_gz bytea (STORAGE EXTERNAL)   -- отдельная таблица, чтобы основные не пухли
fragment         — «место» в структуре: id, act_id, path (art=209/p=1/pp=1.1), article_no ('216.1'), UNIQUE(act_id, path)
fragment_version — версия текста: id, fragment_id, text, breadcrumb, heading, kind, status
                   (active|excluded|removed), text_hash, first_snapshot_id, last_snapshot_id NULL,
                   is_current boolean, ts tsvector GENERATED ... STORED
fragment_embedding(fragment_version_id, model_id, embedding halfvec)   -- только для текущих версий (раздел 3)
fragment_ref     — исходящие ссылки (внутренние → fragment, внешние → act)
citation         — message_id, fragment_version_id, quote_start, quote_end   (LEGAL-03, CHAT-10)
law_request_log  — URL, код, байты, мс, время (хранить ~90 дней)
amendment_queue  — act_id, amending_pravo_id, effective_date, affected_articles, статус (LAW-32)
```

**Индексы (все названы по смыслу, создаются Drizzle, кроме HNSW по выражению):**
- `fragment_version`: **частичный GIN по `ts` `WHERE is_current`** (поиск не видит историю; индекс меньше);
  частичный уникальный `(fragment_id) WHERE is_current`; btree `(fragment_id, first_snapshot_id)`;
  `(text_hash)` для распознавания перенумерации (`LAW-31`: «перенесён» = тот же хэш на другом пути);
  btree по `fragment(act_id, article_no)` для «ст. 210 НК».
- `act_snapshot`: `(act_id, fetched_at DESC)`, `UNIQUE(act_id, sha256)`.
- `law_request_log`: по времени.

**Алгоритм новой редакции (внутри одной транзакции):** загрузили → посчитали `sha256`; совпал с последним — только обновить
`text_checked_at`, снимок **не** сохранять (так история не растёт); иначе разобрать → сравнить с текущими версиями
по `path` и `text_hash` → неизменённые продлить, изменённые закрыть (`is_current=false`, `last_snapshot_id`) и создать новую, пропавшие — `removed`,
новые — `active`; векторизацию изменённых поставить в `law.embed` **той же транзакцией** (`fromDrizzle`, проверено);
вектор закрытой версии удалить. Карантин (`LAW-39`): `parse_status='quarantined'`, версии не применять.

**Сырой HTML.** Измерено на реальных страницах [В]: НК Особенная часть — 5,17 МБ HTML (3,25 млн знаков) →
gzip **0,66 МБ**, xz 0,38 МБ, внутреннее сжатие TOAST (`pglz`) всего 1,04 МБ; три акта: 6,35 МБ → 0,84 МБ (gzip). Выбор:
**gzip (или zstd) на стороне приложения, хранить в `bytea` с `STORAGE EXTERNAL`** (чтобы Postgres не пытался
сжимать повторно). Альтернативы: `text` с `lz4`-сжатием TOAST (в моей встроенной сборке lz4 нет, в официальных образах,
по-видимому, есть [Н]) или файлы на томе (две системы хранения, рассинхронизация, отдельная копия при резервном копировании) —
**не берём**: один `pg_dump` = полная копия. Расчёт для 200 актов при сохранении только изменившихся снимков — десятки МБ в год [Н].

**Оценка общего объёма базы законов (30 тыс. фрагментов) [Н/расчёт]:** текст ~25–50 МБ; `tsvector` ~40 МБ; GIN 30–80 МБ;
векторы `halfvec(1024)` ~61 МБ + HNSW ~80 МБ; снимки 10–50 МБ → **≈ 250–350 МБ**, в рамках «< 1 ГБ» (`LAW-23`).

**Открытое проектное решение (для ADR):** пересборка из сохранённого HTML после исправления парсера. Если путь (`path`) не меняется —
это «тот же снимок, перепарсили»: заменить текущие версии на месте без записи в историю; если схема путей меняется
(редко) — потребуется миграция `fragment.path`. Нужно решить, как отличать «исправление парсера» от «изменение закона»
(предложение: `parser_version` в снимке и режим `reparse`, не создающий новых `first_snapshot_id`).

**Что могло бы изменить выбор:** если истории придётся хранить много (десятки редакций на акт) — вынести `raw_gz` в
файловое хранилище; для курсового MVP не нужно.

**Стык.** Агент/чат: цитата хранит `fragment_version_id` и смещения; «статья изменилась после ответа» —
запрос «у версии есть преемник» (`is_current=false`). LEGAL: проверка дословности идёт по `fragment_version.text` (без хлебной крошки,
которая хранится отдельно). TAX (`LAW-33`): ставка ссылается на `fragment_id`; после новой версии сравнение чисел.

**Источники:** `legal-corpus-strategy.md` §3–4; эксперименты `toast.mjs`, `chunk.py` в scratchpad; разметка pravo.by
(`<p class="article" id="216/1">`), https://www.postgresql.org/docs/current/storage-toast.html.

## 7. Демо-данные, сиды, миграции, тесты на реальной базе

**Что решаем.** Как поднять чистую базу, наполнить её воспроизводимым демо, и как тестировать код на настоящем
Postgres, не замедляя разработку. Например, кнопка «Пересоздать демо-данные» (`DEMO-03`) и тест «изменённая статья
даёт ровно одну новую версию» должны использовать один и тот же слой данных.

### Миграции (dev/test)
- Источник правды — схема Drizzle (`schema/*.ts`), `drizzle-kit generate` → SQL в репозиторий, **обзор диффа
  миграции обязателен** (индексы по выражению и HNSW иногда пишутся руками).
- **Первая миграция — ручная** (`generate --custom`): `CREATE EXTENSION IF NOT EXISTS vector; CREATE EXTENSION IF NOT EXISTS pg_trgm;` [В].
- Применение: программный `migrate()` при старте API/воркера в dev и тестах; `make db-migrate` — тот же код.
- Частичные HNSW-индексы по выражению для конкретной модели эмбеддингов создаёт **задание смены модели** (`CREATE INDEX CONCURRENTLY`), а не
  `drizzle-kit`: размерность заранее неизвестна (раздел 3).
- Откатов нет (Drizzle их не генерирует) — для учебного проекта «сброс и пересоздание» (`make db-reset`) вместо down-миграций.

### Демо-данные
- Сид — **TypeScript-функция** (не SQL-дамп), использующая тот же слой данных: идемпотентный «удалить демо-домохозяйство и
  создать заново» в одной транзакции; её вызывают `make demo-reset` и кнопка в админке (`DEMO-03`).
- Воспроизводимость и привязка к дате (`DEMO-02`): `@faker-js/faker` 10.6.0 с `fakerRU.seed(42)` и
  `setDefaultRefDate(<сегодня>)` — проверено: одинаковый seed даёт одинаковые данные, относительные даты считаются от заданной [В].
  Белорусских контрагентов (Евроопт, Гиппо, Корона…) — **своя таблица-справочник**, faker только для чисел и распределений.
- `drizzle-seed` 0.3.1 генерирует данные по схеме, но «правдоподобие» (зарплата + аванс, один лимит превышен, один на 80%)
  всё равно придётся описывать вручную — не нужен [Н].
- **Законы в демо:** оффлайн-режим показа (без интернета) можно обеспечить заранее разобранным снимком базы законов (`pg_dump` таблиц
  `act*`, `fragment*`) — **вопрос пользователю**, нужен ли такой «чемоданчик» (векторы привязаны к модели, придётся
  хранить дамп вместе с её версией).

### Тесты на реальном Postgres

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Сервер из Compose (`make db-up`) + шаблонная БД + БД на каждый файл тестов** | один раз применить миграции в `kosht_tmpl`, на каждый тестовый файл `CREATE DATABASE test_<id> TEMPLATE kosht_tmpl` | клон схемы из 60 таблиц **~20 мс** (медиана, 10 замеров) [В]; те же образ и версия, что в разработке; параллельность по файлам; без лишних зависимостей | нужен запущенный контейнер БД; тесты не должны удалять не свои БД (защита по префиксу `test_`) |
| B. Testcontainers (`@testcontainers/postgresql` 12.2.1) | контейнер на прогон тестов | полностью самодостаточно, подходит будущему CI | нужен доступ к Docker из пользователя тестов (на этой машине сейчас нет — Docker Desktop не запущен, а к системному сокету нужна группа `docker` [В]), +секунды на старт, дополнительный служебный контейнер |
| C. PGlite (`@electric-sql/pglite` 0.5.11: Postgres 18.6 + pgvector 0.8.7 в процессе) | БД без Docker | мгновенный старт; Drizzle работает (`drizzle-orm/pglite`: миграции, `halfvec`, `bytea`, откат транзакции — проверено [В]); pg-boss умеет `pglite`-бэкенд [В: адаптер в пакете] | WebAssembly 32-бит: **нельзя** судить о скорости и качестве поиска; нет Hunspell; одно соединение, отличия от продакшена |

**Рекомендация: A** (один Postgres на всё), с запасным **B**, если появится CI. PGlite — не вводить (две базы в тестах — «лишнее»),
оставить как аварийный вариант «нет Docker». Тесты уровней: (1) чистая логика без базы (большинство, `NFR-11`);
(2) интеграционные тесты репозиториев и SQL гибридного поиска на реальной базе с **маленькими фикстурами** (3–5 сохранённых страниц актов,
детерминированный «хэш-эмбеддер» вместо модели) — проверяют RRF, фильтр «только текущие и действующие», «одна изменённая статья → одна версия»;
(3) качество поиска на корпусе — **только eval** (`QA-12`), не в обычных тестах. Если нужен запуск вообще без контейнеров для приложения —
процессы приложения на хосте, а база всё равно в контейнере (`make db-up`); нативная установка `postgresql-18` + `pgvector` из репозитория PGDG возможна [С, не проверял].

**Источники:** https://orm.drizzle.team/docs (migrations, custom migrations), https://node.testcontainers.org/modules/postgresql/,
https://pglite.dev, https://fakerjs.dev/guide/randomizer; эксперименты `tmpl.mjs`, drizzle-проекты `drz-latest`/`drz-rc` в scratchpad.
