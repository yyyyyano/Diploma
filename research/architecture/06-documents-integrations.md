## 0. Главное одним абзацем

Все семь задач решаются **на Node.js/TypeScript без Python**, бесплатными библиотеками, и ничего не требует
сети при работе (кроме самих внешних сервисов). Самые важные находки, которых нет в SPEC и которые меняют
выбор:

1. **Excel с диаграммами:** популярный ExcelJS диаграммы писать **не умеет**; бесплатный рабочий путь —
   `wasm-xlsxwriter` (обёртка Rust-библиотеки `rust_xlsxwriter`). Я собрал файл с тремя листами,
   `SUMIFS` по целым столбцам, столбчатой и круговой диаграммами, закреплённой шапкой и фильтром, открыл его
   в LibreOffice и в openpyxl, а формулы пересчитал независимым движком — итог изменился после правки суммы
   (КП из `XLS-03` выполнимо) **[В]**. Важная ловушка: **у каждой формулы надо записать «кэшированный результат»**,
   иначе просмотрщики (и Excel в «защищённом просмотре») покажут нули **[В]**.
2. **Фото с iPhone (HEIC):** `sharp` с его встроенной библиотекой **HEIC не читает** (проверил: ошибка «HEVC decoder
   not built in») **[В]**; нужен отдельный `heic-decode` (12 Мп — 2,7 с, поэтому только в фоне).
3. **QR-код:** `zxing-wasm` — быстрее и надёжнее остальных, но по умолчанию **качает .wasm-файл с CDN jsDelivr**
   — это нарушает «всё локально»; лечится одной настройкой (проверил, работает без сети) **[В]**. `jsQR` на фото
   12 Мп думает от 1 до 16 с — картинку всегда надо сначала уменьшать **[В]**.
4. **Выписки PDF:** готовые «извлекатели таблиц» на тестовой выписке **не нашли таблицу** (`pdf-parse getTable` — 0 таблиц,
   `pdfplumber` по линиям — ничего) **[В]**; рабочий путь — достать из PDF текст **с координатами** (`pdfjs-dist`,
   то есть `unpdf`) и самим собрать строки и колонки: 70 из 70 операций, баланс сходится **[В]**. Модель нужна
   **только чтобы подсказать, какая колонка что значит** (и для сканов), а не чтобы читать все строки.
5. **pravo.by:** `robots-parser` правильно понял все 16 проверенных адресов, включая шаблоны `*` и `$`
   и порядок `Allow`/`Disallow` **[В]**. Лёгкая проверка «текст изменился?» через `HEAD` работает **только если
   не просить сжатие**: с `Accept-Encoding: gzip` сервер не присылает `Content-Length` **[В]**.
6. **Telegram:** grammY (Telegraf не обновлялся с февраля 2024). В Bot API появился метод
   **`sendMessageDraft`** — «потоковый» вывод ответа в личном чате — как раз для `NFR-21` в боте **[В]**.
7. **НБРБ:** курс масштабируется (`Cur_Scale`: у RUB 100 единиц, у AMD 1000) — без деления на масштаб суммы
   в BYN будут неверны **[В]**; запрос диапазона дольше 365 дней **молча обрезается** **[В]**.

## 1. Разбор банковских выписок PDF (`STMT-04`, `STMT-05`, `STMT-06`)

### 1.1 Что решаем и почему важно

Выписка — главный источник операций: Беларусбанк и Приорбанк отдают её в основном как PDF (SPEC §9.7). PDF — это
не таблица, а «набор слов с координатами на странице»: программа должна сама понять, что слова на одной высоте —
одна строка, а слова в одном «столбце» по горизонтали — одна колонка. Например, строка «02.09.2026 …
ZACHISLENIE ZARPLATY … 2 800,00 BYN 4 255,55» в PDF — это десяток кусочков текста, а длинное описание ещё и
переносится на вторую строку (и может оказаться **выше** строки с датой — я это видел).

**Честная оговорка:** реальных выписок в `samples/` нет (SPEC §11, O1). Все числа ниже — на синтетической выписке:
3 страницы, 70 операций, перенос длинных описаний, таблица с рамками, сделана через LibreOffice
(`pdf/stmt.pdf`). Настоящие банковские PDF (JasperReports, iText, 1С, зашифрованные, сканы) могут вести себя иначе.

### 1.3 Что я проверил руками (вариант A)

- `pdfjs-dist` в Node нужно подключать **из `legacy`-сборки** (`pdfjs-dist/legacy/build/pdf.mjs`): современная сборка
  падает на Node 24.21 с ошибкой `hashOriginal.toHex is not a function` **[В]**. `unpdf` уже собирает правильно.
- Алгоритм (в `pdf/t-table.mjs`): слова → строки по близости `y` (допуск 3 пункта) → колонки по `x` первой строки
  с датой → строки без даты в колонке описания приклеиваются к **ближайшей по вертикали** строке с датой (иначе
  потеряем перенос, лежащий выше даты) → суммы и остатки разбираются отдельно.
- Результат: **70 из 70 операций найдены, дата/сумма/остаток верны во всех 70, описание верно в 69**; цепочка
  «предыдущий остаток + сумма = новый остаток» **не нарушена ни разу** **[В]**. Единственная ошибка — перенос строки
  «BY» на границе страниц потерялся. Это важный урок: контроль по остаткам ловит ошибки сумм, но **не ловит потерю
  слов в описании** — нужны тесты на образцы.
- Сканы: у PDF без текстового слоя `getTextContent()` вернёт пусто; это надо ловить («на странице < N символов» →
  «похоже на скан») **[С]**.

### 1.4 Рекомендация и когда нужна модель

**Вариант A** (`unpdf` + собственная сборка таблицы), оформленный как маленький пакет `statement-pdf` с двумя слоями:

1. **Слой «геометрия»** (общий для всех банков): слова с координатами → строки → ячейки.
2. **Слой «банк»**: *точный разборщик* (`STMT-05`, по образцу из `samples/`) знает колонки наизусть; *универсальный*
   (`STMT-04`) ищет шапку по словарю («Дата», «Сумма», «Описание/Назначение», «Остаток», «Валюта», «Приход/Расход»,
   Debit/Credit) и строки по шаблонам даты и суммы.

**Модель — только в двух случаях** и как можно меньше:
- шапку/колонки не удалось определить уверенно → в модель уходит **маскированный кусок** (шапка + 10–15 строк, номера
  карт и ФИО замаскированы по правилам `PRIV`), она возвращает **только JSON «колонка → смысл + формат даты и чисел +
  знак суммы»**; дальше все сотни строк извлекает **код**, а не модель. Это дёшево по лимитам API (`R29`-логика)
  и безопасно для приватности;
- PDF — скан/фото: страницы → изображения → модель с изображениями (та же цепочка провайдеров, что для чеков).
  Локальное распознавание (`tesseract.js`, Apache-2.0, русский словарь) — запасной вариант без облака **[С]**.

Обязательные автоматические проверки перед предпросмотром (чтобы ловить ошибки без модели): сумма операций + остаток
на начало = остаток на конец; цепочка остатков по строкам; все даты внутри периода шапки; число строк > 0.

**Что могло бы изменить выбор:** первые настоящие образцы выписок (O1). Если окажется, что у банка PDF — «картинка»
или шифрованный, придётся добавить OCR/пароль. Если у всех банков из `samples/` формат одинаково «с линиями»,
подойдёт и `pdf2json` (у него есть координаты линий), но выигрыша я не вижу.

### 1.5 Стыки с другими областями

- **Фоновые задачи (pg-boss):** разбор PDF — CPU-тяжёлый (десятки–сотни мс на страницу, на больших файлах секунды);
  выполнять в рабочем процессе очереди `statement.parse`, а не в HTTP-обработчике (`NFR-21`).
- **ИИ-слой (`LLM`):** нужна функция «определи колонки» со строгой JSON-схемой (общая схема Zod для фронта и бэка)
  и функция «опиши скан» с изображением; маскирование — из слоя `PRIV`.
- **Безопасность (`SEC`):** лимит размера и числа страниц; `getDocument({ isEvalSupported: false })`
  (в pdf.js была уязвимость выполнения JS из шрифтов CVE-2024-4367, исправлена давно — оставить отключённым
  «на всякий случай») **[С]**; описания операций — данные, не инструкции (`STMT-12`) — разборщик **не должен**
  передавать их модели без экранирования.
- **Хранилище файлов:** исходный файл хранится (`STMT-10`); разбор идёт с него же.
- **Тесты:** фикстуры — обезличенные копии образцов; для универсального разборщика — набор синтетических PDF
  (генерировать из HTML через LibreOffice, как я сделал, или собрать `pdfkit`-ом в тесте).

### 1.6 Риски и вопросы пользователю

- Без реальных образцов точность — гипотеза. **Вопрос:** когда удастся положить 2–3 PDF выписок в `samples/`?
- PDF с паролем: банки иногда шифруют выписки паролем клиента. `pdf.js` бросает `PasswordException` — нужен
  экран «введите пароль к файлу» (не сохранять пароль). **Вопрос:** встречалось ли это у вас?
- Колонки «Приход/Расход» отдельными столбцами или знак «−» в одной колонке — оба случая надо тестировать.
- Неразрывные пробелы в числах (`1 455,55`: пробел может быть U+00A0 или U+202F) — единая функция разбора чисел
  с тестами.

## 2. Таблицы: XLSX, XLS, CSV (`STMT-03`, `STMT-04`)

### 2.1 Что решаем и почему

Пользователь может прислать файл Excel старого формата `.xls`, нового `.xlsx` или CSV из интернет-банка. Нужно

### 2.3 Находка про кодировки (важно)

Я сохранил CSV в Windows-1251 и проверил:
- `chardet` определил его как **windows-1250 (чешский)** с уверенностью 28% — **неправильно** **[В]**;
- SheetJS, получив «сырые» байты, выдал «ÎÀÎ «Òåñòáàíê»» — мусор, даже с параметром `codepage: 1251`
  (в сборке для Node «Codepage tables are not loaded») **[В]**;
- `new TextDecoder('windows-1251')` в Node 24 работает «из коробки» (полный ICU) и декодирует правильно **[В]**.

Надёжный порядок: 1) пробуем строгий UTF-8 (`new TextDecoder('utf-8', { fatal: true })`, учесть BOM);
2) иначе пробуем `windows-1251`, затем `ibm866` и выбираем тот вариант, где в первых строках встречаются известные
слова шапки («Дата», «Сумма», «Описание»); 3) только потом текст отдаём в `papaparse` / `XLSX.read(text, {type:'string'})`.
`iconv-lite` не нужен.

### 2.4 Рекомендация

**SheetJS CE 0.20.3 (с вендорингом тарболла) для `.xls`/`.xlsx`; `papaparse` для CSV; кодировку определять
собственной функцией по пункту 2.3.** SheetJS нужен именно из-за `.xls`. Если окажется, что `.xls` в Беларуси
не встречается, можно перейти на ExcelJS/`read-excel-file` и убрать зависимость от CDN. Читать файл — в рабочем
процессе очереди, с лимитом размера (защита от «zip-бомб» внутри `.xlsx`) **[С]**.

### 2.5 Стыки, риски, вопросы

- Единый формат результата для PDF/XLSX/CSV: «лист → строки ячеек со значением и текстом» — дальше общий слой
  «определение колонок» (§1.4).
- Определение настоящего типа файла по содержимому (`file-type` 22.2.0, MIT) — не доверять расширению **[В]**.

## 3. Генерация Excel с живыми формулами и диаграммами (`XLS-01…04`)

### 3.1 Что решаем и почему это критично

В SPEC требуется файл, где лист «Сводка» считается формулами `СУММЕСЛИМН/SUMIFS` по листу «Операции», **встроены
диаграммы**, а при правке суммы в листе «Операции» итоги и диаграммы обновляются без нашей системы (`XLS-03`).
Например: пользователь изменил категорию трёх операций — столбики диаграммы «Расходы по категориям» сами
перерисовались. Диаграммы должны быть **настоящими объектами Excel**, а не картинками.

### 3.2 Варианты

| Вариант | Диаграммы | Формулы | Плюсы | Минусы | Зрелость, лицензия |

### 3.3 Прототип (вариант A) — что именно проверено **[В]**

Скрипт `xls/gen-wasm.mjs` собирает файл из 3 листов (123 операции за 3 месяца):
- «Операции»: даты (`dd.mm.yyyy`), суммы в формате `#,##0.00 "BYN"`, колонка «Сумма в BYN» формулой, шапка фирменным
  цветом и шрифтом, **закреплённая шапка** и **автофильтр**;
- «Сводка»: 6 категорий × 3 месяца формулами
  `=SUMIFS('Операции'!$H:$H,'Операции'!$E:$E,$A2,'Операции'!$C:$C,"Расход",'Операции'!$A:$A,">="&DATE(2026,1,1),'Операции'!$A:$A,"<"&DATE(2026,2,1))`,
  итоги, доходы, разница; **столбчатая и круговая диаграммы**, ссылающиеся на ячейки сводки;
- «Лимиты»: `INDEX/MATCH` + процент.

Проверки:
1. **Структура:** в zip есть `xl/charts/chart1.xml`, `chart2.xml`, `drawing1.xml`; `workbook.xml` содержит
   `fullCalcOnLoad="1"` (Excel пересчитает всё при открытии). `openpyxl` читает файл без предупреждений: 2 диаграммы
   (`BarChart`, `PieChart`), формулы, закрепление `A2`, фильтр `A1:H124`.
2. **Отрисовка:** LibreOffice → PDF: диаграмма нарисована, шапка в фирменных цветах.
3. **КП из `XLS-03` — пересчёт:** загрузил файл в движок формул `hyperformula`, он посчитал `SUMIFS` с критериями
   по датам и целыми столбцами; итог расходов января 1738,46 → после «правки» суммы на +100 стал 1838,46; доходы
   3000 не изменились.
4. **Целые столбцы** (`$H:$H`) в `SUMIFS` обеспечивают «добавил строку внутри диапазона — итоги пересчитались»
   (`XLS-03`) без привязки к конкретной последней строке.
5. Работает под `tsx` и `vitest` 5.0.5 (WASM-модуль загружается без флагов) **[В]**.

### 3.4 Две ловушки, найденные в прототипе (обязательные к учёту)

1. **Кэшированный результат формулы.** LibreOffice (по умолчанию), многие просмотрщики и «защищённый просмотр»
   Excel **не пересчитывают** формулы при открытии. Формулы, у которых не записан результат, показали **0,00**
   (у строки «Расходы» и в «Лимитах» — видно на PDF) **[В]**. Решение: для **каждой** формулы вызывать
   `setResult(...)` с числом, которое мы и так знаем (те же суммы по категориям/месяцам, что считает SQL для дашборда).
   Тесты сравнивают кэш со свежим пересчётом (см. п. 3.5).
2. **Кэш диаграммы.** Для ячеек с формулами библиотека пишет в `<c:numCache>` только `ptCount`, без значений **[В]**.
   Excel в «защищённом просмотре» рисует диаграммы из этого кэша → без точек диаграмма может быть пустой до нажатия
   «Разрешить редактирование» **[С]** (в LibreOffice диаграмма нарисована верно, потому что он берёт данные из ячеек **[В]**).
   Я проверил простую пост-обработку: распаковать `xl/charts/chart*.xml` (`jszip`, лицензия MIT выбрана из двойной),
   подставить `<c:pt idx><c:v>` по известным значениям — файл остаётся валидным (`openpyxl` читает 2 диаграммы
   без предупреждений) **[В]**. Но когда в кэш попали нечисловые значения (`undefined`), `openpyxl` предупредил,
   что диаграмму прочитать не может **[В]** — значит, пост-обработку надо делать только из числовых значений,
   которые мы сами посчитали, с тестом.

### 3.5 Как тестировать `КП` в `XLS-03` без Excel

- В обычных тестах: читать выгруженный файл (SheetJS: формулы лежат в `cell.f`), загружать в **HyperFormula**
  (`hyperformula` 3.5.0, поддерживает `SUMIFS`, `DATE`, `INDEX/MATCH`, целые столбцы) **[В]**, менять сумму и
  проверять новый итог категории; плюс проверять, что кэшированные значения совпадают с пересчитанными
  (ловит забытый `setResult`).
- **Лицензия:** HyperFormula — **GPL-3.0-only** (или коммерческая) **[В]**. Как dev-зависимость тестов локального
  учебного проекта, не распространяемого дальше, это допустимо; в рабочую сборку её не включать. Если это
  смущает — запасной вариант: проверка через LibreOffice (`soffice --headless`) как отдельный `make`-шаг; но по умолчанию
  LibreOffice формулы **не пересчитывает** (проверил: показал кэш) **[В]**, поэтому понадобится смена настройки
  «пересчёт при загрузке» — дороже.

### 3.6 Рекомендация

**Вариант A: `wasm-xlsxwriter`** + (1) обязательный `setResult` для каждой формулы, (2) небольшая пост-обработка
кэша диаграмм, (3) целые столбцы в `SUMIFS`, (4) тест с HyperFormula как судья. Лист «Операции» оформить
как обычный диапазон с автофильтром; Excel-«Таблицу» (`Table`, умеет авторасширение) можно добавить для красоты,
но формулы со «структурированными ссылками» поддерживаются не всеми движками (HyperFormula, LibreOffice
частично) **[С]**, поэтому в формулах оставить обычные адреса.

**Что могло бы изменить выбор:** если мейнтейнер `wasm-xlsxwriter` пропадёт — запасной путь D (Python XlsxWriter в
отдельном контейнере/процессе: XlsxWriter 3.3.0 вышел 2026-10-22 **[В]**) или `excelize-wasm`. Прототип на A
занимает ~100 строк, поэтому смена обходится недорого, если спрятать выгрузку за интерфейсом `ExcelExporter`.

### 3.7 Стыки, риски, вопросы

- **Данные:** выгрузка берёт операции и агрегаты из БД; те же агрегаты нужны для кэша результатов формул —
  значит, SQL «итоги по категориям и месяцам» должен быть переиспользуемым модулем (источник для дашборда и Excel).
- **Дизайн (`DES`, `XLS-04`):** шрифты Inter/Playfair в Excel подтянутся, только если установлены на компьютере
  пользователя; иначе подмена на системный. Это нужно оговорить в интерфейсе или использовать Calibri/Arial в листах.
- **Размер:** 123 операции → 16 КБ; тысячи операций — единицы МБ, `saveToBufferSync` синхронный: для >50 тыс. строк
  выгружать в рабочем процессе.
- **Риск:** Excel не установлен — реальную проверку «открывается без «починки»» можно провести только в LibreOffice
  и openpyxl **[В]**; в Excel — вручную перед защитой.
- **Вопрос:** допустимо ли, что диаграммы в «защищённом просмотре» Excel могут быть пустыми, пока не нажата
  «Разрешить редактирование» (если не делать пост-обработку кэша)? Рекомендую сделать пост-обработку.

## 4. QR-код чека и подготовка фото (`RCPT-01`, `RCPT-04`)

### 4.1 Что решаем и почему

QR на чеке содержит УИ (SPEC §9.6: 24 символа; кассы до 17.06.2021 печатают иначе — строкой или штрихкодом).
Он нужен, чтобы **не создать чек дважды**. Читать его нужно локально, из фотографии, снятой в руках: наклон,
размытие, EXIF-поворот, а у iPhone — формат HEIC. Пример: пользователь сфотографировал чек повторно через неделю —
УИ совпал, система показывает «Этот чек уже загружен 12.10».

**Оговорка:** что именно закодировано в QR белорусского чека (только УИ или ссылка, содержащая УИ) я **не проверил** —
реального чека нет. Декодер возвращает строку, а извлечение УИ по шаблону (24 символа) — отдельная функция с
тестом на реальном образце. **[Н]** по формату полезной нагрузки.

### 4.2 Варианты декодера

Тест (`img/t-qr2.mjs`, `t-qr3.mjs`): 24 синтетических фото 3000×4000 (малый QR на «чеке», перспектива, поворот,
размытие, шум) + 4 обычных. «Лёгкие» (модуль ≥ ~9 пикселей) читают все четыре; «жёсткие» — стресс-тест.

| Вариант | Суть | Результат на лёгких | Скорость (12 Мп / 1600 px) | Минусы | Зрелость, лицензия |
|---|---|---|---|---|---|
| **`zxing-wasm`** | C++-библиотека zxing-cpp в WebAssembly; QR + 1D (Code128, EAN, ITF…) + DataMatrix | **4/4 «лёгких» кадра**; на «жёстких» (24 кадра): 4 на полном размере, **6 при уменьшении до 1600 px** (остальные библиотеки — 4); при объединении 5 попыток предобработки — 8 из 24 | 152 мс на 12 Мп; 10–60 мс на 1600 px **[В]** | **По умолчанию качает .wasm с CDN jsDelivr** (нарушение «всё локально»); исправление — `prepareZXingModule({overrides:{wasmBinary}})`, проверил: работает при заблокированной сети **[В]** | 3.1.6 (2026-10-19), MIT **[В]** |

`zxing-wasm`/`rxing-wasm` на «жёстких» — в пределах шума синтетического теста (24 кадра), поэтому выбор опирается на скорость,
поддержку 1D-кодов (старые кассы) и зрелость.

### 4.3 Подготовка изображений (`sharp`) и HEIC

- `sharp` 0.35.5 (Apache-2.0): `.rotate()` без аргументов применяет EXIF-ориентацию (проверил на тестовом
  файле с тегом 6 — QR прочитан) **[В]**; масштабирование, оттенки серого, нормализация яркости, `sharpen` — всё есть.
- **HEIC `sharp` не читает.** Его встроенная libvips собрана без HEVC: `sharp(heic).metadata()` определяет формат
  `heif`, но декодирование падает с «Support for this compression format has not been built in: HEVC» **[В]**.
- Рабочий путь: **`heic-decode` 2.1.0 (ISC; внутри libheif-js под LGPL-3.0, WebAssembly)** → сырые пиксели → `sharp(raw)`
  → JPEG. На 12 Мп: **2,7 с и ~360 МБ памяти процесса** **[В]**. Поэтому HEIC конвертировать **один раз при
  загрузке, в фоновой задаче**, и хранить оригинал + JPEG для модели.
- Что часто избавляет от HEIC: iOS Safari при загрузке через `<input type="file" accept="image/*">` обычно сам
  отдаёт JPEG **[С]**; Telegram при отправке «как фото» присылает уже сжатый JPEG **[С]**. HEIC придёт, когда пользователь
  отправит файл документом (в боте) или перетащит с Mac.
- **Фото из Telegram сжаты** (до ≈1280 px по длинной стороне **[С]**) — маленький QR может стать нечитаемым.
  Это нормально: SPEC допускает дубликат по магазину, дате, времени и итогу (`RCPT-04`). Но подсказка в боте
  «если QR не читается, отправьте фото как файл» повысит процент.

### 4.4 Рекомендуемый конвейер (`RCPT-01/04`)

1. Принять байты, определить тип по содержимому (`file-type`), HEIC → JPEG (`heic-decode`).
2. `sharp.rotate()`; сохранить копию для модели (длинная сторона ≤ 2000–2560 px, JPEG ~85) и **выкинуть GPS из EXIF**
   в копии для модели (оригинал хранится по `RCPT-11`, но координаты — персональные данные: `PRIV`).
3. QR: несколько попыток `zxing-wasm` с `formats: ['QRCode','Code128',…]`, `tryHarder`, `tryRotate`, `tryInvert`,
   `tryDownscale`: (а) кадр 2000 px; (б) 1400 px + нормализация; (в) 1000 px + нормализация; (г) 1400 px + резкость.
   Остановиться на первом успехе. Бюджет ~0,3 с.
4. Нашли — УИ по шаблону; не нашли — дубль по магазину/дате/времени/итогу после распознавания.

### 4.5 Рекомендация

**`zxing-wasm` (с локальным .wasm через `wasmBinary`) + `sharp` + `heic-decode`.** `jsQR` и `@zxing/library`
не брать: медленнее и слабее; `rxing-wasm` — запасной вариант с тем же интерфейсом (luma-массив). На реальных
фото результаты надо перемерить (O1) — мои 24 кадра синтетические.

### 4.6 Стыки, риски, вопросы

- **Очереди:** очередь `receipt.process` (QR → модель → валидатор → сопоставление) с ограниченной конкуренцией
  (ОЗУ: HEIC ~360 МБ на кадр).
- **Frontend:** камера на телефоне даёт 12–48 Мп; можно уменьшать в браузере (canvas) до загрузки, но QR-кроп надо
  делать из оригинала — оставить оригинал.
- **Telegram-бот:** альбом из нескольких фото приходит как несколько обновлений с одним `media_group_id` (§6.3).
- **Вопрос:** сохранять ли оригинал HEIC или JPEG-копию для «Открыть фото» (`RCPT-11`)? Браузеры HEIC не показывают
  (кроме Safari), поэтому для показа нужна JPEG-копия.

## 5. Загрузчик pravo.by (`LAW-35…LAW-39`)

### 5.1 Что решаем

Вежливый и надёжный клиент: один поток, пауза 3–5 с, повторы 30 с/2 мин/10 мин, остановка при 403/429, честный
User-Agent, gzip, проверка `robots.txt` для **каждого** адреса, разбор HTML со структурой
`<p class="article" id="…">`. Пример: ночью система проверяет 120 актов: сначала `HEAD` (дешёвый признак «изменилось»),
при смене — полный `GET` и разбор.

### 5.2 Что я проверил на живом сайте **[В]** (всего 7 запросов с честным UA, из них 2 загрузки страниц актов, между GET пауза 4–5 с; капчи нет)

- `robots.txt`: `Content-Type: text/plain; charset=UTF-8`, `gzip`; файл содержит **`Allow:` до `Disallow:`**, шаблоны
  `/*print=`, `*/index.php`, `/*.aspx*`, `Clean-param` (игнорируется), комментарии после `#`, и даже опечатку
  `Aloww:` — парсер обязан это пережить.
- Текст акта: `charset=UTF-8`, gzip (16 060 байт → 5 036); НК общая часть: 1 096 209 байт → **164 158 байт по сети**,
  0,4 с. В нём 116 статей (`class="article"`), 575 пунктов, 352 подпункта, `changeadd` у вставок **[В]**.
- Сервер ставит cookie `PHPSESSID` — хранить не нужно.
- **`HEAD` с `Accept-Encoding: gzip` вернул заголовки без `Content-Length`**; `HEAD` без сжатия — `content-length: 16060`
  (равно размеру несжатого файла, и для НК 1 096 209 — как и в прежнем ресерче). То есть лёгкая проверка работает, только
  если явно послать `Accept-Encoding: identity` **[В]**; встроенный `fetch` Node это позволяет **[В]**.

### 5.3 HTTP-клиент

| Вариант | Плюсы | Минусы | Зрелость |
|---|---|---|---|
| **Встроенный `fetch` (внутри Node — undici)** + тонкая своя обёртка | Нет зависимостей; сам распаковывает gzip; я проверил, что можно задавать `User-Agent` и `Accept-Encoding: identity`; таймаут — `AbortSignal.timeout` | Повторы и паузы пишем сами (≈50 строк, их всё равно надо адаптировать к правилам `LAW-38`) | Node 24.21 **[В]** |

## 6. Telegram-бот (`TG-01…TG-11`)

### 6.1 Что решаем

Фреймворк для бота: привязка по ссылке `t.me/<бот>?start=<код>`, фото и файлы, голос, кнопки под сообщениями,
опрос серверов Telegram (long polling), обработка накопившихся сообщений, «стриминг» ответа агента. Пример: пользователь
пересылает фото чека, бот сразу отвечает «Читаю чек…», а через несколько секунд присылает карточку с кнопками.

### 6.2 Варианты

| Вариант | Плюсы | Минусы | Зрелость |
|---|---|---|---|
| **grammY 1.46.0** | Активно развивается (релизы каждый месяц, последний 2026-08-26) **[В]**; полные TypeScript-типы по Bot API (`@grammyjs/types` 5.0.0, в нём уже есть `sendMessageDraft`) **[В]**; плагины: `files`, `runner`, `auto-retry`, `transformer-throttler`, `menu`, `commands`, `i18n`, `conversations` | Часть плагинов давно без релизов (но стабильны) | MIT |
| **Telegraf 4.16.3** | Очень известный | Последний релиз **2024-02-29**; зависимость `@telegraf/types ^7.1.0` (Bot API 7.x) — методов Bot API 9–10, в т. ч. `sendMessageDraft`, в типах нет; старые `node-fetch` 2 и `abort-controller` **[В]** | MIT |
| **node-telegram-bot-api 2.1.0** | Простой, много примеров | Колбэки, слабые типы; версия 2.1.0 вышла 2026-08-24, есть 2.2.0-rc2 от 2026-09-07 **[В]** | MIT |

Актуальная версия Bot API — **10.3 от 2026-08-24** **[В]**, grammY отстаёт от неё не критично.

### 6.3 Что проверено по документации Telegram **[В]**

- **Накопившиеся сообщения (`TG-10`):** сервер хранит необработанные обновления **не дольше 24 часов**; обновление
  подтверждено, когда `getUpdates` вызван со смещением выше его `update_id`. Значит, при запуске бот получит всё
  за ≤ 24 ч; если процесс упал посреди обработки, часть обновлений придёт повторно → нужна **идемпотентность по
  `update_id`/`message_id`** (таблица «обработанные обновления»).
- **Время сообщения:** у `message` есть `date` (Unix UTC) — по нему считать «потратил сегодня» (`TG-10`), в часовом поясе
  Минска (`NFR-23`).
- **Привязка (`TG-02`):** ссылка `https://t.me/<бот>?start=<параметр>`; параметр — до 64 символов из `A-Z a-z 0-9 _ -`.
  Подходит одноразовый код из 16 случайных байт в `base64url` (22 символа). grammY отдаёт его как `ctx.match`
  в `bot.command('start')`. Хранить в БД **хэш**, срок жизни ~15 минут, одноразовый.
- **Файлы (`TG-03`, `TG-04`):** `getFile` позволяет скачать **не более 20 МБ**; отправлять боту может больше, но не
  скачать. PDF выписок обычно меньше, но нужна понятная реакция «файл слишком большой» (при >20 МБ — загрузить через сайт).
  Бот отправляет документы до 50 МБ.
- **Кнопки:** `callback_data` — 1–64 байта → в нём хранить **короткий идентификатор** («чек:42:ok»), а не данные.
- **Альбомы:** несколько фото, отправленных разом, приходят как отдельные сообщения с одним `media_group_id`
  (`RCPT-01` — «каждое обрабатывается отдельно»; ответ можно собрать в один пакет по таймеру 1–2 с).
- **Потоковый ответ (`NFR-21` в боте):** в Bot API есть **`sendMessageDraft`** — «потоковая» передача частичного
  сообщения в личном чате (черновик живёт 30 секунд, итог обязательно отправляется `sendMessage`), есть кнопка
  «Остановить» (`can_stop`) и обновление «пользователь остановил генерацию» **[В]**. Проверил: метод есть в типах
  grammY 1.46 (`bot.api.raw.sendMessageDraft`) **[В]**. Запасной вариант — `editMessageText` не чаще раза в ~1 с.
- Доступность из этой сети: `api.telegram.org` ответил (HTTP 401 на фиктивный токен, 0,14 с) **[В]**.

### 6.4 Плагины и «чего не брать»

- **`@grammyjs/files` 1.2.0** — скачивание файлов (`ctx.getFile()` + `file.download()`).
- **`@grammyjs/auto-retry` 2.0.2** (повтор при 429/flood-wait) и **`@grammyjs/transformer-throttler` 1.2.1**
  (лимиты Telegram на скорость отправки) — по умолчанию включить.
- **`@grammyjs/runner` 2.0.3** — параллельная обработка обновлений. Без него `bot.start()` обрабатывает обновления
  **по одному**: тяжёлая обработка (ответ агента 20–60 с) задержит нажатие «Отменить» от того же человека. Два пути:
  (1) в обработчике **только ставить задачу в очередь** и сразу отвечать (рекомендую — так работает и сайт);
  (2) `run(bot)` + `sequentialize(ctx => ctx.chat?.id)`, чтобы сообщения одного чата шли по порядку.
- **`@grammyjs/conversations` 2.1.1 — не брать:** диалог «воспроизводится заново» при каждом сообщении
  (replay-движок), побочные эффекты нужно оборачивать в `external` **[В по докам]** — сложная модель ради сценариев,
  которые у нас закрывает агент (`TG-03`: «в строке 2 не 3, а 2» — это просто реплика агенту) и кнопки.
- **Встроенные сессии и `@grammyjs/storage-*` — не нужны:** привязка «chat_id ↔ user_id» и история лежат в нашей БД
  (`TG-05`: своя история бота).
- **`@grammyjs/i18n` 1.1.2** (Fluent) — подходит под «i18n-ready» (`NFR-19`), но можно использовать общий слой
  сообщений приложения, чтобы тексты бота и сайта были в одном каталоге. Решает область «фронтенд/общее».
- Парсинг «`/undo`», `/balance`…: `bot.command(...)`; меню команд — `bot.api.setMyCommands`.

### 6.5 Важный практический пункт: один опрашивающий

Telegram разрешает **только один** активный `getUpdates` на токен; второй процесс получит ошибку 409. Из-за
требования «работает и локально без контейнеров, и в контейнерах» легко запустить **двух** опрашивающих сразу
(например, забытый `make dev` и `docker compose up`). Решение: перед запуском опроса брать **консультативную
блокировку Postgres** (`pg_try_advisory_lock`) — кто получил, тот и опрашивает **[С]**. Токен бота вводится в
админке (`NFR-16`), поэтому опрос должен стартовать и **останавливаться/перезапускаться без перезапуска сервера**
(`bot.stop()` + новый экземпляр с новым токеном).

### 6.6 Рекомендация

**grammY 1.46** + `files`, `auto-retry`, `transformer-throttler`; обработчики тонкие (ставят задачу в очередь и отвечают
«Читаю…»), длинную работу делает общий рабочий процесс, итог отправляется через `sendMessage`; стриминг ответа агента —
`sendMessageDraft`. `conversations` и сессии не использовать. Идемпотентность по `update_id`. Исходящие
уведомления (`TG-06`) — через «исходящую очередь» pg-boss с учётом лимитов (~1 сообщение/с на чат).

**Что могло бы изменить выбор:** если нужно будет принимать обновления вебхуком (публичного адреса нет — не нужно).
Telegraf выбирать не за что.

### 6.7 Стыки, риски, вопросы

- **ИИ-слой:** потоковый вывод агента → два приёмника (SSE для сайта, `sendMessageDraft` для бота) — общий интерфейс
  потока событий.
- **Голос (`VOICE-01`):** `ctx.message.voice` — Ogg/Opus; Groq Whisper принимает ogg/opus, локальной модели, скорее
  всего, понадобится `ffmpeg` **[Н]** — вопрос смежной области (речь).
- **Безопасность:** бот принимает файлы только от привязанных чатов; группы игнорировать (`TG-11`); лимит размера;
  одноразовый код привязки не логировать.
- **Вопрос:** важна ли «живая» печать ответа в боте (`sendMessageDraft`) или достаточно «Печатает…» и готового ответа?
  Метод новый, поведение клиентов при возможной смене правил проверять на живом боте.

## 7. API НБРБ (`STMT-09`)

### 7.1 Что решаем

Операция в валюте (USD, EUR, RUB…) получает эквивалент в BYN по официальному курсу НБРБ на дату операции (`STMT-09`).
Курсы кэшируются; выходные и ещё не опубликованные дни — «последний установленный».

### 7.2 Что я проверил **[В]** (api.nbrb.by, бесплатно, без ключа, ответ быстрее 0,2 с)

- `GET /exrates/rates/USD?parammode=2&ondate=2026-10-23` → `{"Cur_ID":431,"Cur_Abbreviation":"USD","Cur_Scale":1,"Cur_OfficialRate":2.9543,"Date":…}`.
- **Выходной:** для 24.10 (суббота) и 25.10 (воскресенье) API **сам** вернул тот же курс 2,9543, поле `Date` — запрошенная дата
  (не дата установки курса). НБРБ уже публикует курс на следующий рабочий день (на 26.10 — 2,9460).
- **Будущая дата** (31.12.2026) и неизвестный код (`XXX`) → **HTTP 404** с JSON-ошибкой. Значит, «последний установленный»
  вручную нужен только для будущих дат/сбоев → запросить без `ondate`.
- **`Cur_Scale`:** RUB — 100 единиц (3,6460 за 100), AMD — 1000, UAH — 100, BRL — 10. **Курс за единицу = `OfficialRate / Scale`.**
- **Все валюты за день одним запросом:** `GET /exrates/rates?ondate=2026-10-23&periodicity=0` — 30 валют, 5 КБ.
- **Динамика:** `GET /exrates/rates/dynamics/{Cur_ID}?startDate=…&endDate=…`; при диапазоне больше 365 дней сервер **молча
  возвращает первые 365 дней** (запросил 2025-01-01…2026-10-26 — ответ закончился на 2025-12-31). Проверять, что
  последняя дата ответа = `endDate`.
- `Cur_ID` меняется со временем (SPEC §9.8) — для курса на дату использовать **ISO-код** (`parammode=2`);
  для динамики сначала узнать `Cur_ID` на нужную дату.

### 7.3 Варианты

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **Свой тонкий клиент + таблица кэша в Postgres** | `fx_rates(date, iso, scale, rate, fetched_at)`; запрос «все валюты на дату» один раз, дальше из БД | Просто, без зависимостей, офлайн-тесты на записанных ответах | Пишем сами (≈50 строк) |
| Готовая npm-обёртка | Нет известной поддерживаемой | — | Лишняя зависимость от неизвестного автора **[Н]** |

### 7.4 Рекомендация

Свой клиент поверх `fetch` (та же `PoliteFetcher`-логика повторов, но без паузы 3–5 с — API публичное и быстрое; пауза
~0,2 с, не более нескольких запросов подряд). Кэш в БД по паре (дата, ISO). Алгоритм курса на дату D:
(1) есть в кэше → готово; (2) запрос `ondate=D` на все валюты за день; (3) 404/будущее → последняя дата ≤ D из кэша,
иначе запрос без `ondate` и пометка «курс предварительный». Для **больших** выписок (месяцы) эффективнее
динамика по валюте (1 запрос на ≤ 365 дней). Курс и дата — в «Откуда эта цифра?» (`EXPL`). Деньги хранить как целые минимальные
единицы или `numeric`, не `float`.

### 7.5 Стыки, риски, вопросы

- Расчёт эквивалента — **детерминированный код** (тесты на записанных ответах; `NFR-11`).
- **Риск:** банк в выписке часто сам указывает сумму в BYN по своему курсу — его курс может отличаться от НБРБ. SPEC
  выбирает НБРБ; сумму банка стоит хранить отдельным полем и показывать разницу. **Вопрос:** какую цифру считать
  «главной», если банк указал сумму в BYN?
- **Риск:** недоступность api.nbrb.by — кэш + «последний известный» + уведомление админу.

## 8. Русский язык в JS: морфология, транслитерация, нечёткое сравнение

### 8.1 Что решаем и почему

Три разные задачи, их легко спутать:

1. **Поиск по законам (`LAW-21`)** — «зарплата» должна найти «заработная плата», «вернуть» — «возврат». Здесь нужны
   морфология **в поисковом движке** и словарь «бытовое → юридическое»; это работа базы данных, не JS.
2. **Нормализация наименований товаров (`RCPT-15`, `CAT-04`)** — «Молоко Простоквашино 3,2% 930мл» → «молоко»
   для динамики цен и правил категорий.
3. **Сопоставление магазинов (`TXN-10`)** — чек говорит «Евроопт», выписка — «OOO EVROTORG … EVROOPT MINSK BY»: надо
   сравнить кириллицу с латиницей.

### 8.2 Морфология и лемматизация

Проверено на 20 словах (`nlp/t-az.cjs`) **[В]**:

| Слово | `Az.js` (лемма) | Snowball | `natural` (PorterStemmerRu) |
|---|---|---|---|
| молоком | **молоко** | молок | молок |
| бананы | **банан** | бана (обрезал лишнее) | бана |
| вычеты / вычета | **вычет** | вычет | вычет |
| алиментов | **алименты** | алимент | алимент |
| бытовое | **бытовой** | бытов | бытов |
| деньги | **деньга** (первый разбор неверен — нужна проверка/словарь исключений) | деньг | деньг |

| Вариант | Плюсы | Минусы | Зрелость, лицензия |
|---|---|---|---|
| **Postgres: `to_tsvector('russian', …)`, словарь синонимов, `ts_lexize`** | Встроенный русский Snowball; поиск по законам и так на нём (`LAW-21`); словарь «бытовое→юридическое» делается тезаурусом БД | Лемм (нормальных форм слов) не даёт — только «основы»; в JS недоступно без запроса | Входит в PostgreSQL **[С]** |
| **`Az.js` 0.2.3** (словарный морфоанализатор в стиле pymorphy, словарь OpenCorpora) | Настоящие леммы, грамматические признаки; на Node 24 заработал, загрузка словаря 66 мс, 20 слов — 4,6 мс; 12 МБ словарей | Релиз 2016-06 — не поддерживается; неоднозначность (`деньги→деньга`), новых слов нет; CommonJS | MIT **[В]** |
| **`snowball-stemmers` 0.6.0 / `natural` 8.2.3 / `snowball-stemmers-js` 3.1.2** | Очень быстро, мало кода | Основы, а не слова; «бананы → бана»; для названия товара подходит только как ключ группировки | ISC / MIT / BSD-3 |

**Рекомендация:**
- Для **поиска по законам** — **только Postgres** (стеммер `russian`, тезаурус синонимов, плюс точный поиск по «ст. N НК»);
  в JS морфологию не тянуть (меньше кода, одна «правда»).
- Для **нормализации наименований** — **`Az.js`** (в отдельном модуле `text-normalize`) с очисткой: убрать вес/объём,
  проценты, бренд (по словарю), числа; взять существительное (первое слово в именительном падеже). Результат хранить
  вместе с исходной строкой (`RCPT-15`), чтобы нормализатор можно было улучшать и пересчитывать. Плюс «словарь
  исключений» для неверных лемм. Если `Az.js` не устроит (старость словаря) — запасной вариант: Snowball-основа как ключ
  группировки, без «красивой» леммы.
- **Белорусский (`NFR-19`)** в JS-библиотеках не покрыт **[Н]** — ассистент понимает белорусский на уровне модели, а
  не лемматизатора.

### 8.3 Транслитерация

`transliteration` 2.7.0 (MIT, 2026-10-23) **[В]**: «Евроопт» → `evroopt`, «Хлебница» → `hlebnica`, «Аптека №12» → `apteka no12`.
Варианты: `cyrillic-romanization` 1.2.3 (умеет стандарты ISO 9, BGN/PCGN…), `@sindresorhus/transliterate`, `iuliia`
(2022). Для **сопоставления** (а не для красивого вывода) стандарт не важен: важно приводить обе строки к одной схеме
(нижний регистр, латиница, без знаков). **Рекомендация: `transliteration`**, и для русских названий в справочнике
контрагентов хранить **список алиасов** (латинских написаний), потому что фонетически «Грин» ≠ `GREEN`.

### 8.4 Нечёткое сравнение названий магазинов (`TXN-10`)

Эксперимент (`nlp/t-fuzzy.mjs`): транслитерация + `fuzzball` (порт FuzzyWuzzy, MIT, 2.2.6 от 2026-04-30) **[В]**:

| Пара | `partial_ratio` | `token_set_ratio` | Верно? |
|---|---|---|---|
| Евроопт ~ «OOO EVROTORG EVROOPT T-0042 MINSK…» | 100 | 100 | да |
| Белмаркет ~ «SHOP BELMARKET PR-T NEZAVISIMOSTI…» | 100 | 100 | да |
| Соседи ~ «SOSEDI GRODNO UL SOVETSKAYA 3» | 100 | 100 | да |
| МТС ~ «MTS BELARUS PAYMENT» | 100 | 100 | да |
| Аптека №12 ~ «APTEKA N 12 GRODNO…» | 91 | 71 | да |
| Гиппо ~ «HIPPO MINSK BY» | 80 | 42 | да (только по `partial`) |
| Грин ~ «GREEN MINSK BY» | 50 | 44 | **нет** — перевод, а не транслитерация |
| Евроопт ~ «SHOP BELMARKET…» (разные магазины) | 29 | 23 | правильно «не похоже» |
| Хлебница ~ «EVROOPT MINSK» | 13 | 19 | правильно «не похоже» |

Вывод: после очистки (`STMT-06`) и транслитерации `partial_ratio` отлично работает для «бренд внутри длинной строки»;
плохие случаи — переводы и аббревиатуры — решает **справочник алиасов** (`TXN-10`: «по справочнику контрагентов»).

| Вариант | Где работает | Плюсы | Минусы |
|---|---|---|---|
| **Postgres `pg_trgm`** (`similarity`, `word_similarity`, индекс GIN) | В БД | Поиск похожих среди тысяч строк индексом; пригодится для «найти контрагента по тексту» | Нужен UTF-8-регион (в образе Postgres по умолчанию так) **[С]**; транслитерация всё равно в приложении; не проверял — Docker на машине не запущен |
| **`fuzzball` 2.2.6** | В приложении | Готовые `partial_ratio`, `token_set_ratio`; удобно сравнивать 1 чек с 3–10 кандидатами | Не масштабируется на миллионы (нам не нужно) |
| `string-similarity` 4.0.4 | — | — | **Помечен как «no longer supported»** **[В]**; не брать |

**Рекомендация:** для `TXN-10` (один чек против нескольких кандидатов-операций в окне ±2 дня) — **транслитерация +
`fuzzball.partial_ratio`/`token_set_ratio` в приложении**, порог в настройках (`O15`); `pg_trgm` подключить в БД для
справочника контрагентов (поиск по тексту и «похожие названия» в админке) — это одна строка `CREATE EXTENSION pg_trgm` и
индекс. Сам порог подбирать на демо-данных (в SPEC это O15).

### 8.5 Стыки, риски, вопросы

- **База данных:** расширения `pg_trgm`, `unaccent` (контрибы стандартного образа Postgres), русская конфигурация
  полнотекстового поиска — в зоне ответственности области БД.
- **Тесты:** таблица пар «эталон» (как выше) — готовый тест на регрессии нормализации и сопоставления.
- **Риск:** `Az.js` не обновляется и в CommonJS; изолировать за интерфейсом `Lemmatizer`.
- **Вопрос:** нужен ли белорусский в правилах категоризации («малако»)? Пока — нет, через модель.

## 9. Сквозные требования к приёму файлов (для всех пунктов)

Один модуль `file-intake`: размер и количество; определение типа **по содержимому** (`file-type` 22.2.0);
запрет исполняемых типов; антивирусная проверка не нужна для локального проекта, но имя файла не использовать как путь;
тяжёлые операции (PDF, XLSX, HEIC, QR) — **в рабочем процессе очереди с таймаутом и лимитом памяти**, а не в HTTP-процессе;
исходник хранится как «бинарный объект» с хэшем (дедупликация и `STMT-07`, `RCPT-04`). Образцы из `samples/` не в git (`NFR-18`).
