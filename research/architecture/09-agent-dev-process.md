## 1. Пользовательские сабагенты: формат, модели, инструменты, скиллы

### 1.1 Что решаем и почему важно

Четыре роли конвейера — это четыре «специалиста» с разными правами и разными моделями. Например, критик не
должен случайно «поправить код вместо того, чтобы замечать», а ревьюер не должен молча переписывать то, что
проверяет. В Claude Code роль задаётся одним Markdown-файлом в `.claude/agents/` — «сабагент» (subagent):
отдельная сессия Claude со своим окном контекста, своим промптом, моделью и набором инструментов.

### 1.2 Формат файла (что есть на сегодня) [В — страница sub-agents]

Файл `.claude/agents/<что-угодно>.md`: шапка YAML между `---`, тело — системный промпт роли. Обязательны только
`name` и `description`. Имена полей — строго в camelCase; неизвестные поля молча игнорируются (опечатка в имени
поля не даст ошибки — поле просто не сработает).

| Поле | Что делает | Для нашего конвейера |
|---|---|---|
| `name`, `description` | Идентификатор и «когда звать»; общий размер всех описаний больше 15 000 токенов даёт предупреждение | Описания короткие; детали — в теле файла |
| `tools` | Белый список инструментов (через запятую или списком). Не указано — наследует все, включая MCP | Критик/ревьюер — урезанный список |
| `disallowedTools` | Чёрный список, применяется раньше `tools` | Имплементатору/фиксеру: `Agent` (чтобы не плодили вложенных) |
| `model` | `sonnet`, `opus`, `haiku`, `fable`, полный id (`claude-opus-5-5`) или `inherit` | См. 1.3 |
| `effort` | `low`/`medium`/`high`/`xhigh`/`max`, переопределяет уровень сессии | Стартовые значения в 1.5 |
| `permissionMode` | `default`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`, `plan` | **Мягкая** настройка, см. 1.4 |
| `maxTurns` | Потолок шагов; при превышении вернёт частичный результат, агента можно продолжить | Защита от зацикливания |
| `skills` | Список скиллов, чьё **полное содержимое** кладётся в контекст при старте (до 32) | См. 1.6 |
| `hooks` | Хуки только на время работы этого агента (`Stop` превращается в `SubagentStop`) | Требует «доверия к папке», **не работает в `-p`** — поэтому охранные хуки кладём в `settings.json` (см. раздел 4) |
| `memory` | `user`/`project`/`local`: постоянная память агента в `.claude/agent-memory/<имя>/` | Пока не включать (1.7) |
| `isolation: worktree` | Агент работает во временном git-worktree | Не подходит (1.7) |
| `background` | Всегда в фоне | Не нужен |
| `omitClaudeMd` | Не загружать `CLAUDE.md` (v2.1.271+) | Не нужен |
| `mcpServers`, `color`, `initialPrompt`, `autoCompactWindow`, `experimental.cacheTtl` | MCP-серверы только для агента; цвет; и т. д. | Не нужны |

Где лежат и что приоритетнее [В]: управляемые настройки организации → флаг `--agents` → `.claude/agents/` проекта →
`~/.claude/agents/` → агенты плагинов. Правка файлов подхватывается за секунды (но первое создание папки
`agents/` требует перезапуска сессии). **У агентов из плагинов поля `hooks`, `mcpServers`, `permissionMode`
игнорируются** — ещё один довод держать роли в проекте, а не в плагине.

### 1.3 Как задать модель

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| A. Алиас в файле: `model: sonnet` / `model: opus` | Алиас указывает на актуальную версию (сейчас `sonnet` → Sonnet 5.5, `opus` → Opus 5.5 на Anthropic API) | Проще всего; сам обновляется | При выходе новой версии модель роли «переедет» молча — поменяются поведение и цена |
| B. Полный id: `model: claude-opus-5-5` | Закрепляет версию | Воспроизводимо | Устаревает; придётся править 4 файла |
| C. Разовое `model` в вызове `Agent` | Оркестратор сам решает на каждый вызов; побеждает файл | Нужно для «эскалации» фиксера | Зависит от того, что оркестратор не забудет параметр |
| D. Переменная `CLAUDE_CODE_SUBAGENT_MODEL` | Модель для **всех** сабагентов без своей | Для нас не нужна | `…_FORCE=1` перебьёт все `model:` — **не включать** |

Порядок выбора модели сабагента (с v2.1.251) [В]: параметр вызова → `model:` в файле → `CLAUDE_CODE_SUBAGENT_MODEL` →
модель главной сессии. Модели из чужого списка `availableModels` подменяются с предупреждением (актуально
только в организациях).

**Рекомендация:** вариант A (алиасы) + вариант C для эскалации фиксера. Если когда-нибудь поведение «поплывёт» после
обновления модели — перейти на B.

### 1.4 Как ограничить инструменты (критик и ревьюер — «только чтение»?)

Важный нюанс: «только чтение» для критика и ревьюера нужно **не буквально**, потому что оба должны оставить
после себя отчёт-файл. Три способа:

| Способ | Суть | Надёжность |
|---|---|---|
| 1. Без `Write`/`Edit` совсем, отчёт отдаётся в ответе | Родитель сам сохраняет текст в файл | Надёжно, но отчёт целиком проходит через контекст оркестратора (раздувает его), теряется точность при пересказе |
| 2. `Write` разрешён + хук `PreToolUse` в `settings.json`, который пускает запись только в `tasks/reports/` | Скрипт смотрит `agent_type` и путь, нормализует `../` | Надёжно: хук-запрет действует в любом режиме разрешений, даже `bypassPermissions`; **проверено** [В] |
| 3. `permissionMode: plan`/`dontAsk` | Режим «только чтение» | **Мягко**: если сессию запустили в режиме `auto`, `acceptEdits` или `bypassPermissions`, режим сессии побеждает, и `permissionMode` агента игнорируется [В — документация] |

**Рекомендация:** способ 2 для обоих ролей. У критика нет `Bash` вообще (ему хватает Read, Grep, Glob, Write).
Ревьюеру `Bash` нужен (`git diff`, запуск тестов и линтера) — поэтому второй хук разрешает только белый список
команд и запрещает перенаправления вывода, `git add/commit/checkout/reset/...` (скрипт проверен, это «разумная
осторожность», а не песочница: `make check` сам может что-то записать).

Ещё нюансы:

- **Фильтры платформы:** у любого сабагента отобраны `AskUserQuestion`, `EnterPlanMode`, `Workflow` и т. п. — то есть
  **сабагент не может задать вопрос пользователю**; вопросы пользователю задаёт только главная сессия (то есть
  команда-оркестратор). Критик поэтому возвращает вердикт `NEEDS_USER`, а не спрашивает сам.
- **MCP-инструменты** (например, Context7 — а в вашем `~/.claude/rules/context7.md` написано обращаться к нему за
  документацией библиотек) попадают к агенту только если `tools` не задан или MCP-инструмент в нём указан
  (`mcp__context7__*`). Имплементатору `tools` лучше не задавать (наследует всё); ревьюеру и критику добавить
  `mcp__context7__*`.
- Правило `Agent(a, b)` в `tools` работает только для сессии, запущенной как `claude --agent X`; внутри обычного
  сабагента скобки игнорируются. Чтобы роль не порождала других, используем `disallowedTools: Agent`.
- Фоновые агенты: фоновому сабагенту по умолчанию доступна лишь часть встроенных инструментов (Read, Grep,
  Glob, Bash, Edit, Write, WebFetch, Skill и др.) — для нас достаточно.

### 1.5 Стартовая таблица ролей

| Роль | Модель | effort (стартовый, [Н] подбирать по опыту) | tools | Скиллы (preload) | maxTurns [Н] |
|---|---|---|---|---|---|
| critic | sonnet | high | Read, Grep, Glob, Write*, `mcp__context7__*` | planning-and-task-breakdown | 20 |
| implementer | opus | high | все (кроме `Agent`) | incremental-implementation, test-driven-development | 60 |

применять только после проб [В — model-config].

### 1.6 Как передать скиллы

- `skills:` в файле агента **вливает полный текст** выбранных скиллов в контекст при старте (нельзя скиллы с
  `disable-model-invocation: true`; в установленных 25 таких нет [В]).
- Остальные установленные скиллы **остаются доступны** агенту через инструмент `Skill`, если его не убрали.
  Поэтому схема «базовый набор — preload, специальные — по задаче»: в задаче есть поле `Skills:`
  (например, `security-and-hardening`), и промпт роли велит их вызвать.
- Цена preload: `incremental-implementation` (249 строк) + `test-driven-development` (398 строк) — примерно 650
  строк текста в каждый запуск имплементатора. Для Opus это терпимо; не грузить «на всякий случай» все 25.
- Сабагент не наследует вызванные скиллы и историю главной сессии — **всё нужное передаётся явно** в промпте и
  файлами (раздел 2).

### 1.7 Что не включать сейчас

- `isolation: worktree` для имплементатора: worktree ветвится от **основной ветки по умолчанию**, а не от текущего
  коммита; следующая задача, зависящая от предыдущей, не увидит её кода, пока та не влита. Работаем в основном
  каталоге на ветке задачи, строго по очереди.
- `memory:` — накопление «выученного» в `.claude/agent-memory/` шумит и расходует контекст (читаются первые 200 строк
  или 25 КБ). Вернуться, когда у ревьюера появятся повторяющиеся замечания.
- Фоновые агенты и параллельные задачи: конвейер последовательный по определению.

### 1.8 Риски и открытые вопросы

- Опечатка в поле (`permisionMode`) молча не работает — после создания файлов пройти `/doctor` (он
  ловит дубли имён и неразбираемую YAML в шапке) [С].
- Размер всех шапок `description` и скиллов съедает контекст главной сессии — держать описания в одну-две строки.

## 2. Как оркестрировать цепочку

### 2.1 Что решаем и почему важно

Нужно, чтобы на команду «выполни задачу T-012» четыре роли отработали по очереди, а пользователь получил один
понятный отчёт и предложение «запустить следующую?». Пример: на T-012 «валидатор арифметики чека» критик
замечает, что в критериях приёмки нет случая «скидка по позиции», задача уточняется до старта, а не после
написания неверного кода.

### 2.2 Варианты

| Вариант | Суть | Плюсы | Минусы | Зрелость |
|---|---|---|---|---|
| A. Слэш-команда/скилл `/task-cycle` | Главная сессия по скрипту-промпту вызывает сабагентов один за другим; результаты — в файлах | Просто; видно в разговоре; **может задать вопрос пользователю**; **проверено** [В] | Оркестратор — LLM: может отклониться от скрипта; контекст главной сессии копится | Стабильно |
| B. Динамический Workflow (JS-скрипт) | Скрипт сам держит цикл и ветвление (`agent()`, `pipeline()`, `parallel()`, `phase()`, схема JSON-ответа), выполняется в фоне | Жёсткая логика (счётчик раундов, эскалация на Opus — **кодом**, а не «по настроению» LLM); контекст сессии не засоряется; возобновляется | Нет ввода пользователя в середине (вопросы — только между запусками); новая функция; перед запуском запрос разрешения (или правило `Workflow`) | Есть, не «экспериментальная», но молодая |
| C. Agent Teams | Лидер + самостоятельные «товарищи» с общим списком задач и перепиской | Подходит для споров и параллельной разведки | **Экспериментальная** (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), больше токенов, нет возобновления in-process товарищей; для строго последовательного конвейера не нужна | Экспериментально |
| D. Один «агент-руководитель» (сабагент вызывает сабагентов) | Вложенность до 3 уровней разрешена по умолчанию | Технически работает [В] | Нет вопросов пользователю; лишняя «пересказывающая» прослойка; скрытая цена; нарушает собственный каталог паттернов репозитория | Работает, но не советую |
| E. Внешний скрипт `claude -p` на каждый шаг | Bash/Node-скрипт зовёт `claude -p --agent critic …` по очереди | Полностью детерминированно; годится для ночного прогона | Своя обвязка; теряется интерактивность | Стабильно |

Дополнительно: `/goal "<условие>"` (в 2.1.308 есть) заставляет Claude продолжать ходы, пока малая модель не решит,
что условие выполнено [В]. Подходит для режима «выполняй задачи плана подряд, пока не кончатся» **вместо** шага
«предложить следующую»; но снимает человеческий контроль между задачами — не рекомендую по умолчанию.

### 2.3 Рекомендация

**Начать с A (`/task-cycle`)**, а правила, которые обязаны выполняться жёстко, вынести из LLM в хуки (раздел 4):
число раундов и эскалацию ведёт оркестратор по короткой таблице решений, а «зелёные тесты» и «формат вердикта»
проверяют хуки `SubagentStop`. Если на практике оркестратор будет сбиваться — перенести тот же сценарий в B
(Workflow): структура ролей и файлов остаётся прежней, меняется только «кто дирижирует» (сохранённый workflow
запускается как `/имя`; сценарий пишет сам Claude, справка — встроенный скилл `/workflow-authoring`).

Почему не B сразу: критик иногда обязан остановить цикл и спросить пользователя («объединить T-012 и T-013?»), а
внутри Workflow ввода от пользователя нет [В]; и A проверен запуском, B — только прочитан.

**Команда или скилл?** Команды слиты со скиллами: `.claude/commands/x.md` и `.claude/skills/x/SKILL.md` оба
создают `/x`, старые файлы продолжают работать; при одинаковом имени побеждает скилл [В]. Образцы ниже — в
`commands/` для единообразия с `as-*`; если понадобятся шаблоны отчётов отдельными файлами рядом, удобнее
скилл-папка (`${CLAUDE_SKILL_DIR}`). В шапке: `disable-model-invocation: true` (запуск только вручную),
`argument-hint`, `model: sonnet` (оркестратору не нужен Opus; проверено, что `model:` команды действует) [В].

### 2.4 Может ли сабагент вызывать сабагента — итог

Да, по умолчанию до трёх уровней ниже главной сессии (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` выключает) [В]. В
конвейере это **не нужно и вредно**: глубина строго 1 (команда → роли). Страховка: `disallowedTools: Agent` в
ролях. Это совпадает с духом установленного `references/orchestration-patterns.md` («оркестрация не глубже 1»), хотя
обоснование «платформа запрещает» в нём устарело.

### 2.5 Передача результатов между шагами

Подводные камни: сабагент стартует с чистого листа (без истории), результат возвращается в главную сессию как
текст, «пересказ» теряет детали [В]. Поэтому:

1. Каждая роль **пишет свой отчёт в файл** `tasks/reports/<ID>/NN-<роль>.md` и **возвращает ≤10 строк**: первой
   строкой `VERDICT: …`, затем путь к файлу и счётчики. Оркестратор ничего не пересказывает, а передаёт **пути**.
2. Следующая роль получает в промпте: ID задачи, путь к тексту задачи, пути к предыдущим отчётам.
3. Состояние восстанавливается по файлам: если `01-critic.md` уже есть и вердикт `PROCEED`, команда пропускает
   шаг (удобно после обрыва; `/task-cycle T-012 --from review` — необязательное).

Хранение:

| Где | Плюсы | Минусы |
|---|---|---|
| `tasks/reports/<ID>/` в git целиком | Полная история, материал для рассказа о процессе в дипломе [Н] | Шум в истории |
| В git только `tasks/reports/<ID>/summary.md`, остальное в `.gitignore` | Чисто | Теряются подробности |
| Всё в `.gitignore` | Минимум шума | Нет следа |

Рекомендация: в git — `summary.md` и отчёты ревью; шумное (`NN-impl.md` пошагово) — по желанию. Это решение
пользователя (вопрос 3 ниже). Рядом с существующими `tasks/plan.md` и `tasks/todo.md`, которые создаёт `as-plan`.

### 2.6 Фон и ожидание (интерактивный режим) [С]

Документация: сабагент, запущенный Claude из главного разговора, **по умолчанию стартует в фоне**; чтобы
Claude ждал результат, в интерактивных сессиях выключают режим форка `CLAUDE_CODE_FORK_SUBAGENT=0` (в `settings.json`
→ `env`), либо в промпте явно «в foreground, дождись». В `-p` у меня оркестратор сам ставил `run_in_background: false`
[В], в интерактивном режиме это **не проверено** — проверить на первой реальной задаче (команда `/tasks` покажет
активные агенты и их модель, v2.1.242+). Если фон всё же включён, результат приходит уведомлением следующим ходом —
конвейер всё равно пройдёт, просто «ходами».

### 2.7 Git внутри конвейера

- Перед стартом `git status --porcelain` должен быть чистым (как в установленном `as-build auto`).
- Ветка на задачу `task/T-012-<slug>`; имплементатор делает 1–N коммитов; фиксер — **новыми** коммитами (не
  переписывает историю после ревью); ревьюер смотрит `git diff main...HEAD`, а не отдельные коммиты — ему
  безразлична их нарезка.
- Слияние ветки в `main` (`git merge --ff-only`) и `git push` — только с согласия пользователя (NFR-17: публикация
  только по явной просьбе; push блокируется хуком, раздел 4).
- Вопрос к пользователю: ветки на задачу или коммиты сразу в `main`? (Для одного человека допустимо и то и другое,
  ветки дают дешёвый откат «целой задачи».)

### 2.8 Последовательность и правила выхода

```
/task-cycle T-012
 0. Подготовка: чистое дерево, задача есть в tasks/todo.md и её зависимости закрыты, ветка task/T-012-…
 1. critic            → 01-critic.md
      PROCEED         → дальше
      REVISE/MERGE/DROP/NEEDS_USER → СТОП, показать пользователю, спросить (план меняет только он)
 2. implementer       → 02-impl.md (RED→GREEN→refactor, коммиты; гейт SubagentStop = make check зелёный)
 3. reviewer (раунд 1)→ 03-review-1.md
      APPROVE         → к шагу 6
      CHANGES_REQUESTED → 4
 4. fixer (Sonnet; Opus по условиям из раздела 6) → 04-fix-1.md (гейт make check)
 5. reviewer (раунд 2; на вход: предыдущее ревью + отчёт фиксера + diff правок)
      APPROVE → 6;  остались Critical/Required → fixer на Opus → reviewer (раунд 3)
      после 3-го ревью замечания остались → СТОП, пользователю (не крутить дальше)
 6. Итог: summary.md, чат-отчёт, «запустить следующую задачу T-013?»
```

Потолок: **максимум 3 ревью и 2 правки** — это защита от бесконечного цикла «правка-ревью», в котором к тому
же легко ослабить проверки, чтобы «позеленело» (см. 5, `constraint-driven-development`).

## 3. Правила по модулям монорепы

### 3.1 Что решаем и почему важно

Агенты должны знать правила модуля, в котором работают. Пример: в `apps/web` — «все строки через i18n, у
каждого экрана четыре состояния (DES-16)», в `apps/api` — «ничего из `apps/web` не импортировать, SQL только
через слой данных». Правила не должны лежать в контексте всегда — это сжигает токены.

### 3.2 Что поддерживается сейчас [В — memory.md, large-codebases.md; плюс опыт 8 выше]

- `CLAUDE.md` в каталогах **выше** рабочей папки грузятся при старте; в подкаталогах **ниже** — лениво, когда
  агент читает/пишет/правит файл в этом подкаталоге. Целевой размер — до 200 строк на файл.
- `.claude/rules/*.md` без `paths:` — грузятся всегда; с `paths:` (glob, фигурные скобки допустимы) — когда
  агент читает/пишет/правит подходящий файл. Из полей шапки правила читается **только** `paths`.
- `@путь` в `CLAUDE.md` подключает файл целиком (контекст не экономит). Блочные HTML-комментарии из `CLAUDE.md`
  вырезаются перед загрузкой — удобно для заметок мейнтейнеру.
- Сабагенты получают `CLAUDE.md` (кроме встроенных Explore/Plan) и **лениво подгружаемые правила тоже работают
  внутри сабагента** — проверено запуском [В]: слова из правила и вложенного `CLAUDE.md` появились у сабагента
  после Read файла в нужной папке.
- Грань: ленивая загрузка срабатывает на Read/Write/Edit (и простое `cat`), **не обязательно на Grep/Glob** [С]. Агент,
  который только искал по коду, правил модуля мог не увидеть.
- `claudeMdExcludes` пропускает ненужные файлы; `AGENTS.md` читается, только если нет `CLAUDE.md` (для совместимости
  с другими инструментами — `@AGENTS.md` внутри `CLAUDE.md`).

### 3.3 Варианты

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| A. Вложенные `CLAUDE.md` в каждом модуле | `apps/api/CLAUDE.md`, `apps/web/CLAUDE.md`, `packages/shared/CLAUDE.md` | Лежат рядом с кодом, меняются вместе с ним; владелец — модуль | Покрывают всю папку целиком; сквозные темы («тесты», «миграции») размазаны по модулям |
| B. `.claude/rules/<тема>.md` с `paths:` | Всё в одном месте, привязка по маске | Одно правило на много разбросанных путей; удобный обзор | Правила далеко от кода; легко разъехаться со структурой папок при переносе модулей |
| C. Гибрид | Паспорт модуля — вложенный `CLAUDE.md`; сквозные темы по типу файлов — `rules/` с `paths:` | Каждое правило живёт там, где его проще поддерживать | Два места — нужна договорённость, что куда |

### 3.4 Рекомендация: C

- **Корневой `CLAUDE.md`** (до ~100 строк): карта модулей, команды `make …` (NFR-14), процесс конвейера в двух
  абзацах, правила коммитов, «как просить правила модуля», язык. Без обзоров стека — их агент выводит из кода.
- **`<модуль>/CLAUDE.md`** («паспорт», до ~60 строк): что за модуль, публичный интерфейс, что ему **нельзя**
  импортировать (ссылкой на конфиг dependency-cruiser, а не копией правил — копия протухнет), как запускать
  тесты именно здесь, подводные камни.
- **`.claude/rules/*.md` с `paths:`** по темам: `testing.md` (`**/*.test.ts`, `**/tests/**`), `db-migrations.md`
  (`**/migrations/**`), `a11y-ui.md` (`apps/web/**/*.tsx`), `i18n.md`, `logging.md`, `security.md`
  (`**/auth/**`, `**/secrets/**`). Каждое — до ~40 строк.
- В **промптах ролей** прописать: «до оценки/реализации прочитай `CLAUDE.md` каждого затронутого модуля и
  `Glob .claude/rules/*.md`; сверь пути из `Files likely touched`» — тогда правила гарантированно загружены,
  даже если агент пока только искал по коду.
- Пример правила:

```markdown
---
paths:
  - "apps/web/**/*.tsx"
---
# Интерфейс (WCAG AA, NFR-20; состояния — DES-16)
- Все тексты через i18n-функцию, без литералов в JSX (NFR-19).
- У каждого экрана 4 состояния: загрузка, пусто, ошибка, успех.
- Интерактивные элементы доступны с клавиатуры; смысл не передаётся только цветом.
```

## 4. Хуки Claude Code и git-хуки

### 4.1 Что решаем и почему важно

Инструкции в `CLAUDE.md` — «просьба», хук — «закон». Документация прямо говорит: чтобы запретить действие
независимо от решения модели, нужен хук `PreToolUse`, а не текст в `CLAUDE.md` [В]. Пример: «после каждой
правки отформатировать файл» или «нельзя `git commit --no-verify`» должны выполняться всегда.

### 4.2 Что умеют хуки Claude Code [В — hooks-guide, hooks reference]

- События (выборка): `PreToolUse` (перед инструментом, может запретить), `PostToolUse` (после правки), `Stop`
  (Claude закончил ответ), `SubagentStart`/`SubagentStop`, `TaskCreated`/`TaskCompleted` (для списка задач и
  Agent Teams), `UserPromptSubmit`, `SessionStart`, `InstructionsLoaded` (какие правила подгрузились — полезно
  для отладки), `PreCompact`, `FileChanged`, `WorktreeCreate` и др.
- Обработчики: `command` (скрипт), `http`, `mcp_tool`, `prompt` (один вызов модели), `agent` (мини-сабагент с
  инструментами; **экспериментально**).
- Выход: `exit 0` — ок; `exit 2` — блок + текст из stderr возвращается Claude (для `PostToolUse` инструмент уже
  выполнился); либо `exit 0` и JSON с `decision`/`permissionDecision`/`additionalContext`.
- `matcher` — по имени инструмента (или агента для `SubagentStart/Stop`); `if: "Bash(git commit *)"` сужает до
  вызова с конкретными аргументами.
- Вход хука инструментов содержит `agent_id` и `agent_type` — **так хук знает, какая роль действует** (проверено
  скриптом выше) [В].
- Запрет `permissionDecision: "deny"` или `exit 2` в `PreToolUse` действует **во всех режимах**, включая
  `bypassPermissions`.
- Хуки читаются из `.claude/settings.json` (в git), `settings.local.json`, `~/.claude/settings.json`, плагинов;
  хуки из шапки проектного агента требуют доверия к папке и в `-p` пропускаются.
- Ограничения: `Stop` срабатывает после **каждого** ответа, не только «в конце задачи»; после 8 блокировок подряд
  платформа принудительно завершает (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`); в скрипте проверять `stop_hook_active`.

### 4.3 Что стоит автоматизировать (рекомендуемый набор)

| № | Хук | Событие / matcher | Что делает | Проверено |
|---|---|---|---|---|
| H1 | `guard-git.sh` | `PreToolUse` / `Bash` | Запрещает `git commit --no-verify`, `-n`, `LEFTHOOK=0`, `HUSKY=0`, `core.hooksPath`, `git push`, `reset --hard`, `clean -f`, `checkout --` | да |
| H2 | `restrict-writes.sh` | `PreToolUse` / `Write\|Edit` | Критику и ревьюеру — запись только в `tasks/reports/` | да |
| H3 | `reviewer-bash.sh` | `PreToolUse` / `Bash` | Ревьюеру — белый список команд, без записи | да |
| H4 | `format-lint.sh` | `PostToolUse` / `Write\|Edit` | oxfmt и oxlint на изменённый файл (быстро, секунды); замечания Claude получает через `exit 2` | механизм да, команды oxfmt/oxlint не пробовал |
| H5 | `gate-impl.sh` | `SubagentStop` / `implementer\|fixer` | Запускает `make check` (линтер + типы + офлайн-тесты); красное → `exit 2`, агент **продолжает**, пока не позеленеет | механизм да (на тестовом гейте) |
| H6 | `gate-report.sh` | `SubagentStop` / `critic\|reviewer` | Проверяет, что файл отчёта есть и начинается с `VERDICT:`; иначе — «доработай» | механизм да |

H5 важен именно для вашего конвейера: фраза «тесты прошли» в отчёте имплементатора ничего не стоит, а гейт
запускает тесты сам. Он же решает проблему «имплементатор закончил на красном». Не тащить в H5 медленные
наборы: `make check` должен идти секунды–минуты; тяжёлое (`eval` качества ИИ, `NFR-12`) — не здесь.

Образец скрипта H5:

```bash
#!/usr/bin/env bash
# .claude/hooks/gate-impl.sh — SubagentStop для implementer и fixer
in=$(cat)
[ "$(jq -r '.stop_hook_active' <<<"$in")" = "true" ] && exit 0   # второй заход — не зацикливаем
cd "$CLAUDE_PROJECT_DIR" || exit 0
out=$(make check 2>&1) && exit 0
echo "make check красный. Исправь и повтори; не ослабляй проверки и не отключай тесты.
$(tail -60 <<<"$out")" >&2
exit 2
```

(`stop_hook_active` защищает от бесконечного цикла, но и означает: гейт блокирует **один** раз за остановку; если
после второго захода всё ещё красно, ревьюер поймает и это — дополнительно в оркестраторе: «после роли запусти
`make check` сам и сверь».)

### 4.4 Git-хуки (lefthook/husky) и как они сочетаются с хуками Claude

| Вариант | Суть | Плюсы | Минусы | Версия |
|---|---|---|---|---|
| lefthook | Один бинарник, конфиг `lefthook.yml`, параллельный запуск, фильтр по изменённым файлам встроен | Быстрый; один файл; ставится через npm | Postinstall должен выполниться: в новых pnpm нужно разрешить сборку зависимости или звать `lefthook install` в `prepare` [С] | 2.2.2, 2026-10-13, MIT [В] |
| husky | Тонкая обёртка: файлы-скрипты в `.husky/` | Очень распространён | Нет параллелизма и фильтра по файлам (нужен ещё lint-staged) | 9.1.7, 2026-09-02, MIT [В] |
| commitlint (для сообщений) | Проверка заголовка/тела по правилам | Стандарт де-факто | Node-зависимость | 21.2.4, 2026-10-18, MIT [В] |

**Рекомендация: lefthook + commitlint.** Проверено в одноразовом репозитории:

`lefthook.yml`

```yaml
commit-msg:
  commands:
    conventional:
      run: npx --no-install commitlint --edit {1}
pre-commit:
  parallel: true
  commands:
    size:
      run: scripts/check-commit-size.sh      # проверено: 900 строк → отказ
    # lint:  oxlint по {staged_files}        # [Н] синтаксис oxlint не проверял
    # fmt:   oxfmt --check по {staged_files} # [Н]
    # deps:  depcruise по затронутым модулям # [Н]
```

`commitlint.config.mjs` (проверено)

```js
export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'header-max-length': [2, 'always', 72],               // «≤ ~72 символов» из задания
    'scope-enum': [2, 'always', ['api','web','shared','db','agent','legal','infra','docs','deps','spec','research','process']],
    'subject-case': [0],                                  // русские темы — отключить проверку регистра
    'body-max-line-length': [1, 'always', 100],
  },
};
```

Находки при проверке:

- В **уже существующей** истории `yana/` есть `docs(research): …`, `docs(spec): …` и `chore: …` без scope —
  поэтому `scope-empty: never` отклонил бы три собственных коммита. Я оставил scope необязательным, но
  ограниченным списком (`spec`, `research`, `process` добавлены именно из-за истории). Ужесточить до
  «scope обязателен для `feat/fix/refactor/perf/test`» можно плагином commitlint [Н].
- Сообщение на русском с телом и хвостом `Co-Authored-By: …` проходит [В].
- `/home/user/University/CLAUDE.md` предписывает коммиты на русском; в истории так и есть. Тип и scope —
  латиницей (требование формата), тема — по-русски. Подтвердить (вопрос 5).
- «Не слишком большие и не слишком маленькие»: **большие** ловит `scripts/check-commit-size.sh` (считает
  изменённые строки индекса без lock-файлов; порог предупреждения 400, отказа 800 — я взял из установленного
  `code-review-and-quality`: ~100 хорошо, ~300 приемлемо, ~1000 слишком; подобрать под проект [Н]).
  **Мелкие** автоматически не ловятся; это правило процесса (каждый коммит — одна законченная мысль, тесты
  зелёные) + ось «читаемость» ревью.

Как два набора хуков сочетаются:

- **Настоящая проверка — git-хук**: он срабатывает на любой `git commit` (ваш и агента) и сообщение об ошибке
  Claude видит в выводе команды и исправляется [В — наблюдал `exit 1` и текст].
- **Хук Claude H1** лишь закрывает лазейки обхода (`--no-verify`, отключение хуков) и запрещает `push`. Не
  дублировать в нём разбор текста коммита: сообщения передают по-разному (`-m`, heredoc, `-F`), разбор хрупкий.
- Установка git-хуков — шаг `make setup`/`prepare` (NFR-14); если их забыли установить, гейт молча отсутствует —
  поэтому проверка наличия `.git/hooks/commit-msg` в `make check` — дешёвая страховка [Н].

### 4.5 Риски

- Хуки с `jq` — `jq` на машине есть [В]; в Docker-образах — отдельно.
- Скрипты H1/H3 — «разумная осторожность» на регулярках, не безопасная граница: агент может придумать обход
  (`bash -c "…"`). Настоящая граница — `permissions.deny` + git-хуки + ревью человеком.
- `PostToolUse`-хуки на каждую правку замедляют TDD; держать их в пределах секунды-двух.

## 5. Как совместить установленные скиллы и команды `as-*` с конвейером

### 5.1 Что установлено [В — прочитал]

25 скиллов `addyosmani/agent-skills` в `.claude/skills/`, команды `as-spec`, `as-plan`, `as-build`, `as-test`,
`as-review`, `as-code-simplify`, `as-ship`, `as-constraints`, `as-webperf`, справочники в `references/`
(`definition-of-done.md`, `testing-patterns.md`, `security-checklist.md`, `accessibility-checklist.md`,
`orchestration-patterns.md`…). Папки `.claude/agents/` и `.claude/settings.json` в проекте пока **нет**.

### 5.2 Что переиспользовать, что писать своё

| Что | Вердикт | Как |
|---|---|---|
| `as-spec`, `spec-driven-development`, `interview-me`, `idea-refine` | Использовать до конвейера | `SPEC.md` уже есть |
| `as-plan`, `planning-and-task-breakdown` | Использовать для плана | Формат задачи из скилла почти полный (описание, критерии, проверка, зависимости, файлы, размер); **расширить**: `ID`, `Требования: <ID из SPEC>`, `Модуль`, `Вне рамок`, `Риск: normal/high`, `Skills:`. Критик проверяет именно эти поля |
| `as-build` + `incremental-implementation` + `test-driven-development` | Содержание — в имплементатора, команду — не вызывать | Слэш-команды вызывает пользователь, не сабагент; скиллы подключаются через `skills:`. Цикл RED→GREEN→регрессия→сборка→коммит уже описан в `as-build` — повторить в промпте роли. `/as-build auto` остаётся для мелочей вне конвейера |
| `as-review` + `code-review-and-quality` | Ядро ревьюера | Пять осей и шкала Critical/Required/Optional/Nit — взять как есть; добавить шестую проверку «планка не занижена» (см. ниже) и формат `VERDICT:` |
| `constraint-driven-development` / `as-constraints` | **Очень полезен** | Главный риск конвейера «правка–ревью» — фиксер подавляет проверки (`@ts-ignore`, `skip`, ослабленные ассерты, снижение порога). Ревьюер и фиксер получают правило «планка в `CONSTRAINTS.md` не снижается»; `CONSTRAINTS.md` в корне — один из первых шагов |
| `doubt-driven-development` | Для задач `Риск: high` | Состязательная проверка в свежем контексте — по сути то, чем и должен быть критик/ревьюер на рискованных задачах (деньги, права, шифрование секретов NFR-16, миграции) |
| `debugging-and-error-recovery` | Фиксеру в preload | Причина, а не «замазывание» |
| `security-and-hardening`, `observability-and-instrumentation`, `frontend-ui-engineering`, `api-and-interface-design`, `performance-optimization`, `documentation-and-adrs` | По полю `Skills:` задачи | Не preload; роль вызывает скилл через `Skill`, если он указан в задаче |
| `source-driven-development` + Context7 | Имплементатору | Совпадает с вашим глобальным правилом `context7.md`; следите, чтобы MCP-инструменты были доступны роли (1.4) |
| `git-workflow-and-versioning` | Принципы взять, форму — свою | Размеры и атомарность совпадают с планом; формат коммита фиксируют хуки, не скилл |
| `references/definition-of-done.md` | Основа чек-листа ревьюера | Дополнить строками про «Кошт»: тесты офлайн (NFR-11), структурированные логи (NFR-15), i18n (NFR-19), доступность (NFR-20), секреты не в коде (NFR-16) |
| `as-ship` | Для релизов/показа, не для задач | Ссылается на персоны `code-reviewer`, `security-auditor`, `test-engineer`, которых в `.claude/agents/` **нет** (они поставляются плагином) — без них команда не заработает как задумано; фраза «subagents cannot spawn subagents» устарела |
| `references/orchestration-patterns.md` | Обновить после принятия решений | Устарели: запрет вложенности, «Explore работает на Haiku» (по документации — на основной модели; `Explore` с `model: haiku` можно задать своим файлом) |
| `using-agent-skills`, `context-engineering` | Не трогать | Мета-скиллы, к конвейеру не относятся |

**Писать своё:** четыре роли, `/task-cycle`, шаблоны отчётов, хуки H1–H6, правила модулей, `CLAUDE.md`,
`lefthook.yml`/`commitlint.config.mjs`, `CONSTRAINTS.md`, дополнения к формату задач.

### 5.3 Согласование с философией установленного каталога паттернов

В `orchestration-patterns.md` анти-паттерн C: «агент, сам вызывающий `/spec`, `/plan`, `/build` за пользователя —
убирает человеческие контрольные точки». Предложенный конвейер этому не противоречит: автоматизирован **один
шаг плана** (внутри задачи), а контрольные точки сохранены — остановка при вердикте критика ≠ `PROCEED`,
остановка после трёх неудачных ревью, ручное «да» на запуск следующей задачи и на слияние/`push`.

### 5.4 Риски

- Скиллы и справочники из чужого набора — «советы»; не превращать их в ритуал (каждая роль читает только своё).
- Критик, который «придирается ко всему», — реальный риск: ограничить критерии (см. образец) и счётчик
  «не более N замечаний уровня Required».

## 6. Модель фиксера

### 6.1 Что решаем и почему важно

Фиксер работает много раз; его модель определяет и стоимость, и качество правок. Правка по замечанию «в
`validate.ts:42` не учтена скидка, вот тест» — узкая, чётко поставленная задача; а «разорвать циклическую
зависимость между модулями» — уже проектирование.

### 6.2 Цены и варианты [В — pricing, 2026-10-24]

| Модель | Вход, $/МТок | Выход, $/МТок | Чтение кэша, $/МТок |
|---|---|---|---|
| Sonnet 5.5 | 2 | 10 | 0,10 |
| Opus 5.5 | 4 | 20 | 0,20 |
| Fable 5.1 (только явным выбором; может списываться с кредитов) | 10 | 50 | 0,25 |
| Haiku 5.5 | 0,10 (до 100К токенов в промпте) | 0,50 | 0,01 |

Opus 5.5 — ровно вдвое дороже Sonnet 5.5 за токен; сколько токенов потратит каждая — зависит от задачи
(цифр «в среднем» не выдумываю). Если вы работаете по подписке, а не по API, важнее лимиты Opus, чем доллары
(вопрос 1).

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| A. Всегда Sonnet | Дёшево, быстро | Точечные правки по ревью ему по силам; та же модель, что у ревьюера | «Слепые пятна» ревьюера и фиксера совпадают; сложные структурные правки могут не получиться и крутиться кругами |
| B. Всегда Opus | Максимум качества | Та же модель, что и имплементатор — понимает его замысел | Вдвое дороже на каждой мелкой правке; лимиты Opus |
| C. **Sonnet по умолчанию, Opus по условиям** | Эскалация | Деньги тратятся там, где нужен ум | Чуть сложнее оркестратору (таблица условий) |

### 6.3 Рекомендация: C

Фиксер = **Sonnet** (`effort: medium`; `high` при эскалации не нужен — Opus сам по себе другой класс).
Эскалация на **Opus** (разовое `model: "opus"` в вызове `Agent`, 2.6) если выполнено **любое**:

1. **Второй заход**: после правки Sonnet ревью всё ещё содержит Critical/Required (первая попытка не удалась).
2. Замечание помечено ревьюером `risk: high` — безопасность и секреты (NFR-16), права доступа, деньги и налоги
   (калькулятор вычетов, арифметика чека), миграции с риском потери данных, транзакции/параллелизм, защита от
   prompt injection.
3. Правка выходит за пределы одного модуля или требует менять публичную схему/интерфейс (нарушение границ
   dependency-cruiser чинится перестройкой, а не одной строкой).
4. Фиксер сам вернул `ESCALATE` («не воспроизвожу», «нужно проектное решение») — тогда сначала смотрит
   Opus, а при неразрешимости — пользователь.

Когда пересмотреть: если за 5–10 задач Sonnet-фиксер регулярно не проходит с первого раза — сделать Opus
значением по умолчанию; если ревьюер Sonnet пропускает ошибки, которые потом находит человек, — повысить
`effort` ревьюера или поставить ему Opus на задачах `Риск: high` (это ценнее, чем Opus в фиксере: найти
ошибку труднее, чем исправить названную).

Не рекомендую Haiku (риск тихих некачественных правок) и Fable (в 5 раз дороже Sonnet на входе, для правок избыточен).

Как проверить, что эскалация реально сработала: `/tasks` показывает модель активного агента (v2.1.242+) или
смотреть журнал сабагента в `~/.claude/projects/<проект>/<сессия>/subagents/`. Запасной вариант без зависимости от
параметра — два файла: `fixer.md` (sonnet) и `fixer-deep.md` (opus), общий промпт.

## 7. Образцы файлов (текст-пример, **в проекте не создавались**)

Общее для ролей: язык отчётов — русский; не выдумывать результаты (числа — из реальных запусков); все пути
передаёт оркестратор; ответ ≤10 строк, первая строка `VERDICT: …`.

### 7.1 `.claude/agents/critic.md`

```markdown
---
name: critic
description: Проверяет задачу плана ДО реализации. Вызывается командой /task-cycle, не вручную.
tools: Read, Grep, Glob, Write, mcp__context7__*
model: sonnet
effort: high
maxTurns: 20
skills:
  - planning-and-task-breakdown
---
Ты — критик задач проекта «Кошт». Ты НЕ пишешь код и НЕ правишь план: ты проверяешь,
стоит ли браться за задачу в том виде, как она записана, и пишешь отчёт.

Вход (даёт оркестратор): ID задачи, путь к tasks/todo.md и tasks/plan.md, путь для отчёта
tasks/reports/<ID>/01-critic.md.

Порядок:
1. Прочитай текст задачи, её зависимости (должны быть закрыты в todo.md), требования из SPEC.md
   по указанным ID, CLAUDE.md затронутых модулей и .claude/rules/*.md по путям из «Файлы».
2. Проверь по чек-листу (каждый пункт — «да/нет/частично» + одна строка доказательства):
   - Понятно ли, ЧТО считается готовым? Критерии приёмки проверяемы (число, статус, сообщение),
     а не «работает нормально»?
   - Покрыты ли граничные случаи и ошибки, названные в SPEC для этих требований?
   - Задача нужна? Её не закрывает уже сделанное / другая задача? Нет ли работы «наперёд»?
   - Нужно ли объединить с соседней (слишком мелкая) или разделить (>5 файлов, >~300 строк)?
   - Указаны ли команды проверки (какие тесты), модуль, риск (normal/high), нужные Skills?
   - Нужен ли ADR (решение, которое трудно откатить)? Есть ли конфликт с SPEC §10 (журнал решений)?
3. Не придирайся: замечание допустимо, только если из-за него имплементатор сделает не то или
   нельзя будет проверить результат. «Можно было бы красивее» — не замечание.
4. Запиши отчёт: вердикт, чек-лист, «Уточнения для имплементатора» (дополнения к критериям —
   они становятся частью контракта), предложения по изменению плана (если есть).

Вердикты (первая строка отчёта и ответа):
- PROCEED — можно реализовывать (с уточнениями или без).
- REVISE — задачу надо переписать (что именно).
- MERGE_WITH <ID> / SPLIT — слить или разделить.
- DROP — задача не нужна (почему).
- NEEDS_USER — нужно решение пользователя (сформулируй вопрос с вариантами и примером).

Ответ оркестратору: ≤10 строк: `VERDICT: …`, путь к отчёту, число замечаний.
Писать можно только в tasks/reports/ (остальное запрещено хуком).
```

Порядок:
1. Прочитай задачу, критерии приёмки, 01-critic.md, CLAUDE.md модулей и .claude/rules/*.md

   имя теста), список коммитов (`git log --oneline main..HEAD`), что НЕ сделано и почему,

Ответ оркестратору ≤10 строк: `VERDICT: DONE | BLOCKED`, путь к отчёту, число коммитов, статус make check.

```markdown

4. Если замечание неверно — не выполняй молча: в отчёте `DISPUTED` с аргументом и тестом/ссылкой.
   Если нужно проектное решение или не удаётся воспроизвести — `ESCALATE` с описанием.
5. Отчёт: таблица «замечание → статус (fixed/disputed/escalate) → коммит → тест», реальный вывод make check.

Ответ ≤10 строк: `VERDICT: FIXED | PARTIAL | ESCALATE`, путь, счётчики.
```

### 7.5 `.claude/commands/task-cycle.md`

```markdown
---
description: Выполнить одну задачу плана по конвейеру критик → имплементатор → ревьюер → фиксер
argument-hint: "<ID задачи, например T-012>"
disable-model-invocation: true
model: sonnet
---
Задача: $1. Текущая ветка: !`git branch --show-current`. Состояние дерева: !`git status --porcelain | head -20`

Ты ДИРИЖЁР, а не исполнитель: сам код не пишешь и не ревьюишь. Каждую роль вызывай инструментом
Agent с subagent_type, в foreground (run_in_background: false), и дожидайся ответа. Роли не
пересказывай: передавай им пути к файлам, читай только их короткий ответ (первая строка VERDICT).
Отчёты — в tasks/reports/$1/ (создай каталог).

0. Подготовка. Дерево должно быть чистым, задача $1 — в tasks/todo.md, зависимости закрыты.
   Иначе остановись и скажи пользователю, что именно не так. Если есть файлы отчётов — это
   возобновление: пропусти шаги, у которых вердикт уже получен.
1. critic → 01-critic.md. Вердикт не PROCEED → СТОП: покажи пользователю краткий итог и задай вопрос
   (инструмент AskUserQuestion; варианты и пример последствий простыми словами). План правит только он.
2. Создай ветку task/$1-<slug>. implementer → 02-impl.md. BLOCKED → СТОП, покажи причину.
3. reviewer (раунд 1) → 03-review-1.md.
4. Если CHANGES_REQUESTED: fixer (модель по умолчанию sonnet) → 04-fix-1.md, затем reviewer (раунд 2).
   Если и теперь есть Critical/Required, ИЛИ в ревью есть risk: high, ИЛИ fixer вернул ESCALATE,
   ИЛИ правка выходит за один модуль — второй fixer вызови с параметром model: "opus"
   (04-fix-2.md) и reviewer (раунд 3). Не больше 3 ревью и 2 правок: если замечания остались —
   СТОП и покажи пользователю остаток.
5. Сам проверь `make check` и `git log --oneline main..HEAD`. Запиши tasks/reports/$1/summary.md:
   что сделано по каждому критерию, коммиты, раунды ревью и число замечаний, что осталось, отклонения.
   Числа — только из реальных запусков.
6. Отметь задачу в tasks/todo.md ТОЛЬКО если последнее ревью APPROVE и make check зелёный.
7. Сообщи пользователю: краткий отчёт (до 15 строк), ветку, коммиты. Найди следующую незакрытую
   задачу с закрытыми зависимостями и спроси (AskUserQuestion): «Слить ветку и запустить T-…?» —
   варианты: слить и запустить следующую / слить и остановиться / не сливать. Слияние (--ff-only)
   и push — только после ответа «слить»; push не делай никогда без прямой просьбы.
```

### 7.7 Проверенные скрипты хуков и git

Все прогнаны на тестовых входах (коды выхода сверены). Лежат в стенде
`…/scratchpad/research-agent-process/{hooks,hooks2,repo}/`; здесь — полный текст, чтобы не зависеть от временной папки.

`.claude/hooks/guard-git.sh` (H1, `PreToolUse` / `Bash`; 10 случаев: нормальный коммит и `git log` проходят,
`--no-verify`, `-n`, `LEFTHOOK=0`, `push`, `reset --hard` блокируются)

```bash
#!/usr/bin/env bash
cmd=$(jq -r '.tool_input.command // empty')
deny() { echo "Заблокировано: $1" >&2; exit 2; }
if grep -Eq '(^|[;&|[:space:]])git[[:space:]]+(-[^[:space:]]+[[:space:]]+)*commit\b' <<<"$cmd"; then
  grep -Eq '(--no-verify|[[:space:]]-[a-zA-Z]*n[a-zA-Z]*[[:space:]])' <<<"$cmd" && deny "git commit --no-verify запрещён: хуки проверки обязательны"
  grep -Eq '(LEFTHOOK|HUSKY)=0|core\.hooksPath' <<<"$cmd" && deny "отключение git-хуков запрещено"
fi
grep -Eq 'git[[:space:]]+push' <<<"$cmd" && deny "git push — только по явной просьбе пользователя (NFR-17)"
grep -Eq 'git[[:space:]]+(reset[[:space:]]+--hard|clean[[:space:]]+-[a-z]*f|checkout[[:space:]]+--[[:space:]])' <<<"$cmd" && deny "разрушающая git-команда"
exit 0
```

`.claude/hooks/restrict-writes.sh` (H2, `PreToolUse` / `Write|Edit`; `../`-обход тоже ловится через `realpath -m`)

```bash
#!/usr/bin/env bash
in=$(cat)
agent=$(jq -r '.agent_type // empty' <<<"$in")
case "$agent" in critic|reviewer) ;; *) exit 0 ;; esac
path=$(jq -r '.tool_input.file_path // empty' <<<"$in")
root="${CLAUDE_PROJECT_DIR:-$PWD}"
abs=$(realpath -m -- "$path" 2>/dev/null || echo "")
case "$abs" in "$root"/tasks/reports/*) exit 0 ;; esac
echo "Роль $agent может писать только в tasks/reports/ (запрошено: $path)" >&2
exit 2
```

`.claude/hooks/reviewer-bash.sh` (H3, `PreToolUse` / `Bash`; белый список, запрет перенаправлений и изменяющих git-команд)

```bash
#!/usr/bin/env bash
in=$(cat)
[ "$(jq -r '.agent_type // empty' <<<"$in")" = "reviewer" ] || exit 0
cmd=$(jq -r '.tool_input.command // empty' <<<"$in")
if grep -Eq '(^|[^0-9&])>|>>|\btee\b|\bsed\b.*-i|\brm\b|\bmv\b|\bcp\b|\bgit +(add|commit|checkout|reset|stash|merge|rebase|push|restore|clean)\b|\$\(|`' <<<"$cmd"; then
  echo "Ревьюеру нельзя изменять файлы или историю: $cmd" >&2; exit 2
fi
ok='^(git (diff|log|show|status|blame|ls-files)|make (check|lint|typecheck|test)|pnpm (-r |--filter [^ ]+ )?(lint|typecheck|test|depcruise)|ls|cat|head|tail|wc|grep|rg|jq|sort|uniq|nl)( |$)'
while IFS= read -r part; do
  part=$(sed -E 's/^ +//' <<<"$part"); [ -z "$part" ] && continue
  grep -Eq "$ok" <<<"$part" || { echo "Команда вне белого списка ревьюера: $part" >&2; exit 2; }
done < <(sed -E 's/(\|\||&&|;|\|)/\n/g' <<<"$cmd")
exit 0
```

`scripts/check-commit-size.sh` (вызывается из `lefthook.yml`, `pre-commit`; 900 строк → отказ)

```bash
#!/usr/bin/env bash
set -euo pipefail
limit_warn=${COMMIT_WARN_LINES:-400}
limit_block=${COMMIT_MAX_LINES:-800}
n=$(git diff --cached --numstat -- . ':!pnpm-lock.yaml' ':!package-lock.json' ':!**/*.snap' \
    | awk '$1 ~ /^[0-9]+$/ {s += $1 + $2} END {print s+0}')
if [ "$n" -gt "$limit_block" ]; then
  echo "Коммит слишком большой: $n изменённых строк (лимит $limit_block). Разбей на части." >&2; exit 1
elif [ "$n" -gt "$limit_warn" ]; then
  echo "Предупреждение: $n изменённых строк (рекомендуемый максимум $limit_warn)." >&2
fi
```

Оговорки: `COMMIT_MAX_LINES=…` в `git commit` — это обход лимита; хук H1 такие переопределения не видит, при желании
добавить их в его запрет. Скрипты H5/H6 (`gate-impl.sh` — образец в 4.3; `gate-report.sh` — проверка `head -1` файла
отчёта на `VERDICT:`) в стенде не прогонялись, проверен только сам механизм `SubagentStop`+`exit 2`.

## 9. Стыковка с другими областями

- **Структура кода и монорепа:** от неё зависят названия модулей, `paths:` в правилах, `scope-enum` коммитов,
  `Files likely touched`.
- **Линтер/форматтер/границы (oxlint, oxfmt, dependency-cruiser):** команды попадут в `make check`, в хук H4 и
  `lefthook.yml`.
- **Тесты и eval:** гейт H5 запускает только быстрые офлайн-тесты (NFR-11); eval (NFR-12) — отдельной командой,
  вне гейта.
- **Docker/Makefile:** `make check`, `make setup` (установка git-хуков) — требования к Makefile.
- **Логирование/секреты:** правила `logging.md`, `security.md` и запрет чтения `samples/` (NFR-16, NFR-18).
