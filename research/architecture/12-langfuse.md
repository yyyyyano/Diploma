# 12. Langfuse для трасс ИИ: как подключить и не нарушить приватность

Область: решение пользователя «трассы ИИ хранить и смотреть в Langfuse (локально, self-hosted), а не в своих таблицах
Postgres». Требования: `LLM-05`, `LLM-06`, `OBS-03…05`, `ADM-20…22`, `PRIV-03`, `PRIV-06`, `PRIV-07`, решения `R23`, `R39`.
Опирается на отчёты 04 (слой ИИ, §5 «Трассировка») и 08 (наблюдаемость, решения 7–8); решение 10-consensus
«Vercel AI SDK» принято. Метки: **[В]** проверил сам, **[С]** косвенно (документация, без запуска), **[Н]** предположение.

**Что с проверкой на этой машине.** Docker здесь недоступен: Docker Desktop не запущен (`~/.docker/desktop/docker.sock`
нет), системный `dockerd` работает, но пользователь не в группе `docker` (`/var/run/docker.sock`: `root:docker`, `0660`).
`sudo` я не использовал, Docker Desktop не запускал. Поэтому **сам Langfuse не поднимался** — всё про его контейнеры,
ресурсы и интерфейс — по документации и исходникам (метка [С]). Зато я **запустил на настоящих пакетах** (`ai@7.0.152`,
`@langfuse/otel@6.0.2`, `@langfuse/vercel-ai-sdk@6.0.2`) цепочку «AI SDK 7 → OpenTelemetry → процессор Langfuse → HTTP»
на поддельной модели и поддельном приёмнике, и проверил приватность по-настоящему [В] (эксперименты в разделе 8).
Файл Compose для профиля прошёл `docker compose config` [В] (демон для этого не нужен).

## 0. Главное одним абзацем

Langfuse **можно** сделать местом просмотра трасс, и он совместим с приватностью — **но не «из коробки»**. Четыре вещи,
которых нет в рекламе и которые я нашёл при проверке:

1. **Маскирование на стороне клиента Langfuse не закрывает тексты AI SDK 7** [В]: функция `mask` у `LangfuseSpanProcessor`
   не трогает атрибуты `gen_ai.input.messages` / `gen_ai.output.messages` / `gen_ai.tool.call.*` — тексты уехали бы
   в Langfuse как есть. Нужен свой «охранник» на выходе (`PrivacyExporter`, раздел 4).
2. **Трасса AI SDK показывает текст до нашего маскирования** [В]: если маскирование ПДн (`PRIV-03`) сделано как обёртка модели
   (middleware), провайдер получил `[ИМЯ_1]`, а в трассе записано «Иван». Значит, в режиме разработки текст надо
   маскировать заново, в охраннике, а не рассчитывать, что «уже замаскировано».
3. **Автоудаление по сроку (data retention) в бесплатной версии Langfuse не работает** [В: код `entitlements.ts`, документация]:
   оно только в Enterprise (лицензионный ключ). «Не дольше 7 дней» (`OBS-05`) придётся обеспечивать своей ночной задачей
   через API удаления трасс (в бесплатной версии удаление трасс по API есть [В]).
4. **Даже с выключенными текстами в трассу попадает текст ошибки** [В]: сообщение исключения провайдера (`400: … Иванов Иван BY20…`)
   уходит в статус спана и в событие `exception`. Охранник вырезает и это.

Ещё два следствия: **Langfuse не должен быть единственным источником для админки** (`ADM-20`) и счётчиков лимитов (`LLM-05`):
профиль опционален (выключен по умолчанию), данные доезжают с задержкой, а лимиты нужны синхронно. Нужен тонкий журнал вызовов
в Postgres **без пользователя и без текстов** — он всё равно нужен для `LLM-05` (раздел 5). Это не «возврат к своим таблицам трасс»:
дерево шагов, просмотр и разбор живут в Langfuse, а в Postgres остаётся ~12 числовых колонок.

## 1. Что такое Langfuse self-hosted сегодня

**Версия и поддержка.** Langfuse **v4.69.0** от 2026-10-23, релизы выходят почти ежедневно (4.64 → 4.69 за 5 дней) [В: GitHub releases].
Репозиторий — 36 тыс. звёзд, коммит от 2026-10-24; в `LICENSE` — «© 2023–2026 ClickHouse, Inc.» [В].
Образы на Docker Hub (сжатые, amd64): `langfuse/langfuse` (web) **302 МБ**, `langfuse/langfuse-worker` **368 МБ** [В: Docker Hub API].

**Лицензия.** MIT для всего, кроме каталогов `ee/`, `web/src/ee/`, `worker/src/ee/`, `packages/shared/src/server/ee/` [В: `LICENSE`].
Функции, требующие лицензионный ключ (EE) [В: документация `license-key`]: роли на уровне проекта, защищённые метки промптов,
**политики хранения данных (data retention)**, журнал аудита, **серверное маскирование**, кастомизация UI, API управления
организациями/SCIM, режим FIPS. Всё остальное «без ограничений». Мы EE не используем; ключ не нужен.
Проверка в коде: в тарифе `oss` есть `trace-deletion`, `scheduled-blob-exports`, `in-app-agent`; `data-retention` — только
`self-hosted:enterprise` [В: `web/src/features/entitlements/constants/entitlements.ts`]; в `initialize.ts` переменная
`LANGFUSE_INIT_PROJECT_RETENTION` молча игнорируется без этого права [В].

**Состав (официальный `docker-compose.yml` из репозитория, на сегодня)** [В]:

| Контейнер | Образ в compose Langfuse | Зачем |
|---|---|---|
| `langfuse-web` | `langfuse/langfuse:4` | сайт и API приёма трасс (порт 3000) |
| `langfuse-worker` | `langfuse/langfuse-worker:4` | фоновая обработка: приём, оценки, экспорт, удаление |
| `postgres` | `postgres:17` | пользователи, проекты, ключи API, настройки (не трассы) |

Итого **6 контейнеров** в официальном compose (в моём варианте 7 — с одноразовым созданием ведра) — как и писал отчёт 04. Без S3 и без ClickHouse Langfuse v4 не работает.
Требования к версиям v4: PostgreSQL ≥ 15 (рекомендуется 16), ClickHouse ≥ 25.12 (рекомендуется 26.4), Redis ≥ 7 (рекомендуется 7.2) или
**Valkey ≥ 8 — официально поддержан** [В: документация инфраструктуры].

**Минимальные ресурсы (документация)** [В]: web 2 CPU / 4 ГиБ, worker 2 / 4, Postgres 2 / 4, Redis 1 / 1,5, ClickHouse 2 / 8,
blob-хранилище 2 / 4 — это «минимум для продакшена». Для виртуалки с Docker Compose рекомендуют «≥ 4 ядра и 16 ГиБ». Compose
Langfuse сам называет себя «без высокой доступности, масштабирования и резервного копирования» — для локальной работы это нормально.
Это числа для боевой нагрузки; реальный расход простаивающего Langfuse на ноутбуке я **не мерил** (нет Docker) — оценка в разделе 6 [Н].

### 1.1 Решение: где хранить и смотреть трассы

**Что решаем.** Пользователь хочет Langfuse как «профессиональный» вариант. Вопрос — делать ли его *единственным* хранилищем
или оставить рядом тонкий журнал в Postgres. Пример: админ открывает «Запросы к ИИ» (`ADM-20`), когда Langfuse выключен
(он в профиле, не по умолчанию) — страница должна показать числа, а не ошибку.

| | Суть | Плюсы | Минусы | SPEC |
|---|---|---|---|---|
| **A. Только Langfuse** (решение пользователя буквально) | Админка читает Public API Langfuse, лимиты — тоже из него | Один источник; ничего не дублируем | Админка и `LLM-05` зависят от 7 контейнеров и от задержки приёма; без профиля `ADM-20` пуст; удаление по `PRIV-06` асинхронное; лимиты по минутам нельзя считать из аналитики с задержкой | `ADM-20` ⚠, `LLM-05` ✘ |
| **B. Langfuse для трасс + тонкий журнал вызовов в Postgres** (рекомендую) | Один хук AI SDK пишет и в Langfuse (если включён), и строку-метаданные в Postgres (всегда). В журнале нет ни текста, ни пользователя | `ADM-20/21` и `LLM-05` работают всегда и офлайн; Langfuse — для разбора агента и показа на защите; приватность проверяется тестом | Два места записи (но один хук, ~60 строк) | `LLM-05/06`, `OBS-03/04`, `ADM-20…22`, `PRIV-06/07` ✔ |
| **C. Только свои таблицы** (прежняя рекомендация 04/08) | Всё в Postgres, свой экран | Ноль новых контейнеров; текст записать нельзя по построению | Нет дерева трасс и «профессионального» просмотра; решение пользователя не выполнено | ✔ |

**Рекомендация: B.** Это исполняет решение пользователя («трассы смотреть в Langfuse»), но не делает Langfuse точкой отказа
для админки и лимитов. Журнал в Postgres нужен **в любом случае** для `LLM-05` (раздел 5.2), так что это не лишняя работа.
**Что изменило бы выбор:** если пользователь согласен, что `ADM-20` работает только при запущенном профиле `observability` — тогда
A проще (раздел 5.1 описывает, как читать Metrics API).

**Стыковка.** От бэкенда (08): сквозной `request_id` (AsyncLocalStorage) кладём в спан как атрибут; от слоя ИИ (04): единственная
точка вызова моделей — `LlmGateway` (иначе охранник обойдут); от тестов: канарейка-тест трассы (раздел 4.5). **Риск:** две записи
могут разойтись (например, Langfuse был выключен) — это нормально, журнал считается эталоном для цифр, Langfuse — для разбора.

## 2. Инфраструктура Langfuse: Postgres, S3, Redis

### 2.1 Postgres: наш или отдельный

Langfuse использует схему `public` выбранной базы и **поддерживает Postgres ≥ 15 (рекомендует 16)** [В: документация]. Технически можно
завести в нашем Postgres отдельную базу `langfuse` и роль `langfuse` (наш Postgres 17/18 подходит).

| | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Отдельный контейнер `langfuse-db`** (рекомендую) | `postgres:17-alpine` в профиле `observability` | Профиль включается и выключается, не трогая основную БД; `make db-reset` не стирает Langfuse и наоборот; миграции Langfuse (Prisma) не ходят рядом с нашими; ноль связей с `compose.yaml` без профиля; ~+60–100 МБ ОЗУ [Н] | Ещё один контейнер |
| B. Отдельная база в нашем Postgres | `CREATE DATABASE langfuse` | Один процесс Postgres | Базу надо создавать скриптом (init-скрипты образа работают только на пустом томе); профиль зависит от основной БД; общий потолок ОЗУ и версий |

**Рекомендация: A** — изоляция важнее 100 МБ. В Postgres Langfuse **трасс нет** (они в ClickHouse), там пользователи/проекты/ключи [В].

### 2.2 S3-хранилище (MinIO заархивирован)

**Факты.** MinIO: репозиторий `minio/minio` **заархивирован** (последний коммит 2026-04-24) [В: GitHub API]. Но официальный compose Langfuse
сегодня **всё ещё использует MinIO** (сборка Chainguard `cgr.dev/chainguard/minio`) [В]. Документация Langfuse называет **SeaweedFS** и
**MinIO/AIStor** «официально поддерживаемыми» для самохостинга и рекомендует «SeaweedFS или MinIO» [В]. Helm-чарт Langfuse по
умолчанию разворачивает SeaweedFS (`chrislusf/seaweedfs`, режим allInOne) [В: `langfuse-k8s` values.yaml]. **S3 обязателен:** «Langfuse needs
an S3 bucket to upload raw event information» — переменные `LANGFUSE_S3_EVENT_UPLOAD_*` обязательны в каждом развёртывании [В]; режима
«без S3» и «локальная папка» в документации нет — обойтись без S3 нельзя [В].

| Вариант | Суть | Плюсы | Минусы | Зрелость, лицензия | Поддержка в Langfuse |
|---|---|---|---|---|---|
| **A. SeaweedFS** (рекомендую) | один контейнер `server -s3`, порт 8333 | Официально поддержан и используется в их Helm; живой проект | Ведро нужно создать (одноразовый контейнер); я его **не запускал** [С] | v4.49 (2026-10-23), образ `chrislusf/seaweedfs:4.48_large_disk` 194 МБ [В]; **Apache-2.0** [В] | Official |
| B. MinIO (Chainguard-сборка из compose Langfuse) | как у Langfuse | Работает «из коробки» по их compose | Проект заархивирован (нет исправлений безопасности от авторов); AGPL-3.0 [В]; образ собирает Chainguard — зависимость от стороннего форка | archived 2026-04-24 | Official (формально) |
| C. RustFS | S3-совместимый, Rust | Apache-2.0 [В], v1.0.3 (2026-10-17) [В], образ 115 МБ [В] | В документации Langfuse не упомянут → «любой S3-совместимый» = best effort (community); не проверял | молодой (1.0.x) | Community |
| D. Garage | лёгкое S3-хранилище | Очень малый расход [Н] | Лицензия AGPL-3.0 [Н]; в документации Langfuse не упомянут; совместимость с `DeleteObjects` не проверена | — | Community |

**Рекомендация: A (SeaweedFS), версия закреплена тегом.** Причина: официально поддержан Langfuse и не заархивирован. Проект у нас локальный,
AGPL от MinIO нам не мешает юридически, но архивность — реальный риск. **Что проверить при внедрении (я не мог):** что `weed shell` создаёт ведро
так, как в моём фрагменте Compose (метка [Н]), и что удаление трасс стирает файлы событий (Langfuse вызывает `DeleteObjects`; для
старых MinIO нужна переменная `LANGFUSE_S3_DELETE_OBJECTS_CHECKSUM_ALGORITHM=MD5`; со SeaweedFS в документации этого нет).
Ведро версионирования не включать. **Заметка:** физическое освобождение места в SeaweedFS после удаления идёт при уплотнении томов, не мгновенно [Н].

### 2.3 Redis / Valkey и ClickHouse

- **Valkey 8** (`valkey/valkey:8-alpine`, 17 МБ, BSD-3) вместо `redis:7`: официально поддержан Langfuse («Valkey ≥ 8 — Official») [В].
  Redis 8 сменил лицензию (не чисто BSD) — [Н], не вдавался; Redis 7 тоже годится (его использует compose Langfuse).
  Обязательно `--maxmemory-policy noeviction` и пароль; сохранение на диск можно выключить (`--save ""`): тогда при перезапуске Valkey события, ещё не записанные
  в ClickHouse, пропадут — для режима разработчика приемлемо [Н].
- **ClickHouse 26.4** (257 МБ; документация: «≥ 25.12, 26.4 рекомендуется») [В]. Нужен часовой пояс UTC (по умолчанию так) [В].
  ClickHouse по умолчанию стремится занять до ~90% доступной памяти [С] — **обязателен `mem_limit`** в Compose (раздел 6).

## 3. Подключение к Vercel AI SDK 7

### 3.1 Что изменилось в AI SDK 7

В AI SDK 7 телеметрия — это **колбэки** (`registerTelemetry(...)`), а не флаг `experimental_telemetry` из v6 [В: документация Langfuse и
Context7 `/vercel/ai/ai_7.0.0`]. `registerTelemetry(...integrations)` принимает **несколько** интеграций сразу [В: `index.d.ts`], а
`telemetry.integrations` на конкретном вызове перекрывает глобальные [В]. Это важно: **наш хук для журнала в Postgres и интеграция Langfuse
работают одновременно**, не мешая друг другу. Настройки на вызов: `telemetry: { isEnabled, functionId, recordInputs, recordOutputs,
includeRuntimeContext, integrations }`.

### 3.2 Какие пакеты

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. `@langfuse/vercel-ai-sdk` 6.0.2 + `@langfuse/otel` 6.0.2 + `@langfuse/tracing`** (рекомендую) | Официальная интеграция Langfuse для AI SDK 7: класс `LangfuseVercelAiSdkIntegration` + процессор `LangfuseSpanProcessor` | Документирована; тонкая обёртка над `@ai-sdk/otel` (добавляет только связь с `langfusePrompt`) [В: чтение `dist/index.mjs`]; `propagateAttributes` для сессии/тегов; +26 пакетов / +≈41 МБ к `ai` [В: `npm i`] | Требует Node ≥ 22 (у нас 24 — ок) |
| B. Только `@ai-sdk/otel` 1.0.152 + любой OTLP-экспортёр на `/api/public/otel/v1/traces` | Без пакетов Langfuse | Меньше зависимостей | Теряем `propagateAttributes` и сопоставление атрибутов на стороне клиента; больше ручного кода |

**Рекомендация: A.** Версии на сегодня (все MIT, кроме `ai` — Apache-2.0): `ai` 7.0.152, `@langfuse/*` 6.0.2 (2026-10-22),
`@ai-sdk/otel` 1.0.152, `@opentelemetry/sdk-trace-node` 2.12.0 [В: `npm view`].

**Ловушка зависимостей (проверено, ломает импорт) [В].** Сегодня OpenTelemetry JS выпустил линию 3.x / 0.300.0 (`@opentelemetry/api` 1.10.0),
а `@langfuse/otel` 6.0.2 и `sdk-trace-node` 2.12 ещё ждут `@opentelemetry/api` < 1.10. Если поставить `@opentelemetry/exporter-trace-otlp-http`
«последней» (0.300.0), то (а) `npm` отказывается ставить (ERESOLVE), (б) `pnpm` ставит с предупреждением — и **`import '@langfuse/otel'` падает**
(`SyntaxError: … '@opentelemetry/api' does not provide an export named 'SeverityNumber'`). Рабочий набор, проверенный и под `npm`, и под `pnpm`
(команда `pnpm peers check` — «No peer dependency issues»):

```

@opentelemetry/sdk-trace-node@2.12.0   @opentelemetry/api@1.9.1
@opentelemetry/exporter-trace-otlp-http@0.223.0     # ← ровно эта, НЕ 0.300.0
```

В монорепозитории: закрепить в каталоге версий (`catalog:`) / `overrides` и написать рядом комментарий «снять, когда Langfuse обновит peer-зависимости».
`@opentelemetry/sdk-trace-node` помечен устаревшим («используйте `@opentelemetry/sdk-trace`») — у Langfuse в документации по-прежнему он.

### 3.3 Как выглядит подключение

```ts
// apps/api/src/observability/tracing.ts — выполняется один раз при старте, ДО первого вызова модели
import { registerTelemetry } from "ai";
import { LangfuseSpanProcessor } from "@langfuse/otel";
import { LangfuseVercelAiSdkIntegration } from "@langfuse/vercel-ai-sdk";
import { NodeTracerProvider } from "@opentelemetry/sdk-trace-node";

export function setupTracing(cfg: Config, ledger: LedgerWriter) {
  // 1) Журнал в Postgres работает всегда (LLM-05, ADM-20): число-метаданные, без текста и без пользователя.
  registerTelemetry(new LedgerTelemetry(ledger));

  // 2) Langfuse — только если включён профиль observability (в конфигурации есть адрес и ключи).
  if (!cfg.langfuse) return;
  const exporter = new PrivacyExporter(cfg.devTrace, cfg.masker, new OTLPTraceExporter({
    url: `${cfg.langfuse.baseUrl}/api/public/otel/v1/traces`,
    headers: { Authorization: basic(cfg.langfuse), "x-langfuse-ingestion-version": "4" },
  }));
  const processor = new LangfuseSpanProcessor({
    exporter, exportMode: "batched",
    environment: cfg.devTrace ? "dev-full" : "normal",   // фильтр в интерфейсе Langfuse
    publicKey: cfg.langfuse.publicKey, secretKey: cfg.langfuse.secretKey, baseUrl: cfg.langfuse.baseUrl,
  });
  new NodeTracerProvider({ spanProcessors: [processor] }).register();
  registerTelemetry(new LangfuseVercelAiSdkIntegration());
}
```

На вызове (в `LlmGateway`, единственном месте вызова моделей):

```ts
generateText({ model, messages, tools,
  telemetry: { functionId: task, recordInputs: cfg.devTrace, recordOutputs: cfg.devTrace }, // слой 1
  // runtimeContext НЕ передаём в telemetry: по умолчанию туда попадает только то, что помечено includeRuntimeContext [В]
});
```

Что видно в Langfuse, проверено на поддельной модели с двумя шагами агента и вызовом инструмента [В]: корневой спан `invoke_agent`, спаны
`step 1/2`, `chat <модель>` (провайдер, модель, токены вход/выход/кэш, причина завершения, длительность), `execute_tool <имя>`;
токены читаются из `gen_ai.usage.*` (сервер Langfuse понимает и `gen_ai.usage.input_tokens`, и старые `ai.usage.*` [В: `OtelIngestionProcessor.ts`]).
Ошибка провайдера → спан со статусом ERROR.

**Пользователь и сессия.** `propagateAttributes({ traceName, userId, sessionId, tags, metadata }, () => generateText(...))` кладёт их на все
вложенные спаны [В: документация]; сервер Langfuse читает `user.id`, `session.id` [В: код]. Как мы это используем — раздел 4 (в обычном режиме
`userId` **не передаём вообще**).

**Падение Langfuse не ломает приложение** [В]: при недоступном адресе (`127.0.0.1:9`) `generateText` вернулся за 12 мс, процесс не упал,
исключений нет (экспорт идёт фоном, таймаут по умолчанию 5 с).

### 3.4 Токены и «условная стоимость» для бесплатных и локальных моделей

Langfuse считает стоимость по таблице **определений моделей** (Настройки проекта → Models): имя модели сопоставляется регулярным выражением
(`match_pattern`), цена задаётся на токен ввода/вывода; **свои определения приоритетнее встроенных** [В: документация]. Это ровно «условная
стоимость» (`ADM-20/21`): для `openai/gpt-oss-120b` ставим $0,15 / $0,60 за млн токенов (цифры из отчёта 04), для Z.ai и локальных — 0.
Нюансы:

- **Цена применяется только к новым трассам** (стоимость считается при приёме и не пересчитывается задним числом) [В: документация] — в отличие от ADM-21,
  где админ правит цену и хочет видеть новую цену в отчёте. Поэтому «настоящая» условная стоимость для админки считается **у нас** в журнале
  (по таблице цен ADM-21 в момент записи), а Langfuse — справочная.
- Определения можно создавать и **идемпотентно обновлять через API**: `PUT /api/public/models/{id}` (создать или заменить определение проекта;
  встроенные менять нельзя), `GET/POST/DELETE` тоже есть [В: `fern/.../models.yml`, документация описывает без PUT]. Команда `make langfuse-seed` может переносить
  таблицу цен ADM-21 в Langfuse — необязательное удобство.
- Токены локальных моделей приходят из ответа `llama-server`; у OpenAI-совместимых адаптеров нужен `includeUsage: true` при стриминге (отчёт 04, §5.4) [В].
  Если токены не пришли — Langfuse попытается посчитать токенайзером только для `gpt*`/`claude*`, для остальных получится пусто [В: документация].

## 4. Приватность: как совместить Langfuse с `OBS-04/05`, `PRIV-03/06/07`

### 4.1 Что проверено экспериментально [В]

Поддельная модель (`MockLanguageModelV4`) в «Groq-подобной» роли, два шага: инструмент с аргументом-IBAN, затем ответ с ФИО. Чем «заражаем»:
в запросе «Иван Иванов, счёт BY20OLMP…», в аргументе инструмента IBAN, в ответе ФИО и сумма, runtimeContext с email, и отдельный прогон, где
провайдер бросает ошибку с ФИО и IBAN в тексте. Смотрю, что получает экспортёр Langfuse и что уходит по сети.

| Режим | Что попало в экспорт |
|---|---|
| по умолчанию (`telemetry` без флагов) | **Всё**: `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.tool.call.arguments/result` с ФИО и IBAN; в сети — тоже |
| `recordInputs: false, recordOutputs: false` | Текстовые атрибуты **пропали**, токены/модель/провайдер/длительность остались. `runtimeContext` с email не просочился (он отключён по умолчанию) |
| то же, но провайдер бросает ошибку с ПДн | **Утечка**: `status.message` и событие `exception` содержат ФИО и IBAN (на 3 спанах из 3) |
| `LangfuseSpanProcessor({ mask })` без отключения записи | **Не маскирует**: `gen_ai.*` остаются как были — `mask` применяется только к полям `langfuse.observation.input/output` и метаданным |
| обёртка-«охранник» (белый список атрибутов + удаление событий и сообщения статуса) | Утечек нет ни в атрибутах, ни в событиях, ни в сетевых байтах; ошибка остаётся статусом без текста |
| маскирование ПДн как middleware модели | Провайдер получил `Привет, я [ИМЯ_1]`, **а в трассе записано `Привет, я Иван`** |

Вывод: одной настройки SDK мало; нужен охранник на границе «наше приложение → Langfuse».

### 4.2 Решение: как гарантировать «нет текстов» в обычном режиме

| | Суть | Плюсы | Минусы |
|---|---|---|---|
| A. Только `recordInputs/recordOutputs: false` | Флаги AI SDK | Одна строка; официальный способ | Не закрывает текст ошибок [В]; зависит от того, что каждый вызов передаёт флаги (забыли в одном месте — утечка); новые атрибуты будущих версий не покрыты |
| **B. Слой 1 (флаги) + слой 2 (`PrivacyExporter` — белый список)** (рекомендую) | Экспортёр-обёртка перед OTLP: пропускает **только** перечисленные атрибуты, режет события и сообщение статуса | Защита по построению: незнакомый атрибут просто не уйдёт; единственная точка проверки; тестируется офлайн | ~60 строк своего кода; придётся следить за обновлениями AI SDK (белый список расширяем сознательно) |
| C. Серверное маскирование Langfuse (EE) | Колбэк `LANGFUSE_INGESTION_MASKING_CALLBACK_URL` | Централизованно | **Требует лицензию EE** [В]; по умолчанию «открытый отказ» (при сбое пишет без маскирования); данные до маскирования лежат в S3 |

**Рекомендация: B.** Объяснение простыми словами: флаги — это «просьба не писать», белый список — «замок»: даже если кто-то забудет флаг или AI SDK
добавит новый атрибут с текстом, наружу уйдёт только то, что мы явно разрешили.

Эскиз (проверено на поддельных данных: экспортёр-обёртка и процессор-вариант оба закрыли утечки) [В]:

```ts
const ALLOW = /^(gen_ai\.(operation|provider|request\.model|response\.(model|id|finish)|usage|tool\.name)|langfuse\.(trace\.(name|tags)|environment)|kosht\.)/;
const TEXT  = /^gen_ai\.(input\.messages|output\.messages|system_instructions|tool\.call\.(arguments|result))$/;

class PrivacyExporter implements SpanExporter {
  constructor(private dev: boolean, private mask: (s: string) => Promise<string>, private inner: SpanExporter) {}
  async export(spans: ReadableSpan[], done: (r: ExportResult) => void) {
    const clean = await Promise.all(spans.map((s) => this.sanitize(s)));
    this.inner.export(clean, done);
  }
  private async sanitize(s: ReadableSpan): Promise<ReadableSpan> {
    const attrs: Record<string, unknown> = {};
    for (const [k, v] of Object.entries(s.attributes)) {
      if (ALLOW.test(k)) attrs[k] = v;                                   // метаданные — пропускаем
      else if (this.dev && TEXT.test(k) && typeof v === "string") attrs[k] = await this.mask(v); // режим разработки: тексты, но маскированные
    }
    // в обычном режиме — ни событий exception, ни текста ошибки; в режиме разработки текст ошибки тоже маскируем
    const status = s.status.message && this.dev ? { ...s.status, message: await this.mask(s.status.message) } : { code: s.status.code };
    return Object.create(s, { attributes: { value: attrs }, events: { value: [] }, status: { value: status } });
  }
  shutdown() { return this.inner.shutdown(); }
  forceFlush() { return this.inner.forceFlush?.() ?? Promise.resolve(); }
}
```

Экспортёр (в отличие от процессора) может быть **асинхронным** — это важно, потому что маскер из отчёта 04 (русская NER, 30–150 мс на строку) асинхронный.

### 4.3 Два режима и их переключение (`OBS-03/05`, `R39`)

| | Обычный режим (по умолчанию) | Режим разработки (`KOSHT_DEV_TRACE=1`, только конфигурация) |
|---|---|---|
| Флаги `recordInputs/Outputs` | `false` | `true` |
| Что уходит в Langfuse | только метаданные: задача, провайдер, модель, локальная/облачная, токены, время, ошибка **без текста**, названия инструментов | + тексты запросов, ответов, аргументов и результатов инструментов — **после `PRIV-03`-маскирования**, и для облачных, и для локальных моделей (как требует `OBS-05`) |
| `userId` / `sessionId` в трассе | **не передаём** | `userId = HMAC-SHA256(секрет_установки, внутренний_id)` (псевдоним), `sessionId` = внутренний id диалога |
| Среда (`environment`) в Langfuse | `normal` | `dev-full` (видно в фильтре) |
| Админка | баннера нет | баннер «режим разработки» по флагу конфигурации (`ADM-60`); из админки не включается |

Переключатель — только переменная окружения/файл конфигурации (как уже решено в отчёте 08): ни кнопки, ни таблицы настроек. Доступ к интерфейсу Langfuse — отдельная
учётная запись (не пользователь «Кошта»); из админки «Кошта» ссылки на Langfuse нет.

### 4.4 Доступ, срок хранения, удаление

**Доступ только разработчику** [В/С]: порт `127.0.0.1:3001` (в моём Compose `ports: ["127.0.0.1:3001:3000"]`), остальные контейнеры портов наружу не
публикуют; `AUTH_DISABLE_SIGNUP=true` (никто не зарегистрируется); первая учётная запись и ключи создаются при старте переменными `LANGFUSE_INIT_*`
(пароль и ключи — случайные, из `.env`, вне git); `TELEMETRY_ENABLED=false` — иначе веб-контейнер раз в 12 часов шлёт на `eu.posthog.com`
агрегаты, в том числе «до 30 почтовых доменов из таблицы пользователей» (почты не отправляются) [В: документация telemetry]; `LANGFUSE_DISABLE_SIGNUP_ONBOARDING=true`
(в браузере после регистрации Langfuse обращается к `langfuse.com`). Неотключаемо: проверка обновлений — запрос веб-контейнера на `langfuse.com` при
открытии интерфейса, «падает мягко» без интернета [В]. Образы по умолчанию тянутся через `docker.langfuse.com` (прокси аналитики Reo.dev, записывает
факт скачивания) — в моём Compose имена **Docker Hub напрямую**, без этого префикса [В: документация контейнеров].

**Срок хранения (`OBS-05`: «не дольше 7 дней»).** Встроенное «Data Retention» — только EE (минимум 3 дня) [В]. В бесплатной версии:

| | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Своя ночная задача** (рекомендую) | Задача pg-boss/`make trace-prune`: читает корневые наблюдения `GET /api/public/v2/observations?isRootObservation=true&toStartTime=<сейчас−7 дней>` курсором и удаляет пачками `DELETE /api/public/traces {traceIds}` (до 1000 за раз) | Работает в OSS; покрывает ClickHouse **и** файлы событий в S3 (удаление трасс убирает записи «во всех хранилищах» [В: документация + `ingestionFileDeletion.ts`]) | Нужен запущенный Langfuse; удаление асинхронное — «обычно в течение 15 минут», подтверждения нет [В]; физически место освобождается при слияниях ClickHouse/уплотнении SeaweedFS [Н] |
| B. Стирать тома целиком | `make observability-reset` | Железно | Теряем всё, не только старше 7 дней |
| C. Ключ EE | `LANGFUSE_EE_LICENSE_KEY` | Встроенный механизм | Платная лицензия; телеметрия лицензии нельзя отключить [В] |

**Рекомендация: A + проверка при старте приложения** (если режим разработки выключен, а в `dev-full` остались трассы старше 7 дней — удалить и записать в журнал `OBS-07`).
Если пользователь выключил режим разработки — трассы `dev-full` доживают свои 7 дней и стираются задачей.

**Удаление данных пользователя (`PRIV-06`)**: в обычном режиме в Langfuse **нет пользователя вообще** (нечего связывать) — удалять нечего.
В режиме разработки: при удалении аккаунта вычисляем тот же HMAC-псевдоним, ищем `GET /api/public/v2/observations?userId=<псевдоним>` (фильтр `userId`
есть, `fields=core` — без текстов), собираем `traceId`, `DELETE /api/public/traces`, проверяем повторным запросом (асинхронно). Ограничение: удаление трасс **не** трогает
другие объекты (датасеты и т. п.) — мы их не используем; запрещаем создание датасетов в Langfuse. Кроме того, раз всё равно ≤ 7 дней — остаточный риск ограничен.
КП из SPEC («после удаления аккаунта ни в одной таблице и папке…») проверяется тестом с канарейкой в режиме разработки.

### 4.5 Автотест приватности (без Langfuse, офлайн)

Тот же приём, что в моих экспериментах: `MockLanguageModelV4` + запоминающий экспортёр на месте `OTLPTraceExporter`, заведомо уникальные «канарейки»
(`CANARY-IBAN-…`, `CANARY-FIO-…`), два прогона: обычный режим → в атрибутах, событиях, статусе и сериализованных байтах канарейки **нет**; режим разработки →
канареек нет, но есть метки `[СЧЁТ_1]`, `[ИМЯ_1]` (`КП` «в трассе облачного запроса нет номера счёта, ФИО и телефона»). Проверка падающей модели (ошибка с ПДн). Обычные тесты остаются
офлайн (`QA-01`).

### 4.6 Что остаётся несовместимым с буквой SPEC

1. **`OBS-05` и `R39` говорят «в отдельный файл»** — а Langfuse не файл. Предлагаю переформулировать: «в отдельное хранилище трасс разработчика (Langfuse на 127.0.0.1),
   не в админку, ≤ 7 дней (ночная очистка)». Требования `PRIV-07` и «отдельно от админки» сохраняются по духу.
2. **`PRIV-07` «ни через интерфейс, ни через логи»**: Langfuse — второй интерфейс. В обычном режиме текстов там нет, поэтому не нарушает. В режиме разработки их видит тот, у кого
   пароль Langfuse, — то есть разработчик, который и так сам включил режим (как и в `OBS-05`).
3. **`ADM-20` не должна зависеть от Langfuse** (раздел 5.1) — иначе при выключенном профиле страница пуста.
4. **Интерфейс Langfuse — только на английском** [Н: русской локали в документации нет]. Требование «интерфейс на русском» относится к продукту; Langfuse — инструмент разработчика. Нужно подтверждение пользователя.

## 5. Админка «Запросы к ИИ» и лимиты тарифов

### 5.1 Откуда `ADM-20`

**Что решаем.** Страница «Запросы к ИИ»: запросы, токены, условная стоимость, время, доля ошибок — за период, по задачам и по провайдерам; облачные/локальные; расход
дневных лимитов; список последних вызовов с названиями инструментов, без текстов.

| | Суть | Плюсы | Минусы |
|---|---|---|---|
| A. Из Langfuse (Metrics API v2 + Observations API v2) | Бэкенд ходит в `GET /api/public/v2/metrics` и `/v2/observations?fields=core,basic,usage` (без `input/output`) | Агрегаты «из коробки»: сумма/число/задержка/токены, группировка по `providedModelName`, `traceName`, `tags`, `environment`, `level` (ошибки), `userId`, `toolNames` [В: `dataModel.ts`]; в v4 лимит строк 100–1000 [В] | Работает только при запущенном профиле (ключ и 7 контейнеров); данные «в реальном времени» только с заголовком `x-langfuse-ingestion-version: 4` (мы его ставим) [В]; нет измерения «провайдер» отдельно от модели — придётся класть в теги; «расход дневных лимитов» всё равно считать самим |
| **B. Из журнала в Postgres** (рекомендую) | Тонкая таблица `ai_call`: время, задача, провайдер, модель, локальная/облачная, статус, код ошибки, токены вход/выход/кэш, длительность, условная стоимость, `fallback_from`, `run_id`; рядом `ai_tool_call` (имя инструмента, ok, мс) | Работает всегда и офлайн; `ADM-20` — обычные `GROUP BY`; `ADM-21` (прайс) — обычная таблица; **без `user_id` и без текстов → нечего удалять по `PRIV-06`**; тот же источник для `LLM-05` | Своя страница админки (она нужна в любом случае) |

**Рекомендация: B.** Без `user_id` у журнала нет персональных данных вообще (`ADM-20` не требует разреза по людям). Если для отладки нужен разрез по пользователю — это режим разработки и Langfuse
(там есть вкладка «Users»). Дополнительно в админке можно показать ссылку «Открыть в Langfuse» **только** в режиме разработки; а по умолчанию её нет.
Колонка `trace_id` (OTel) в журнале позволяет в режиме разработки найти трассу в Langfuse по номеру. **Что изменило бы выбор:** согласие пользователя, что админка требует запущенный Langfuse → вариант A.

### 5.2 Учёт лимитов бесплатных тарифов в реальном времени (`LLM-05`)

Лимиты Groq (отчёт 04): `gpt-oss-120b` — 30 запросов/мин, 1000/день, 8000 токенов/мин, 200 000 токенов/день; лимиты **на модель**. Заголовки ответа `x-ratelimit-remaining-*` дают
остатки по запросам и по токенам в минуту, но **не дают токены в день** — этот счётчик нужно вести самим. Это операционное состояние, а не трасса.

| | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. В памяти процесса + журнал `ai_call` в Postgres** (рекомендую) | Скользящие окна «мин/день» на пару «провайдер+модель» в памяти; при старте окна восстанавливаются суммой из `ai_call` за последние 24 ч; заголовки `x-ratelimit-*` корректируют окно, 429 + `retry-after` размыкают «размыкатель» пары | Нет новых сервисов; переживает перезапуск; один процесс — гонок нет (приложение на одной машине) | Если запущено два процесса приложения — счёт разойдётся (мы не планируем) |
| B. Redis/Valkey Langfuse | Общий счётчик | Быстро | Это очередь Langfuse (`noeviction`, пароль, профиль может быть выключен) — **нельзя** делить с приложением |
| C. Только заголовки провайдера | Без своих счётчиков | Просто | Нет токенов/день; после перезапуска неизвестно; нет локальных и Z.ai (там своя логика) |

**Рекомендация: A.** Пример: за день ушло 180 000 токенов у `gpt-oss-120b` → лимитёр заранее отправляет следующий запрос в `gpt-oss-20b`, а админка показывает «90% дневного лимита».
Сброс «день» у Groq — точный момент сброса я не проверял [Н]; по умолчанию считаем скользящие 24 часа и корректируем по `x-ratelimit-reset-*`/429.
Таблицу журнала писать **в той же функции**, что кормит лимитёр (одна точка записи), и не из Langfuse.

## 6. Профиль Compose `observability` и память

### 6.1 Профиль (отчёт 08, решение 1: один `compose.yaml`, профили)

- **Профиль `observability` выключен по умолчанию** (`make up` и `make dev` его не поднимают; приложение работает полностью — журнал в Postgres, лимиты, админка).

- **Режим «без контейнеров» (`make dev`) Langfuse не меняет:** Langfuse как таковой без Docker не запустить (ClickHouse + S3 + очередь), поэтому приложение на хосте ходит на `http://127.0.0.1:3001`,
  а Langfuse остаётся в Docker. Если Docker недоступен — приложение работает без Langfuse (регистрация процессора пропускается, раздел 3.3).
- Проверка корректности: в `make doctor` — «Langfuse доступен/нет», «`TELEMETRY_ENABLED=false`», «порт привязан к 127.0.0.1», «нет переменных `LANGFUSE_*` в основном режиме».

Полный файл фрагмента — в приложении A (проверен `docker compose config` на Compose v5.5.1 [В]; **запуск не проверялся** [С]).

### 6.2 Память (замеров нет — только пределы, оценка [Н])

Пределы (`mem_limit`) в моём фрагменте и ориентир по idle-расходу (оценка, не замер):

(3) диск: образы ≈ 1,4 ГБ сжатыми (web 302 + worker 368 + ClickHouse 257 + SeaweedFS 194 + Postgres 117 + Valkey 17) [В: Docker Hub], тома растут вместе с трассами; в обычном режиме трассы малы (нет текстов);

## 7. Риски и открытые вопросы к пользователю

**Риски.**
1. **Быстрое устаревание Langfuse** (новая версия почти каждый день; в этом году — переход v3 → v4 со сменой модели данных). Закрепить точную версию (4.69.0), обновлять осознанно по заметкам к релизу. Резервного копирования в compose нет — для режима разработчика приемлемо.
2. **Зависимости OpenTelemetry** (раздел 3.2): сегодняшний релиз OTel 3.x ломает установку без пина. Оставить комментарий и проверку `pnpm peers check` в `make check`.
3. **Охранник опирается на форму атрибутов AI SDK 7** (`gen_ai.*`). Белый список — защита от новых; но если AI SDK **переименует** разрешённый атрибут, метаданные исчезнут из Langfuse (тихо). Лечится тестом «ожидаемые метаданные присутствуют».
4. **Маскирование тоже может ошибаться** (NER не идеальна) — в режиме разработки в Langfuse всё же могут попасть остатки ПДн; срок 7 дней и доступ только разработчику ограничивают риск. Это и есть смысл «режима разработки».
5. **SeaweedFS и создание ведра не проверены** (нет Docker) [С]. Запасной вариант — Chainguard-MinIO из официального compose (работает «из коробки», но проект заархивирован).
6. **Два места записи** (журнал и Langfuse) могут разойтись; эталон для цифр — журнал.
7. Когда `Langfuse` Data Retention понадобится по-настоящему (если проект вырастет) — EE-лицензия платная; наша ночная задача это обходит.

**Вопросы к пользователю** (в порядке важности):
1. **Согласен ли на «гибрид» (раздел 1.1): Langfuse для трасс, плюс тонкий журнал вызовов в Postgres без текстов и без пользователя** — для `ADM-20/21` и `LLM-05`? Это не «хранить трассы в своих таблицах», но и не «только Langfuse».
2. **Переформулировать `OBS-05` и `R39`:** «отдельный файл» → «отдельное хранилище трасс разработчика (Langfuse на 127.0.0.1), ≤ 7 дней через ночную очистку»? Без этого пункты SPEC буквально нарушены.
3. **Для демо-пользователя** (синтетические данные, `DEMO-01`) разрешить полные тексты в Langfuse на защите (чтобы показать дерево с шагами агента «вживую»)? Реальных ПДн там нет, но сейчас SPEC говорит «в демо выключен» — это изменение `R39`. Без него на защите покажем метаданные, токены, задержки, цепочку «Groq 429 → Z.ai ok» — тоже эффектно, но без текстов.
4. **Профиль выключен по умолчанию** (приложение работает без Langfuse) — подходит? Альтернатива «включён всегда» утяжеляет `make up` на ≈ 2 ГБ и 6 контейнеров.
5. **Docker Desktop или Engine** (связано с отчётом 05: iGPU и `/dev/dri`). Для Langfuse всё равно, но это влияет на лимит памяти VM.
6. Приемлем ли **английский интерфейс Langfuse** как инструмент разработчика?
7. В обычном режиме `userId` в Langfuse **не передаётся** (нечего связывать с `PRIV-06`) — устраивает, или нужен просмотр по пользователям даже в обычном режиме (тогда HMAC-псевдоним и обязательное удаление по `PRIV-06`)?
