## 0. Рекомендованная стратегия одним абзацем

Строить базу **от спроса и от структуры**, а не выгрузкой реестра. Хранение двухуровневое: (1) **каталог** с метаданными (реквизиты, статус, темы, ссылки, есть ли текст на pravo.by) на сотни актов; (2) **индекс** — полный текст, разбитый по структуре «акт → глава → статья → пункт → подпункт», с полнотекстовым поиском и векторами, только для актов с HTML-текстом, прошедших отбор. В каталог акты попадают из четырёх источников: стартового курируемого списка; **графа ссылок** (номера актов из текстов уже загруженных актов однозначно переводятся в ID pravo.by); ежедневных «Новых поступлений» после **дешёвых фильтров по метаданным** (раздел Нац. реестра, префикс ID, шаблоны заголовков, статус); **журнала вопросов без ответа**. Для отсечения лишнего LLM не нужна: темы акта, у которого есть текст, программа берёт из **рубрик Единого правового классификатора (ЕПК)** на карточке `guid=11031` и сопоставляет их с 10 темами по таблице. LLM остаётся для единиц спорных случаев в день. Поиск гибридный: (а) точное обращение по реквизиту («ст. 210 НК») без векторов; (б) полнотекстовый поиск с лемматизацией и (в) векторы, объединённые слиянием рангов; (г) подтягивание статей, на которые ссылается найденный фрагмент. Индекс версионируется **по фрагментам**: при новой редакции заново векторизуются только изменённые статьи и пункты, а ответ ссылается на конкретную версию фрагмента. Текст НПА берётся **только с pravo.by**. Постановления Пленума Верховного Суда (есть там же текстом) и разъяснения МНС подключаются как отдельные типы документов «разъяснение, не НПА» с явной пометкой.

### 1.3 Дешёвые фильтры релевантности (без LLM), в порядке применения

1. **Раздел реестра / префикс ID.** Разделы 15–18 (`D9…`, `R9…`, местные Советы и исполкомы) — в каталог не брать. Исключение — решения Минского горисполкома и облисполкомов о тарифах и ставках местных налогов, но только по ручному добавлению [Н: нужно ли — решает владелец продукта]. За 14.10.2026 это отсекло 27 из 41 [В].
2. **Шаблоны заголовков** (регулярные выражения, список правится в админке):
   - кадровые и персональные акты: `^О [А-ЯЁ][а-яё-]+ [А-ЯЁ]\.[А-ЯЁ]\.$`, «О назначении», «Об освобождении», «О присвоении», «О награждении», «О помиловании»;
   - разовые и территориальные: «Об изменении границ», «О предоставлении полномочий», «О выделении», «О создании (учреждения…)»;
   - **изменяющие акты** (`^О(б)? (внесении )?изменени|^О внесении (изменений|дополнений)`) не становятся отдельной записью каталога: это **событие** для изменяемых актов. Названия ПСМ часто прямо указывают цель («Об изменении постановлений Совета Министров … от 27 июня 2017 г. № 483 и от 28 июня 2023 г. № 416») [В]: из такого заголовка программа строит ID целей и внепланово проверяет их карточки.
3. **Статус по карточке:** есть «Дата ограничения действия» → утратил силу, не индексировать (в каталоге оставить отметку «утратил силу с …», чтобы отвечать «акт утратил силу»).
4. **Наличие текста:** HEAD `guid=3871` → 200 (кандидат на индекс) / 302 (только каталог, карточкой). Для новых актов без текста повторять проверку раз в неделю в течение 8 недель: текст может появиться, когда акт включат в ТБД [Н].
5. **Тема по ЕПК** (для актов с текстом): рубрики с карточки `guid=11031` → таблица «префикс ЕПК → тема “Кошта”» (пример ниже). Если ни одна рубрика не попала в 10 тем, акт уходит в «предложенные», а не автоматически в индекс.
6. **Вид органа / адресат** (для министерских актов без ЕПК): словарь органов-«своих» (МНС, Минтруда, Минфин, НБ, МАРТ, Минздрав, Минобразования, Минжилкомхоз, МВД (штрафы ГАИ), Минтранс) по полю «Вид акта, орган принятия» карточки. Остальные органы (Белстат, Минсельхозпрод, Госстандарт…) — в «предложенные».
7. **LLM — только для остатка:** заголовок плюс первые 1–2 тыс. знаков, если текст есть. Ожидаемо 1–5 актов в день [Н], то есть несколько запросов из 1000 в день. Режим «только предлагать» уже согласован.

## 2. Двухуровневое хранение и «ленивый» режим

### 2.1 Модель

```
Каталог (акт)            : id_pravo, вид, орган, дата, номер, № в Нац. реестре, название, краткие имена/псевдонимы,
                           темы (из ЕПК | вручную | LLM-предложение), рубрики ЕПК, статус (действует / утратил силу с …),
                           has_text (200/302 + дата проверки), источник попадания (ядро / граф от X / новые поступления / админ / спрос),
                           уровень (каталог | индекс | карточка), режим (авто / подтверждён админом), очередь изменений
Индекс (фрагменты)       : только для уровня «индекс», см. раздел 3
```

Сразу индексировать все акты из каталога, у которых **есть текст и подтверждена тема**: объём это позволяет (часы CPU один раз, дальше дельты), а ответ так всегда быстрый и предсказуемый.

### 2.2 Нужен ли «ленивый» режим

| | Ленивая догрузка по требованию | Заблаговременная индексация |
|---|---|---|
| Точность | ниже: поиск не находит то, чего нет в индексе; вопрос должен сначала «попасть» в акт по названию или рубрике в каталоге | выше: гибридный поиск видит все фрагменты |
| Скорость ответа | +3–5 с на загрузку, +1–3 с на разбор; векторизация среднего акта (100–200 фрагментов) займёт **1–5 мин на CPU** [Н], для кодекса — десятки минут | без задержек |
| Нагрузка на pravo.by | минимальная | умеренная, но плановая (ночью) |
| Предсказуемость для защиты | ответ зависит от того, что пользователь спросил раньше | одинаковый |

**Рекомендация:** основной режим — заблаговременный. Ленивый оставить **резервным путём** для двух случаев:
1. пользователь или агент назвал акт по реквизитам («Указ № 200», ссылка на pravo.by), а его нет в индексе;
2. вопрос попал по названию или рубрике в акт каталога, у которого есть текст, но он намеренно не индексирован (низкий приоритет).

Важная деталь: после загрузки и разбора акта **полнотекстовый поиск и точный поиск по статьям доступны сразу**, а векторы досчитываются в фоне. Ответ на «ленивый» вопрос строится по полнотекстовому поиску и структуре, с пометкой «акт добавлен в базу только что». Ограничения: не больше N ленивых загрузок в день (например, 20), только для актов, прошедших фильтры 1.3, с уведомлением админу; акт остаётся в индексе со статусом «добавлен по запросу». Если текста нет — карточка и ссылка (уже согласовано).

## 3. Как резать и индексировать

### 3.1 Что даёт HTML pravo.by (измерено на 22 актах) [В]

- Абзацы размечены классами: `article` (4 202 на 22 акта), `point` (11 413), `underpoint` (5 201), `chapter`, `newncpi` (обычный абзац, часть статьи), `changeadd`/`changei` (шапка «Изменения и дополнения»), `title`.
- У `article` атрибут `id` равен номеру статьи (`<p class="article" id="24">Статья 24. …`), он уникален внутри акта. У `point` `id` начинается заново в каждой статье (1, 2, 3, 1, 2…), поэтому путь фрагмента надо строить из иерархии, а не из одного `id`.
- В кодексах и законах единица — статья; в указах, ПСМ и Пленумах статей нет (`article` = 0), единица — пункт (ПСМ № 569: 155 пунктов, Указ № 108: 520 пунктов).
- Статьи бывают огромными: самая длинная в НК (Особенная часть) — **65 586 знаков**, в ТК — 43 946, в КоАП — 43 902. Резать только по статьям нельзя.
- В ГК 32 упоминания «исключена/Исключена»: исключённые статьи остаются заголовками, их надо хранить как фрагменты со статусом «исключена», чтобы честно отвечать «ст. N исключена».

### 3.2 Единица хранения

**Фрагмент = наименьшая цитируемая единица, которая помещается в лимит**, внутри дерева:

```
акт → (раздел) → (глава) → статья → (часть) → пункт → подпункт
```

Правило нарезки:
1. Статья (или пункт для актов без статей) целиком, если ≤ ~1 500 знаков.
2. Иначе — по пунктам; подпункты одного пункта склеиваются, пока не превышен лимит; части статьи без нумерации (`newncpi`) — по абзацам.
3. К тексту для векторизации и полнотекстового поиска **приписывается «хлебная крошка»**: «НК (Особенная часть) › Глава 16 › Статья 209. Стандартные налоговые вычеты › п. 1 › пп. 1.1». Дословность цитаты проверяется по **чистому тексту фрагмента без крошки**.
4. Целевой размер ~800–1 500 знаков (≈200–400 токенов) [Н]: укладывается в 512 токенов у FRIDA и оставляет место в узком контекстном бюджете Groq (8K токенов в минуту, `tech-factcheck.md` [С]). Узкий бюджет — главный аргумент за точный поиск: в контекст влезет 6–10 фрагментов, а не 30.

Метаданные фрагмента: `act_id`; `path` (например, `art=209/p=1/pp=1.1`; надстрочные номера — «20¹» хранить как `20.1`, разметку pravo.by для них не проверял [Н]); `heading` статьи; `breadcrumb`; `text`; `hash` нормализованного текста; `kind` (норма / определения / переходные / вступление в силу / приложение / исключена); `themes` (наследуются от акта и уточняются по главе); `refs_out` (см. 3.4); `version` (см. 4); `anchor` для ссылки, если pravo.by поддерживает переход к `#id` [Н — проверить в браузере].

### 3.3 Поиск: какие варианты рассмотрены

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| Только векторы | понимает бытовые формулировки («вернуть телефон в магазин») | промахивается на номерах, суммах, терминах («стандартный вычет», «ст. 210»); плохо различает похожие статьи разных актов | не единственный |
| Только полнотекстовый поиск (BM25) с русской морфологией | точен на терминах, мгновенен, без GPU, индекс сразу после разбора | не понимает перефразирование | обязателен |
| **Гибрид: полнотекстовый + векторы + слияние рангов (RRF)** | лучшее из обоих, дёшево | две системы индексов | **основной** |
| Переранжирование кросс-энкодером (например, bge-reranker-v2-m3) | заметно точнее топ-5 [С по общим данным] | на CPU: 20 пар × ~350 токенов ≈ 7 тыс. токенов → **6–35 с** [Н] — для чата много | **опционально**: топ-10, отрывки до 256 токенов; включать по результатам замеров |
| Переранжирование LLM | без локальной нагрузки | тратит дневной лимит токенов | нет, только в отладочной оценке |
| Граф знаний целиком | красиво | дорого строить, мало выигрыша сверх ссылок между статьями | нет; нужен только граф ссылок (3.5) |
| Структурный поиск по реквизитам | 100 % точности на «ст. 210 НК», «п. 3 ст. 13 Закона о защите прав потребителей» | только явные ссылки | **обязателен**, срабатывает первым |

Конвейер запроса:
1. **Разбор реквизитов** (регулярные выражения + таблица псевдонимов актов: НК, ГК, ТК, ЖК, КоАП, ПИКоАП, КоБС, «Закон о защите прав потребителей», «ЗоЗПП», «Указ 345»…; псевдонимы правятся в админке). Нашёлся реквизит — берём фрагменты напрямую.
2. **Классификация темы вопроса** (дешёвый классификатор или словарь; используется как мягкое усиление, не жёсткий фильтр).
3. **Расширение запроса** словарём «бытовое → юридическое» (зарплата → заработная плата, вернуть → возврат/обмен, ИП → индивидуальный предприниматель). Словарь курируемый; LLM-переформулировка — одним вызовом, только если первый проход ничего не нашёл.
4. Полнотекстовый поиск по леммам (например, лемматизация pymorphy3 при индексации и при запросе; или словарь `russian` в PostgreSQL; или FTS5 в SQLite с заранее лемматизированным полем) + векторный поиск → RRF → топ-20.
5. Фильтры: только действующие акты и действующие версии фрагментов; исключённые статьи — только при прямом обращении.
6. (Опционально) переранжирование топ-10.
7. **Расширение по графу** (3.4): к выбранным фрагментам добавить статью с определениями терминов и статьи, на которые они ссылаются, в пределах бюджета токенов.
8. Сборка контекста: фрагменты с реквизитами, путём, датой снимка и пометкой «есть принятые, но не вступившие изменения».

### 3.4 Граф ссылок между статьями

- **Внутренние ссылки** («статьей 209 настоящего Кодекса», «пунктом 3 статьи 13 настоящего Закона»): в 22 текстах их от 0 до 944 на акт (НК, Особенная часть — 944, ГК — 360) [В]. Они разрешаются регулярными выражениями в `path` того же акта.
- **Внешние ссылки по реквизитам** («Законом Республики Беларусь от 8 июля 2008 г. № 369-З»): перевод в ID для законов, указов и ПСМ однозначен (1.1). В теле 22 текстов — 152 различных акта [В].
- **Ссылки на кодексы по названию** («Гражданским кодексом Республики Беларусь», «Трудовым кодексом») — по таблице псевдонимов.
- Неявные ссылки («в порядке, установленном Советом Министров», «законодательством») не разрешаются, и это нормально.
- Использование: (а) подтягивание контекста при ответе (1 шаг, с бюджетом); (б) «См. также» в карточке цитаты; (в) обнаружение актов для каталога (1.2 Б); (г) уведомление «изменилась статья, на которую ссылается ваша норма» (на будущее).

## 4. Обновления и редакции

### 4.1 Хранение снимков и версий

```
snapshot        : act_id, fetched_at, raw_html_gz, content_length, sha256, header_amendments[] (ID из шапки),
                  card_amendments[] (ID с карточки), parse_status (ok / quarantined), parser_version
fragment_version: fragment_key (act_id + path), text, hash, first_seen_snapshot, last_seen_snapshot | NULL,
                  status (действует / изменён / исключён / удалён), embedding_model, embedding
answer_citation : answer_id, fragment_version_id, quote_start, quote_end, snapshot_date
```

Алгоритм для новой редакции:
1. Разобрать HTML в дерево фрагментов.
2. Сопоставить со старой версией по `path`. Хэш совпал — продлить версию (`last_seen` = новый снимок). Хэш другой — закрыть старую версию и создать новую. Пути нет в новом снимке — «удалён/исключён». Новый путь — «добавлен».
3. **Перенумерация:** если фрагмент с другим `path` имеет тот же хэш, что и пропавший, отметить «перенесён» и не векторизовать заново.
4. Векторизовать только новые версии. Полнотекстовый индекс обновить для тех же фрагментов.
5. Сырой HTML хранить всегда: при смене парсера всё пересобирается из снимков без запросов к сайту.

Две даты не путать: **«наблюдали в тексте с даты снимка»** (знаем точно) и **«юридически действует с»** (знаем, только если её указал изменяющий акт). Пользователю показывать «редакция по состоянию на <дату снимка>»; дату вступления — только если она взята из текста изменяющего акта с дословной цитатой.

### 4.2 Связь ответов со статьёй-версией

Каждая цитата в ответе хранит `fragment_version_id` и смещения. Это даёт: (а) «на момент ответа норма звучала так» даже после изменения; (б) пометку в истории диалога «эта статья изменилась <дата>» — дешёвый запрос «есть ли у версии `last_seen` и преемник»; (в) пересчёт тестов качества (`make eval`) на новой редакции: какие эталонные ответы поменялись.

### 4.3 Вступление «по этапам» и принятые, но не вступившие изменения

Что известно [В, ресерч pravo.by + 1.1]: текст на pravo.by — действующая на сегодня редакция; карточка уже показывает принятые изменяющие акты; у части изменяющих актов есть HTML-текст со статьёй «Вступление в силу» (№ 150-З), у части — только PDF (закрыт robots.txt).

Схема:
1. **Очередь** = `card_amendments − header_amendments` (для актов 2012+ точно, для старых — по датам). Всё, что в очереди, — «принято, не отражено в тексте».
2. Для каждого изменяющего акта из очереди: HEAD `guid=3871`.
   - **Есть текст** → загрузить, найти статью «Вступление в силу» и статьи вида «Внести в <акт> следующие изменения: … статью N изложить в следующей редакции». Извлечение «какой акт → какие статьи → с какой даты» делает LLM **один раз на изменяющий акт** (их единицы в месяц); каждую дату и номер статьи программа проверяет дословным совпадением с текстом. Результат — предупреждение **на уровне фрагмента**: «ст. 10 ТК изменится с 01.07.2027 (Закон № 150-З, ст. 48)».
   - **Нет текста** → предупреждение на уровне акта: «принят Закон № 170-З от 17.07.2026, изменяющий этот акт; содержание изменений в базе отсутствует» + ссылка на карточку.
3. **Календарь проверок:** все даты «вступают в силу …» из шапок и из статей о вступлении → внеплановый полный снимок на следующий день после даты.
4. **Контроль:** дата прошла, а текст не изменился за 7 дней → уведомление админу (возможна задержка консолидации на pravo.by).
5. Утрата силы: «Дата ограничения действия» на карточке → акт выводится из поиска, ответы по нему — «акт утратил силу с …»; если утративший силу акт назван в перечне нового акта (как Указ № 530 в Указе № 108), показать замену.

Ответ не может строиться только на разъяснении: нужна хотя бы одна норма НПА или явная фраза «в НПА базы прямой нормы нет, есть разъяснение МНС».

## 6. Вежливость и устойчивость загрузки

### 6.1 Темп и расписание

- Один поток, **1 запрос в 3–5 с** со случайным разбросом. Окно — ночь по Минску (например, 02:00–06:00). Без параллелизма.
- **Уровни частоты** (вместо «всё каждый день»):
  - ежедневно: карточки и HEAD текстов ~50 «горячих» актов (кодексы, ключевые законы, всё с непустой очередью изменений) + акты, названные в заголовках вчерашних «Новых поступлений» + 1 страница «Новых поступлений»;
  - раз в 3–7 дней по кругу: остальные акты индекса;
  - раз в неделю: полный GET с хэшем для всех актов индекса (защита от изменений, при которых `content-length` не меняется). Это ~200 × ~100 КБ gzip ≈ 20 МБ, ~15 мин.
  - Итого ~100–200 запросов в сутки при 200 актах [Н, расчёт], 10–15 минут.
- Первичная загрузка (ядро + граф) — ~300–600 запросов разово, растянуть на 1–2 ночи.

### 6.2 Идентификация

- Свой User-Agent: `KoshtBot/<версия> (+<URL проекта или e-mail оператора>)`. Стандартные UA библиотек получают 403 (ресерч pravo.by). Под браузер не маскироваться.
- Контакт берётся из настроек админки (каждая локальная установка — свой оператор); без контакта загрузчик не запускается.
- `Accept-Encoding: gzip`: НК — 164 КБ вместо 1,1 МБ [В].

### 6.3 robots.txt

- Загружать robots.txt раз в сутки и проверять **каждый** URL перед запросом.
- Осторожно [С]: стандартный `urllib.robotparser` в Python не понимает `*` в середине пути, а у pravo.by такие правила есть (`/*?print=`, `*/index.php`). Нужен разборщик с поддержкой синтаксиса Google (например, protego) и тест на реальном robots.txt pravo.by: `/poisk-v-tbd/?category=…` → запрещено, `/document/?guid=3871&p0=…` → разрешено.

### 6.4 Повторы и отказ

- 5xx и таймауты: повтор через 30 с → 2 мин → 10 мин, затем акт откладывается до следующего цикла.
- 403 или 429: **остановить весь цикл до следующих суток** и уведомить админа (возможна блокировка; продолжать — невежливо).
- Предохранитель: больше 20 % ошибок за цикл → стоп и уведомление.
- Журнал запросов (URL, код, размер, время) — в админке, раздел «журнал».

### 6.5 Изменение вёрстки

- **Контрактные тесты парсера** на сохранённых образцах HTML (5–7 актов разных видов: кодекс, закон, указ, ПСМ, Пленум, акт с подпунктами, акт с исключёнными статьями) в `make test` (офлайн).
- **«Канарейки»** в каждом ежедневном цикле — 3 известных акта, для которых проверяется: число статей (Закон № 90-З — 51 статья [В]), наличие известных заголовков («Статья 20. …»), наличие блока «Изменения и дополнения», карточка с полем «Регистрационный номер Национального реестра».
- **Карантин снимка:** если новая редакция теряет больше 5 % фрагментов, пропала шапка, кодировка битая или статей 0 — снимок не применяется, остаётся прежняя версия, админ получает уведомление «вероятно, изменилась вёрстка». Автоматически ничего не удалять.
- Версия парсера хранится в снимке; после исправления парсера — пересборка из сохранённого HTML.

### 6.6 Правовое

Одно письмо в НЦЗПИ (portal@center.gov.by, ресерч pravo.by) до публичного запуска: описание сценария, объём (~100–200 запросов в сутки ночью), цитирование со ссылкой. Отдельно спросить про автоматическое чтение рубрик ТБД (`poisk-v-tbd`). Ответ записать в документацию.

## 7. Поток работы системы

### 7.1 Первый запуск (фоновое задание из админки, с прогрессом)
1. Загрузить robots.txt и проверить канарейки (структура сайта не изменилась).
2. Стартовый каталог (~27 актов, правка в админке): для каждого — карточка `3961` (реквизиты, статус, изменяющие акты), HEAD `3871`, карточка `11031` (рубрики ЕПК).
3. Акты с текстом: GET → снимок → разбор в дерево → фрагменты → полнотекстовый индекс (сразу) → очередь векторизации.
4. Извлечь ссылки (внутренние → граф; внешние → кандидаты в каталог).
5. Кандидаты 1-го шага: карточка + HEAD → фильтры 1.3 → «авто в каталог», «предложить админу» или «отбросить» (с причиной в журнале).
6. Построить очереди изменений и календарь дат вступления; для изменяющих актов с текстом — извлечение этапов (LLM, единицы вызовов).
7. Векторизация в фоне, ночью. До её окончания поиск работает на полнотекстовом индексе и реквизитах — в админке видно «векторный индекс: 43 %».
8. Отчёт админу: сколько актов в индексе, сколько только карточкой, сколько кандидатов ждёт решения.

### 7.2 Ежедневный цикл (ночью)
1. robots.txt, канарейки. Ошибка → стоп и уведомление.
2. «Новые поступления» за вчера → фильтры 1.3:
   - изменяющие акты → определить цели (из заголовка или текста) → внеплановая проверка целей;
   - новые самостоятельные акты → тема (ЕПК при наличии текста, иначе словарь органов, иначе LLM) → «добавить автоматически» или «предложить» (переключатель в админке), уведомление.
3. «Горячие» акты + акты по кругу: карточка (новые изменяющие акты, утрата силы) → HEAD (длина) → при изменении GET → снимок → дифф по фрагментам → новые версии → векторизация только изменённого → предупреждения о затронутых ответах и цитатах.
4. Наступившие даты вступления → полный снимок; дата прошла без изменений → уведомление.
5. Раз в неделю: полный GET с хэшем для всех; повторная проверка «нет текста» у новых актов; сводка «вопросы без ответа → кандидаты».
6. Раз в месяц: страницы ведомственных сайтов из списка → новые ссылки на pravo.by → кандидаты.

### 7.3 Вопрос пользователя
1. Вопрос → защита от инъекций → разбор реквизитов → тема.
2. Реквизит найден → фрагменты напрямую; иначе гибридный поиск → (переранжирование) → расширение по графу.
3. Ничего релевантного выше порога в индексе → поиск по каталогу (названия, псевдонимы, рубрики ЕПК):
   - акт с текстом, но не в индексе → ленивая загрузка (полнотекстовый поиск сразу) → ответ с пометкой;
   - акт только карточкой → «в базе нет текста этого акта, см. карточку <ссылка>»;
   - ничего → «в моей базе нет» + запись темы в журнал спроса.
4. LLM получает 6–10 фрагментов с реквизитами, датой снимка и пометками об изменениях → ответ с цитатами.
5. Программа проверяет дословность каждой цитаты по `fragment_version.text`; несовпадение — цитата удаляется или ответ перегенерируется.
6. Ответ: цитаты, ссылка на `guid=3871` (или карточку), «редакция на <дата снимка>», предупреждение о принятых, но не вступивших изменениях, дисклеймер. Сохранить `answer_citation` с `fragment_version_id`.

## 9. Формулировки для спецификации

1. Правовая база хранится на двух уровнях: **каталог** актов (реквизиты, статус, темы, наличие текста, источник попадания) и **индекс** (полный текст по фрагментам) — только для актов с HTML-текстом на pravo.by, прошедших отбор.
2. Акты попадают в каталог из: стартового списка; ссылок в текстах уже загруженных актов (1 шаг); ежедневных «Новых поступлений»; ведомственных страниц из настраиваемого списка; журнала вопросов без ответа; ручного добавления по ссылке или списку ссылок.
3. Отсев нерелевантных актов выполняется программно по метаданным (раздел Нац. реестра, префикс ID, шаблоны заголовков, статус, наличие текста, рубрики ЕПК, орган); LLM применяется только к актам, которые эти правила не решили. Причина отсева видна в журнале.
4. Тема акта с текстом определяется по рубрикам ЕПК (карточка `guid=11031`) через редактируемую таблицу «рубрика ЕПК → тема».
5. Изменяющие акты не становятся отдельными записями каталога, а порождают событие проверки изменяемых актов.
6. Единица индекса — наименьшая цитируемая структурная единица (статья, пункт, подпункт) с полным путём «акт → глава → статья → пункт → подпункт»; длинные статьи делятся по пунктам; исключённые статьи хранятся со статусом «исключена».
7. Поиск: сначала точное обращение по реквизитам («ст. 210 НК») по таблице псевдонимов актов; затем гибридный поиск (полнотекстовый с русской морфологией + векторный, слияние рангов); затем добавление фрагментов, на которые ссылается найденный (1 шаг, в пределах бюджета токенов).
8. Новый акт доступен в полнотекстовом поиске сразу после разбора; векторный индекс достраивается в фоне, прогресс виден в админке.
9. Если вопрос относится к акту из каталога, у которого есть текст, но нет индекса, система догружает акт по требованию (не больше N в сутки) и сообщает админу.
10. Каждый фрагмент версионируется: при новой редакции создаются версии только для изменённых фрагментов, и только они векторизуются заново; сырой HTML каждого снимка хранится.
11. Модель эмбеддингов выбирается замером на этой машине (скорость на 500 фрагментах и качество на эталонном наборе вопросов); при каждом векторе хранится имя и версия модели; смена модели — фоновое задание полной переиндексации.
12. Каждая цитата в ответе ссылается на конкретную версию фрагмента; в истории диалога отмечается, что норма с тех пор изменилась.
13. Для каждого акта ведётся очередь принятых, но не отражённых в тексте изменений; если у изменяющего акта есть текст, даты вступления и затронутые статьи извлекаются один раз и проверяются дословным совпадением; предупреждение показывается на уровне статьи, а без текста — на уровне акта.
14. Даты вступления в силу ставят внеплановую проверку; «дата прошла, текст не изменился за 7 дней» — уведомление админу.
15. Текст НПА берётся только с pravo.by. Постановления Пленума ВС — отдельный тип «разъяснение суда». Разъяснения МНС (этап диплома) — отдельный тип «разъяснение, не НПА», каждое подтверждается админом и помечается «могло устареть», если цитируемая статья изменилась после его даты.
16. Загрузчик: один поток, 1 запрос в 3–5 с, ночное окно, свой User-Agent с контактом оператора (без контакта не запускается), gzip, проверка каждого URL по robots.txt с поддержкой шаблонов `*`; остановка цикла при 403/429 или при >20 % ошибок.
17. Частота: ежедневно — «горячие» акты, акты с очередью изменений и акты, названные в заголовках новых поступлений; остальные — по кругу раз в 3–7 дней; раз в неделю — полная сверка хэшей.
18. Парсер покрыт офлайн-тестами на сохранённых страницах; в каждом цикле проверяются канарейки; снимок со структурной аномалией (потеря >5 % фрагментов, нет статей, нет шапки) помещается в карантин и не заменяет действующую редакцию.
